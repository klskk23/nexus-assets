# 013 · 权限模型

**分支**：`013-permissions` ｜ **状态**：设计已定，待实现

## 缘起

这套系统到今天只有一个准入边界：邮箱域名白名单。进得来的人，什么都能做——删设备、
改已经发生过的流转记录、改状态定义、重算把全库编号刷掉。`users` 表里有一列 `role`
（`001_init.sql`，默认 `'admin'`，注释写着 reserved, not enforced yet），地基在，
从没接过线。

本轮把线接上：**角色是一组权限开关，用户绑一个角色**。

设计访谈里反复回到同一个判断：先把「谁能做什么」做对，不碰「对哪些设备」。
带范围的权限（只能管某棵类别子树、只能管某个仓库）会让每一条查询都要按人收窄，
而设备会流转——一台从上海签出到北京的机器归谁管，是个必须回答且怎么答都有人觉得
不对的问题。范围以后要加，在角色表补一列就行，不用推翻这一轮。

## 决策

### 决策 77：权限是全局开关，没有范围

一个开关回答「能不能」，不回答「对哪些」。「修改设备 ✓」的意思是全公司的设备都能改。

由此，**系统里没有任何一条查询需要按人过滤**——列表还是那个列表，导出还是那份导出，
只是有些按钮按不动。这是本轮成本可控的全部原因。

### 决策 78：读默认全开放，只有审计要权限

台账的价值在于全员能查：谁手上有哪台机器、某台机器在哪，这是它每天被打开的理由。
配置类的读（字段、型号、状态、持有方）也开放——普通用户录设备时本来就要看到字段和
型号，关掉会让录入表单变成空白。

**账号列表同样开放**：流转给人时要在里面挑人，锁了它等于锁了流转。「管账号」
（新建、停用）仍然是写权限。

唯一例外是**审计**：它是关于人的，不是关于设备的。

### 决策 79：十八个开关

| 组 | 开关 key | 名称 | 管住的端点 | 普通用户预设 |
|---|---|---|---|---|
| 资产 | `asset.create` | 录入设备 | `POST /assets` | ✓ |
| | `asset.update` | 修改设备 | `PATCH /assets/:id` | ✓ |
| | `asset.delete` | 删除设备 | `DELETE /assets/:id`、`POST /assets/delete` | ✗ |
| 流转 | `transfer.create` | 流转 | `POST /transfers` | ✓ |
| | `transfer.update` | 修改流转记录 | `PATCH /transfers/:id` | ✗ |
| 日常 | `print` | 打印标签 | `POST /print` | ✓ |
| | `import` | 导入 | `POST /import/preview`、`/import/commit` | ✓ |
| | `export` | 导出 | `GET /export.csv`、`GET /rows` | ✓ |
| 配置 | `schema.manage` | 管理类别与字段 | 类别与字段的增改删、绑定解绑、**重算** | ✗ |
| | `model.manage` | 管理型号 | `/models` 的增改删 | ✗ |
| | `status.manage` | 管理状态 | `/statuses` 的增改删 | ✗ |
| 持有方 | `holder.create` | 新增持有方 | `POST /holders` | ✓ |
| | `holder.update` | 修改持有方 | `PATCH /holders/:id`（改名、改上级、改备注） | ✗ |
| | `holder.delete` | 删除持有方 | `DELETE /holders/:id` | ✗ |
| | `holder.default_stock` | 设为默认库存点 | `PATCH /holders/:id` 的 `is_default_stock` | ✗ |
| 管理 | `user.manage` | 管理账号 | `POST /users`、`PATCH /users/:id` | ✗ |
| | `audit.read` | 查看审计 | `GET /audit` | ✗ |
| | `role.manage` | 管理角色 | 角色的增改删、把用户绑到角色上 | ✗ |

几处切法值得记下理由：

- **资产的增/改/删拆成三个**：仓管要能录、能改自己录错的，但不该能删。
- **重算并进「管理类别与字段」**：它名义上属于改字段，后果是重写整棵子树上千台设备的
  编号。访谈里权衡过单列，结论是不值得多一个开关——能改表达式的人本来就在改编号。
- **「修改流转记录」单列**：流转是历史。给能签出的人顺带给这个是错的。
- **持有方拆成新增/修改/删除**：业务是不断有新客户，一线要能自己加，但不该能改也不该
  能删既有的。
- **「设为默认库存点」单列**：它决定全系统「归还」时东西回到哪里，点错一次之后所有
  未指定目的地的归还都去错地方，且不会有人立刻发现。它不是某个持有方的属性。
- **不给「建密钥」设开关**：他能做的事本来就能做，密钥没扩大边界，只是换了调用方式。

### 决策 80：管理员是一个标记，不是十八个勾

角色表上一列 `is_admin`，含义是「全部权限，**包括以后新增的**」。

不用「十八个勾全开」是因为下一轮加第十九个开关时，那一行的第十九个勾默认是关的——
除非每次加开关都记得写迁移把它打开。漏一次，管理员就悄悄少一样权限，而没人会想到
去查角色表。

管理员角色仍然是角色列表里的一行，仍然能改名、能被绑定；它的权限不可编辑，因为它
没有勾可改。

### 决策 81：一个用户一个角色

不算并集。多角色会让「张三为什么能删设备」的答案变成「因为他还在另一个角色里」，
排查要翻两三个地方。需要组合时，复制一个角色改两个勾，比解释并集便宜。

### 决策 82：必须始终至少有一个启用状态的管理员

三条路都撞这一条：降级、停用账号、删角色。另加两条：

- **自己不能降级自己**；
- **角色下还绑着人时拒绝删除**，并列出是谁——与删持有方、删状态同一种做法。

管理员角色本身**可以删除**，前提是没人绑着它，而「至少一个启用的管理员」会在最后
一个人被移走时先拦住。

### 决策 83：升级不改变任何人今天的能力

存量用户**全部迁成管理员**。上线那一刻没有人的能力发生变化，收权是之后由管理员逐个
做的另一件事。升级和收权分开，出问题时知道是哪一件引起的。

新账号：管理员在界面上新建时**当场选角色**，无默认。

**OIDC 登录方式里的第一个人成为管理员**，不论系统里有没有本地管理员账号。这是给
「装好机器、第一次用 Google 登进来的人」准备的：他就是要配置这套东西的人。之后每个
OIDC 自动创建的账号都是普通用户。

> 已知代价：唯一的准入边界是邮箱域名白名单，所以「第一个用 OIDC 登录的人」在理论上
> 可能不是装机的人。这次提升会进审计，bootstrap 管理员随时能把他降下来。

### 决策 84：密钥的权限就是主人此刻的权限

用户建的 `nxk_…` 密钥不带自己的权限（决策 74 定的「等同于它的主人」不变）：主人被
降级，密钥当场跟着降。不给它第二套模型。

**配置文件里的 `NEXUS_ADMIN_API_KEY` 永远是管理员**，与它对应账号绑了什么角色无关。
理由和它存在的理由一致：它是给必须一直能工作的东西用的——备份、监控——写在配置文件
里、界面上撤销不了。让它受界面上一次误操作影响，就取消了它的意义。

### 决策 85：导入要同时具备「录入设备」和「导入」

否则会出现「不能录一台、却能一次录三百台」的自相矛盾状态。这是唯一一处开关之间有
依赖的地方，写在这里以免以后被当成 bug 改掉。

## 界面

- **页面都进得去**（读是开放的），差别只在按钮按不按得动。
- **按钮禁用而不是隐藏**，并说明缺哪个权限——与既有约定一致（「不适用的菜单项禁用而
  不是隐藏」）。同事看得见功能存在，知道该找谁开。
- **例外：审计**没权限时从导航里去掉。一个永远打不开的页面不该占位置。
- `/me` 返回有效权限数组与 `is_admin`，前端据此禁用。**把关的永远是服务端**，逐端点
  校验——前端那份只是为了不显示按不动的希望，和持有方树的 `allowedParents` 同一个道理。
- 角色管理是一个新页面（设置里进），沿用元数据表格约定：点击行编辑、右键出菜单、
  破坏性操作要确认并输入标识。
- 权限不足统一 **403**，文案指明缺哪个权限；对话框里发生的拒绝显示在对话框里。

## 审计

建角色、改角色的开关、把谁绑到哪个角色，全部进审计。新增目标类型 `role`。

## 数据模型

```sql
-- 迁移 016
CREATE TABLE roles (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  is_admin    INTEGER NOT NULL DEFAULT 0,  -- 1 = 全部权限，含以后新增的
  permissions TEXT NOT NULL DEFAULT '[]',  -- JSON 数组，is_admin=1 时忽略
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);
ALTER TABLE users ADD COLUMN role_id TEXT REFERENCES roles(id);
```

迁移同时：建「管理员」（`is_admin=1`）与「普通用户」（决策 79 的预设开关）两行；
把存量用户全部绑到「管理员」。`users.role` 那一列保持不动——它从未被读过，删它是另一
件事。

## 动工前先补的洞

**删除持有方没有检查 `home_holder_id`**。一台机器的 home 是某仓库、此刻却签在人手上
时，那个仓库删得掉；之后归还时 `applyOne` 解析出的 home 是一个已经不存在的 id，而
流转路径上没有存在性校验——设备会落到一个没有名字的持有方上，且不报错。

补第四条守卫：**被任何设备指为 home 时拒绝删除**，并列出是哪几台，与「有设备持有」
那条同一种做法。这个洞与权限无关，是它自己的 bug，先修再动权限。
