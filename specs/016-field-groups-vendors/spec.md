# Feature Specification: 字段组与厂商实体

**Feature Branch**: `016-field-groups-vendors`

**Created**: 2026-09-05

**Status**: Draft

**Input**: 见本轮 `/grill-me` 访谈：字段组（绑定时展开）、厂商实体化、绑定目标从两个变三个、
互斥规则改为「类别 vs 设备」、型号实时继承厂商字段、字段页加组与厂商筛选、资产页加厂商筛选。

## 决策记录（105–113）

上一轮 015 的决策编号到 104，本轮从 105 起。

- **决策 105：字段组是绑定时展开的糖，不是运行时概念。** 把一个组绑到某个目标，
  等于把组内每个字段逐个绑到那个目标；库里落的仍是既有的绑定表，一个字段一行。
  `EffectiveFields` 不因为组而改动一行。
  代价是明确接受的：往组里加第七个字段，已经绑过的十二个型号**不会**自动跟上，
  得有人重新绑一次组。换来的是整套解析、唯一性、导出、列解锁完全不必认识「组」这一层。
- **决策 106：组内任一成员违反互斥，整组拒绝。** 不写入任何一行，并点名是哪个字段、
  卡在哪里。与「绑定被拒则字段也不创建 —— 半个结果不值得留下」是同一条原则：
  「绑了半个组」这种状态事后无从分辨，因为展开后不留痕迹。
- **决策 107：删除组不解除任何已展开的绑定。** 组只是当时的一个快捷方式。
  确认框必须写明这一点，否则「删了组，字段却还在型号上」会被当成 bug。
- **决策 108：厂商是实体，型号引用它。** `product_models` 的自由文本厂商列变成
  指向厂商实体的可空引用。可空是必须的：有些设备就是没有厂商（白牌、自组）。
- **决策 109：迁移按原样，一个不同的字符串一个厂商。** 绝不在迁移里归并
  `Dell` / `DELL` / `dell`。归并会让原本合法共存的两台同名型号撞上唯一约束，
  使迁移在别人的生产库上当场失败。归并只能是事后的、能报冲突的人工动作。
- **决策 110：绑定的互斥规则从「类别 vs 型号」改为「类别 vs 设备」。**
  设备侧包含型号与厂商，两者可以混绑，取并集。
  015 定互斥时给了三条理由，今天只剩两条成立：冗余，以及唯一性范围失去单一答案。
  第三条（两条绑定的必填开关各说各话）已随 018 把必填搬到字段身上而消失。
  型号与厂商在剩下两条上是同一侧的：它们都在回答「哪台设备」，并起来仍是一个集合。
  类别不同 —— 它回答「哪一类设备」，与设备侧并起来就没有单一答案了。
- **决策 111：型号实时继承厂商的字段。** 型号的有效字段 = 自己绑的 ∪ 它厂商绑的。
  新建的型号开箱即有，不需要任何人记得回去补 —— 「得有人记得」正是这套系统一直在消灭的东西。
- **决策 112：换厂商会归档，但改之前先告知波及多少台。** 值留在 `attrs` 里，
  读取时因为不在有效字段集内而被切进 `archived_attrs`，写路径一行不做。
  与 015 决策 98 同一机制。但改一个型号的厂商一次波及该型号的**所有**设备，
  所以保存前必须 dry-run 告知台数，与「勾必填会波及 N 台」「改表达式即重算」同一套做法。
- **决策 113：字段行同时报「绑在哪」与「到达哪」。** `vendor_ids` 说前者，
  `model_ids` 说后者且是展开后的到达集。这样列解锁、录入表单收窄、导出逐行留空、
  导入行不匹配拒绝这四处判定一行都不用改 —— 它们本来就是按到达集判的。
  `binding_mode` 的取值随之从 `category | model | unbound` 改为
  `category | device | unbound`。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一次给整个产品线加字段（Priority: P1）

管理员新采购了一批戴尔设备，戴尔全系都有 ServiceTag。他建一个 ServiceTag 字段，
绑到厂商「Dell」上，于是现有的每一款戴尔型号立刻都有了这个字段。
三个月后同事新建了第六款戴尔型号，它开箱就带 ServiceTag，没有人需要想起这件事。

**Why this priority**: 这是整个特性的动机。今天要达到同样效果，得把字段逐个绑到五款型号上，
而且下个月的第六款一定会被忘掉 —— 忘掉的后果是那批设备少一个字段，而没有任何东西会提醒。

**Independent Test**: 只做厂商实体化与继承，不做字段组，这个故事就完整可用。

**Acceptance Scenarios**:

1. **Given** 厂商 Dell 下有三款型号，**When** 把 ServiceTag 绑到 Dell，
   **Then** 这三款型号的有效字段集里都出现 ServiceTag，且录入这三款型号的设备时表单里有它
2. **Given** ServiceTag 已绑到 Dell，**When** 新建第四款 Dell 型号，
   **Then** 该型号的有效字段集里已有 ServiceTag，无需任何额外操作
3. **Given** 一台没有厂商的型号，**When** 查看它的有效字段集，
   **Then** 其中不含任何厂商绑定的字段
4. **Given** ServiceTag 已绑到 Dell，**When** 试图把它再绑到某个 Dell 型号上，
   **Then** 界面上该型号的勾选框是禁用的，并说明「厂商 Dell 已经提供了这个字段」

### User Story 2 - 把常用的一组字段一次绑上（Priority: P2）

网络设备总要记 MAC、管理 IP、固件版本这三样。管理员把它们收进一个叫「网络参数」的组，
以后新增一款交换机型号时，绑一次组就够了，不用记住是哪三个。

**Why this priority**: 省的是重复劳动与遗漏，价值真实但不改变任何数据模型 ——
它完全建立在既有的绑定机制上。

**Independent Test**: 只做组、不做厂商，这个故事照样成立（组可以绑类别与型号）。

**Acceptance Scenarios**:

1. **Given** 组「网络参数」含三个字段，**When** 把它绑到型号 EDGE620，
   **Then** 该型号绑定了这三个字段，与逐个绑三次的结果完全一致
2. **Given** 组内的「基准 MAC」已经绑在某个类别上，**When** 把该组绑到一个型号，
   **Then** 整个操作被拒绝、一行都没写入，且拒绝信息点名是「基准 MAC」以及它卡在哪个类别
3. **Given** 组「网络参数」已经绑到三个型号，**When** 删除这个组，
   **Then** 那三个型号的字段原样保留，且删除确认框在删除前就说明了这一点
4. **Given** 一个字段同时属于「网络参数」与「必备信息」两个组，
   **When** 把两个组都绑到同一个型号，**Then** 该字段只有一条绑定，不产生重复

### User Story 3 - 按厂商找设备、按组找字段（Priority: P2）

有一批戴尔设备要统一升级固件，管理员要先找出它们。他在资产页按厂商筛选。
另一次，他想看看「网络参数」这个组里到底放了哪些字段，于是在字段页按组筛选。

**Why this priority**: 前两个故事把数据组织好之后，找不到就等于没有。

**Independent Test**: 筛选可以在绑定功能之外单独验证 —— 有厂商实体就能按厂商筛资产。

**Acceptance Scenarios**:

1. **Given** 资产列表，**When** 选择厂商「Dell」，
   **Then** 只列出型号属于 Dell 的设备，且该筛选进入地址栏
2. **Given** 字段页，**When** 选择组「网络参数」，**Then** 只列出属于该组的字段
3. **Given** 字段页，**When** 选择厂商「Dell」，**Then** 只列出绑定到 Dell 的字段
4. **Given** 资产页的筛选栏，**When** 查看有哪些筛选，**Then** 其中没有「组」这一项

### User Story 4 - 改错了厂商，知道代价再改（Priority: P3）

有人把 EDGE620 的厂商填成了 Dell，实际是联想。改回来之前，系统告诉他这会让
30 台设备上已经填写的 ServiceTag 变成只读历史。

**Why this priority**: 是安全网而不是新能力。但没有它，一次下拉框的修改会静悄悄地
把三十台设备的字段变成历史，改的人不一定意识到。

**Independent Test**: 需要厂商绑定已经可用；可独立于组与筛选验证。

**Acceptance Scenarios**:

1. **Given** 30 台 EDGE620 都填了来自 Dell 的 ServiceTag，**When** 把该型号的厂商改成联想并保存，
   **Then** 保存前弹出确认，说明会波及 30 台设备
2. **Given** 上述确认已被接受，**When** 查看其中一台设备，
   **Then** ServiceTag 的值出现在已归档字段里，只读可见，一个不丢
3. **Given** 上述确认，**When** 取消，**Then** 厂商没有改变

### Edge Cases

- 组内某个字段被删除后，组的成员关系随之消失，组本身仍在
- 把一个空组绑到目标：不产生任何绑定，也不算失败
- 删除一个还有型号在引用的厂商：拒绝，并说明有多少款型号引用它（与删除类别、状态同一条规则）
- 导入 CSV 的 vendor 列填了系统里没有的厂商名：预览阶段拒绝该行，导入不创建主数据
- 迁移后出现 `Dell` 与 `DELL` 两个厂商：这是刻意的，字段绑到其中一个时另一个旗下的型号拿不到 ——
  归并是事后的人工动作
- 一个字段绑到厂商 A 与型号 B（B 属于厂商 C）：合法，到达集是 A 旗下全部型号加上 B
- 一个字段绑到厂商 A 与 A 旗下的型号 B：合法但冗余，界面应当禁用 B 的勾选框而不是事后拒绝
- 唯一字段绑到厂商：其取值在该厂商旗下全部型号内不重复，而不是每个型号内各自不重复

## Requirements *(mandatory)*

### Functional Requirements

**字段组**

- **FR-001**: 系统 MUST 允许创建、重命名与删除字段组，组有名称，可为空组
- **FR-002**: 系统 MUST 允许一个字段同时属于多个组
- **FR-003**: 把组绑定到类别、型号或厂商时，系统 MUST 等价于把组内每个字段逐个绑定到该目标
- **FR-004**: 组内任一成员的绑定被拒绝时，系统 MUST 拒绝整个绑定动作，不写入任何绑定，
  并在拒绝信息中点名该字段与冲突所在
- **FR-005**: 删除组时系统 MUST 保留所有已展开的绑定，且必须在确认时说明这一点
- **FR-006**: 同一字段经由两个组绑到同一目标时，系统 MUST 只产生一条绑定

**厂商**

- **FR-007**: 系统 MUST 把厂商作为可增删改查的实体，型号引用它，且该引用可以为空
- **FR-008**: 系统 MUST 保持「同一厂商下型号名不重复」这一约束，且在型号没有厂商时同样有效
- **FR-009**: 迁移 MUST 把每个不同的存量厂商字符串变成一个厂商实体，不做任何归并或规范化
- **FR-010**: 系统 MUST 在厂商仍被型号引用时拒绝删除该厂商，并说明有多少款型号引用它

**绑定与继承**

- **FR-011**: 字段与字段组 MUST 能绑定到类别、型号或厂商三者之一
- **FR-012**: 系统 MUST 拒绝把同一个字段同时绑到类别与设备侧（型号或厂商）
- **FR-013**: 系统 MUST 允许同一个字段同时绑到型号与厂商，取并集
- **FR-014**: 型号的有效字段 MUST 包含它自己绑定的字段与它所属厂商绑定的字段
- **FR-015**: 界面 MUST 禁用「厂商已经提供了该字段」的型号勾选框，并说明原因，
  而不是接受点击之后再拒绝
- **FR-016**: 唯一字段在设备模式下的取值范围 MUST 是「直接绑定的型号 ∪ 所绑厂商旗下的全部型号」
- **FR-017**: display_key MUST 仍然只能从类别模式的字段中选择

**值的归宿**

- **FR-018**: 修改型号的厂商时，系统 MUST 在保存前告知这会让多少台设备的哪些字段变成只读历史
- **FR-019**: 修改型号的厂商后，不再适用的字段取值 MUST 作为已归档字段保留且只读可见

**接口与筛选**

- **FR-020**: 字段的接口表示 MUST 同时给出「绑在哪些厂商」与「到达哪些型号」，后者为展开后的集合
- **FR-021**: 字段的绑定模式取值 MUST 为 `category`、`device` 或 `unbound`
- **FR-022**: 字段页 MUST 支持按组与按厂商筛选
- **FR-023**: 资产页 MUST 支持按厂商筛选，且该筛选进入地址栏
- **FR-024**: 资产页 MUST NOT 提供按组筛选

**导入导出**

- **FR-025**: 导入时 vendor 列指向不存在的厂商，系统 MUST 在预览阶段拒绝该行且不创建厂商
- **FR-026**: 导出与导入模板的列 MUST 由类别的完整有效字段集决定，其中包含厂商绑定的字段

**权限**

- **FR-027**: 组与厂商的管理 MUST 沿用既有的 schema.manage 权限，不新增权限开关

### Key Entities

- **字段组**：一个名称，加上一组字段成员。多对多。它不出现在任何设备的有效字段集里 ——
  它只在「绑定」这个动作发生的那一刻存在
- **厂商**：一个名称。型号引用它（可空）。它可以被字段与字段组绑定，
  绑在它上面的字段流向它旗下的所有型号
- **型号**（既有，被改动）：厂商从自由文本变成对厂商实体的引用

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 给一个有五款型号的厂商加一个字段，从零到五款型号都有该字段，操作数从五次降为一次
- **SC-002**: 在已有厂商字段的前提下新建一款该厂商的型号，该型号的字段集正确，且新建过程中
  无需任何与字段相关的额外操作
- **SC-003**: 把一个含三个字段的组绑到一个型号，结果与逐个绑三次完全一致，可通过比对有效字段集验证
- **SC-004**: 组内含一个非法成员时，绑定后数据库中与该组相关的绑定行数为零
- **SC-005**: 迁移在含有大小写不一致厂商名的存量库上成功完成，且迁移前后型号总数与
  「厂商名 + 型号名」组合数完全一致
- **SC-006**: 修改型号厂商前的告知台数与实际变成只读历史的设备台数一致
- **SC-007**: 015 与更早各轮的既有行为全部保持：类别绑定、型号绑定、唯一性、
  导入导出、列解锁的既有测试全部通过

## Assumptions

- 厂商是扁平的，没有层级（没有「Dell 中国」属于「Dell」这种关系）
- 一款型号只属于一个厂商
- 组不嵌套（组里不能放组）
- 组本身不携带必填、排序等属性 —— 必填在字段身上（018），组只是成员清单
- 归并两个厂商的功能不在本轮范围内；迁移之后的重复厂商由人工逐个改型号的厂商来收拾
- 厂商没有「停用」，只有删除（有型号引用时拒绝）—— 与持有方、状态同一条规则
- 厂商的管理入口是型号页旁边的一个页签，实现为两条独立路由，
  以免两张列表在同一个地址上争抢搜索与翻页参数
