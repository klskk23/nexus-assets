# 调研：流体内容列

四个问题。两个把工作量缩小了，一个纠正了规格里的一个数字，一个决定了验收怎么写。

---

## 一、宽度声明有四处，但只有三处是内容列

```
routes/AppShell.tsx:186        max-w-[960px]   ← 内容列
routes/Import.tsx:184          max-w-[760px]   ← 内容列
features/transfers/TransferForm.tsx:193  max-w-[640px]   ← 内容列
features/common/ListToolbar.tsx:41       max-w-[640px]   ← 搜索框，是控件
```

**第四处必须留下。** 它和 `TransferForm` 是同一个数字 640，
一次 `grep -l "max-w-\[640px\]" | xargs sed` 就会把搜索框一起改掉，
而那不会有任何测试报错 —— 表现是搜索框在宽屏上拉成一整行。

FR-007 存在的理由就是这一处。**判据：它约束的是「一段内容有多宽」还是「一个控件有多宽」。**

## 二、规则可以写成一条 CSS 声明

主面板的固定开销是 **356px**：侧栏 236 + 外层 `p-3` 两侧 24 + 面板内边距 `pl-14`/`pr-10` 共 96。
所以内容列的包含块宽度 = 视口 − 356。

```
width: min(100%, max(960px, 76%))
```

三段各司其职，且**没有 `max-width`**：

| 片段 | 管什么 |
|---|---|
| `76%` | 比例。留白恒定占包含块的 24%（FR-002、FR-005） |
| `max(960px, …)` | 地板。窄窗口下与 018 逐像素一致（FR-004） |
| `min(100%, …)` | 兜底。包含块窄于 960 时贴合而不溢出，交给表格框自己横向滚动 |

逐档验算：

| 视口 | 包含块 | 内容列 | 留白 | 占比 |
|---|---|---|---|---|
| 1280 | 924 | **924**（100% 生效） | 0 | 0% |
| 1440 | 1084 | **960**（地板生效） | 124 | 11% |
| 1920 | 1564 | 1189 | 375 | **24%** |
| 2560 | 2204 | 1675 | 529 | **24%** |
| 3840 | 3484 | 2648 | 836 | **24%** |

**地板在视口 1619 以下一直生效**（76% × (v−356) ≥ 960 ⇔ v ≥ 1619）。

## 三、规格里「1548」这个数字是错的

规格的边界情况一节写「<1548px 窗口，地板生效」。那是按 `62vw` 的旧算法推的，
而第六条裁定把算法换成了「面板百分比」。**按 76% 算，门槛是 1619，不是 1548。**

不影响任何需求 —— FR-004 要的是「≤1440 与 018 逐像素一致」，1440 < 1619，成立。
但那个数字若留着，走查时会按它去找门槛而找不到。**规格已改。**

## 四、零测试断言宽度 —— 与 018 同一个结论，但这次要主动破例

`tests/` 里对 `960`、`760px`、`max-w-` 的命中：**0**。

018 的调研得出同样结论并据此决定「不写断言类名的测试」。那个判断在 018 是对的
（改的是四十处类名，写断言等于把类名抄一遍）。**这一轮不同**：

- 这一轮只改**一条规则**，断言的是**它的行为**（不同窗口下留白占比恒定），不是它的类名；
- 而 SC-005 明确要求「把宽度改回固定值时断言会红」。

jsdom 不做布局，`getBoundingClientRect()` 恒返回 0 —— **所以这条断言写不进 vitest**。
它只能在真实浏览器里量。这一轮的验收因此分成两半，两半都要留下可重跑的产物：

1. **DOM 测试**（vitest）：守「宽度规则只有一处声明」这个**静态事实** ——
   可以断言，因为它是代码结构不是布局。
2. **实测脚本**（Playwright）：守留白占比。**必须双向验证** ——
   把宽度改回 `max-w-[960px]` 时它要报错，否则它什么也没守住。

第 2 项的产物存进仓库（`.playwright-mcp/` 是 gitignore 的，所以脚本进 `specs/020-*/`）。
