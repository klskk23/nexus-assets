# 实施计划：流体内容列

**分支**：`020-fluid-content-column` ｜ **规格**：[spec.md](./spec.md) ｜ **决策**：130–134

## 概要

把内容列的 960px 固定上限换成一条按面板比例流动、无上限、带 960 地板的规则。
**贴左不对称保留**，字号行高圆角间距一律不动，服务端零改动。

调研（[research.md](./research.md)）把这一轮缩到了很小，也指出了一处真正的风险：

1. **整个规则是一条 CSS 声明** —— `width: min(100%, max(960px, 76%))`，
   三段分别管比例、地板、兜底，**没有 `max-width`**
2. **要改的内容列只有三处**，但同一个数字 `640px` 在第四处是搜索框，**必须留下**
3. **jsdom 不做布局**，所以留白占比这条核心验收**写不进 vitest** —— 必须在真实浏览器里量

## Complexity Tracking（章程偏离登记）

| 违反项 | 必需性理由 | 被拒绝的更简方案 |
|---|---|---|
| **原则二**：「任何触及 UI 的变更必须新增或更新至少一条 DOM 测试」。本轮新增的是**源码不变量测试**（`tests/contentColumn.test.ts`），不是 DOM 测试 | **这一轮的改动在 jsdom 里没有任何可观察行为。** jsdom 不做布局，`getBoundingClientRect()` 恒返回 0，任何关于宽度或比例的断言都会无视 CSS 恒真。真正的验收是 `measure.mjs`，它在真实浏览器里量，并且**双向验证过**（改回固定值报错、改回来通过） | **写一条断言类名的 DOM 测试**：它看起来满足了原则二，实际什么也不守 —— 018 的概览页测试正是这样，断言 `grid-cols-[...]`，结果在版面正确时报红、在版面可能错时通过。**用一条假测试满足条文，比登记偏离更坏** |

登记的这条同样双向验证过：把 `max-w-4xl` 当内容列写进导入页，测试立刻报出文件名。

## 阶段

### 第 0 阶段：调研 ✅

### 第 1 阶段：设计 ✅

- `measure.mjs` —— 可重跑的实测脚本

### 第 2 阶段：实施顺序

```
先立验收（实测脚本 + 静态断言），并在**改代码之前**跑一遍拿到「改造前」的数字
   ↓
换 AppShell 的规则 ── 删两处逐页上限
   ↓
实测三档窗口 → 占比极差 ≤5 个百分点；窄屏三档 → 与 018 逐像素一致
   ↓
双向验证：把规则改回 max-w-[960px]，脚本必须报错；改回来
   ↓
文档同步（web-tables.md 数字表、018 quickstart 第 1 步、design README 第三处不一致）
```

**验收必须先立。** 改完再写脚本，脚本会不自觉地按现状写成永远为真 ——
018 的概览页测试就是这么来的（断言 `grid-cols-[...]`，版面正确时反而报红）。

## 风险

| 风险 | 应对 |
|---|---|
| **`640px` 一个数字两种含义，改错搜索框且无测试报错** | FR-007 单列一条；实施时按文件逐处改，**不用 `sed` 批量替换**；收口 grep 复核 `ListToolbar` 的 640 仍在 |
| **实测脚本写成永远为真** | SC-005 要求双向验证，任务清单里把「改回固定值确认变红」列成独立一步 |
| **窄屏出现回归而没人发现** | 地板在 1619 以下始终生效，理论上 ≤1440 不可能变。但仍逐档实测 1280/1366/1440，因为「理论上不会」正是回归最常藏身的地方 |
| **文档留下与代码相反的数字** | FR-011、FR-012、SC-006 三条把它写成验收标准；收口 grep 全仓 `960` 复核 |
| **超宽屏上表格列被拉开被误当成 bug** | 已在规格里单列「已接受的代价」一节，并写明「都不修」及其理由 |
| **半成品被误发布** | 017+018 的 43 个提交仍未推，020 在其上继续；中途不打 tag、不合 main |
