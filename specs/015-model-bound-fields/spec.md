# 015 · 字段可以绑定型号

**分支**：`015-model-bound-fields` ｜ **状态**：设计已定，待实现 ｜ **创建**：2026-09-04

## 缘起

戴尔的设备有 ServiceTag，联想的没有。这是一个**每台设备各自不同**的编号（跟序列号一个
性质，不是同型号共享的规格值），但它**只对某些型号有意义**。

今天的字段只能绑类别，于是这种字段无处可放，两条路都别扭：

- **绑到整个「笔记本电脑」类别**：联想、惠普的设备录入表单上也长出一个 ServiceTag 输入框，
  永远空着；导入模板、导出 CSV 也多一列，非戴尔行永远空。系统层面无法表达
  「这个字段只属于戴尔」。
- **按厂商拆子类别**（笔记本电脑/戴尔、笔记本电脑/联想……）：能用现有机制实现，零 schema
  改动，但类别树从此同时承担「设备种类」和「厂商」两条正交的分类轴。厂商一多、设备种类
  一多，子类别数量乘起来，而且以后调整分类会牵动型号归属。

第三条路是让字段能直接绑到型号上。本轮做这条。

**先划清一件事**：这**不是**「型号级共享值」。ServiceTag 的值仍然属于每一台设备，存在
`assets.attrs` 里，跟今天任何字段一样。变的只是**「这个字段该不该出现在这台资产上」这个
判断的依据**——从「看类别」扩展成「也可以看型号」。型号上原有的 `attr_defaults` 是另一回事
（选型号时一次性复制的默认值），本轮不动它。

## 决策

### 决策 96：字段绑定新增「绑型号」这个目标，且与「绑类别」互斥

字段绑定多一种目标：型号。一个字段的绑定**只能是一种模式**——要么全是类别绑定（今天的
机制，原样不动），要么全是型号绑定，**不能混**。字段当前绑定为空时，下一次绑定决定它是
哪一种；已经有一种绑定存在时，尝试绑另一种直接拒绝。

互斥不是洁癖，混绑会同时撞上三件事：

1. **冗余**：字段绑了类别 C，C 的子树里本来就包含型号 M，再把同一字段绑到 M 上没有任何
   新效果——M 下的资产已经被类别绑定覆盖了。这条绑定纯粹是摆设。
2. **必填冲突**：绑定各自带自己的必填开关（决策 70）。类别绑定说必填=否、落在该类别里的
   某个型号绑定说必填=是，同一台资产两条绑定都命中，必填听谁的没有天然答案。
3. **唯一性范围说不圆**：类别绑定的唯一性范围是类别子树，型号绑定的是绑到的型号集合
   （决策 99）。一个字段同时占两种绑定，范围变成「子树 ∪ 型号集合」，
   `asset_unique_values.scope_id` 该存什么就没有干净的答案了。

互斥之后三个问题全部不存在。**判断规则一句话**：一台资产该显示哪些字段 =
（类别模式字段中，绑定命中它的类别链的）+（型号模式字段中，绑定命中它 `model_id` 的）。
两组来自不同字段，互不重叠。

### 决策 97：绑定粒度是具体型号，不引入「厂商」实体

型号模式下直接勾选一个或多个具体型号，多对多，复用今天字段绑类别的同款交互与机制。

**不做**「按厂商自动包含」。`ProductModel.Vendor` 今天只是型号表上的一个自由文本字段
（参与重名判定），不是可引用的实体——两个型号只要厂商名拼错一个字就是两个厂商。要做
「以后新增的戴尔型号自动带上 ServiceTag」，得先把厂商升格成一等实体，那是另一轮的事。

**代价说清楚**：以后新增一个戴尔型号，需要有人手动把 ServiceTag 勾上去。漏勾不会报错，
只是那台新型号的设备录入时不会出现这个字段。接受这个代价。

### 决策 98：资产换型号后，旧型号绑定字段的值进 `archived_attrs`

一台资产原本是戴尔某型号、ServiceTag 已经填了值，后来它的型号被改成联想某型号（录错了在
更正，或者设备本身被替换），而新型号没有绑 ServiceTag——这个值进 `archived_attrs`，
只读可查，不再是活跃字段。

复用的是解绑字段时**已有的**机制（决策 72 之后的既定行为），不发明新东西。不同的是**触发源
第一次变成「改了资产自己的型号」**，而不是「管理员显式解绑了字段」。

**不选**「拒绝换型号」：换型号是一个日常动作，为了一个字段的值把它变成可能失败的操作，
代价大于收益。**不选**「什么都不做，值留在 attrs 里无人管」：那会形成一个没有人显式决定过
的孤儿状态，本质跟归档一样，只是没标记、界面上也不会被特殊对待。

### 决策 99：唯一性范围按绑定模式各自计算

- **类别模式**的字段：范围不变，仍是绑定所在类别的子树（决策 71）。
- **型号模式**的字段：范围是**这个字段绑到的所有型号合起来**。

也就是说 ServiceTag 同时绑了 Latitude 5420 和 OptiPlex 7090，那这两个型号下的设备之间不能有
重复的 ServiceTag。这是「唯一性按字段的绑定footprint 计算」这条既有规则的自然延伸，
只是 footprint 从类别子树换成了型号集合。

**不选**「每个型号各自一个命名空间」：戴尔的 ServiceTag 实际上是全局唯一的标识符，
两个不同型号各有一台设备同为 `ABC1234` 却不报错，是一个真实的数据完整性漏洞。

### 决策 100：`display_key` 只能从类别模式的字段里选

类别的 `display_key`（决定人可读编号的那个字段）**不接受型号模式字段**作为候选。

理由：`display_key` 要为这个类别里的**每一台**资产生成编号。型号模式字段只覆盖部分型号，
没被覆盖的资产会**永远**退回 UUID 前 8 位——不是「还没填」，是「压根不会有」。同一个类别里
一半设备有正经编号、另一半永远是 UUID，取决于它碰巧是什么型号，这不是编号该有的样子。

### 决策 101：改动集中在 `EffectiveFields`，五个消费方自动跟上

`schema.EffectiveFields(categoryID)` 今天是**唯一**的「这个类别有哪些字段」的答案来源，
被五处消费：

| 消费方 | 文件 |
|---|---|
| 录入表单 / 类别 schema 接口 | `internal/httpapi/handlers_metadata.go` |
| 资产写入校验 | `internal/asset/query.go` |
| 导入模板与逐行解析 | `internal/importer/template.go`、`resolve.go`、`rows.go` |
| 导出 CSV | `internal/importer/export.go` |
| 资产页显示列下拉 | 经 `GET /categories/:id/schema` |

型号模式字段要并进这一个函数的结果里（并进的是：该类别链上注册的型号所绑定的字段），
上述五处**不需要各自改**。`GET /api/rows`（zenith 数据源）同理。

字段条目要多带一个「这个字段绑到哪些型号」的信息，前端才知道某一列该不该解锁（决策 103）；
类别模式字段这一项为空。

### 决策 102：导出列由类别的完整 schema 决定，导入错配行在预览阶段拒绝

**导出**：型号模式字段**固定出现**在该类别的导出列里，哪怕本次导出的结果里一台对应型号的
设备都没有。**列是 schema 的事，行才是查询的事**——同一个类别导出两次列数必须一致，否则
下游写脚本按固定表头解析的人会被这个不稳定性坡到。不匹配的行该列留空，这一点导出代码
**今天就已经支持**（取值时 `v, ok := a.Attrs[key]`，取不到写空串），不需要新逻辑。

**同类别不同型号不分包**。今天跨类别导出分包的理由是「两个类别的字段词汇不同，同一个表头
下会是两种含义」；同一个类别内的不同型号，字段词汇还是同一个类别的，只是表宽一点，
不存在「同一列两种含义」，没理由再拆。

**导入**：某一行 `model` 列选的型号没有绑某个型号模式字段，但那一列却填了值——**预览阶段
拒绝这一行**，说明该字段对所选型号不适用，不写入任何数据。不静默丢值（填表人可能是真想写
这个值，只是型号那列选错了，静默丢比报错更危险），也不静默写入（那会造出一个从诞生起就不
对应任何绑定的孤儿值）。

### 决策 103：资产列表加型号筛选，型号字段列按筛选状态解锁

**型号筛选**与类别/状态/负责人/持有方并列，**只进地址栏**（`useSearchParams`），
不进 localStorage——与今天所有筛选值的做法一致（筛选值本身从不做跨会话持久化，
只有「选了哪些列」进 localStorage）。

**显示列下拉里，型号模式字段的勾选框只在当前选中的型号命中该字段绑定时可选**，
其余时候禁用（不是隐藏，遵循既有约定）。解锁精度**按绑定算**：选了戴尔某型号，只解锁绑在
它身上的字段，联想型号的字段仍然锁着——否则会让人勾上一个对当前筛选永远空白的列。

型号筛选清空或换成不匹配的型号后，已勾选的型号字段列**靠现有的「与当前 `available` 求交」
机制自动收回**，不新增存储维度。代价是回到同一个型号要重新勾一次，接受。

### 决策 104：资产弹窗顶部加一张只读属性卡

资产详情弹窗最顶部（`DialogHeader` 之下、流转卡**之上**）加一张只读卡，展示这台设备
**类别模式与型号模式字段的当前值**。

放在流转之上是对 014 决策 89 之后那轮排序的**修正而非推翻**：那轮解决的是「流转被折叠面板
挡住」，本轮说的是「设备是什么（身份）排在要对它做什么（动作）之前」。先认清设备再决定动作，
扫码场景下尤其成立。

**范围**：只有类别/型号绑定的动态字段。**不含**六个内建字段——状态（标题栏徽章）、
当前持有方与负责人（流转卡内的只读块）、备注（资产卡内的文本框）都已经在弹窗别处有自己的
位置，不重复摆。

**与下方「编辑设备属性」折叠面板的关系**：折叠面板原样不动，继续负责编辑。两边内容**故意
重叠**——看和改是两件事，想快速看就看顶部的卡，想改就展开下面的面板。

## User Scenarios & Testing

### User Story 1 - 给特定型号配一个专属字段 (Priority: P1)

管理员在字段库里新建 ServiceTag，绑定的时候不选类别，改选「戴尔 Latitude 5420」和
「戴尔 OptiPlex 7090」两个型号。此后录入这两个型号的设备时表单上出现 ServiceTag，
录入联想设备时不出现。

**Why this priority**：这是本轮存在的理由，其余故事都建立在它之上。

**Independent Test**：只实现这一条就已经可用——建一个型号模式字段，用两个不同型号的设备
各录一台，验证字段只在其中一台的表单上出现。

**Acceptance Scenarios**：

1. **Given** 字段库里有一个未绑定的字段，**When** 管理员为它选择型号模式并勾选两个戴尔型号，
   **Then** 绑定成功，字段列表显示它绑到了这两个型号。
2. **Given** 某字段已经绑了一个类别，**When** 管理员尝试再给它加一个型号绑定，
   **Then** 系统拒绝，并说明一个字段只能是纯类别或纯型号绑定。
3. **Given** ServiceTag 绑在两个戴尔型号上，**When** 录入一台联想型号的设备，
   **Then** 表单上没有 ServiceTag 这一项。
4. **Given** ServiceTag 已在两个戴尔型号上标为唯一，**When** 在这两个型号下各录入一台设备
   且 ServiceTag 相同，**Then** 第二台被拒绝，提示编号重复。

### User Story 2 - 在列表里按型号筛选并看到专属字段列 (Priority: P2)

仓管想核对一批戴尔设备的 ServiceTag，在资产列表里先按类别筛到笔记本电脑，再按型号筛到
Latitude 5420，然后在显示列里勾上 ServiceTag，一屏看完。

**Why this priority**：字段能录进去之后，「看得到、对得上」是紧接着的需求。

**Independent Test**：在已有型号模式字段的前提下，用列表页的筛选与显示列完成一次核对。

**Acceptance Scenarios**：

1. **Given** 列表已按某类别筛选，**When** 打开显示列下拉，**Then** 型号模式字段的勾选框
   是禁用状态，并说明需要先选定型号。
2. **Given** 已选中 Latitude 5420 这个型号，**When** 打开显示列下拉，
   **Then** 绑在该型号上的字段可以勾选，绑在其他型号上的仍然禁用。
3. **Given** 已勾上 ServiceTag 这一列，**When** 把型号筛选清空，
   **Then** 该列自动从表格上收回，不留下一个有表头没内容的空列。

### User Story 3 - 打开一台设备先看清它是什么 (Priority: P2)

任何人点开一台设备，弹窗最上方直接看到它全部字段的当前值，不需要展开任何折叠面板。

**Why this priority**：与 P2 并列——它不依赖型号绑定就有价值（类别字段一样受益），
但也不是本轮的核心目的。

**Independent Test**：点开任意一台已有设备，验证顶部卡片列出了它的字段值。

**Acceptance Scenarios**：

1. **Given** 一台有若干字段值的设备，**When** 打开它的弹窗，
   **Then** 最顶部展示这些字段的名称与当前值，无需展开折叠面板。
2. **Given** 一台戴尔设备，**When** 打开它的弹窗，
   **Then** 顶部卡片里同时包含类别绑定字段和 ServiceTag 这类型号绑定字段。
3. **Given** 顶部卡片已展示字段值，**When** 查看弹窗其余部分，
   **Then** 状态、当前持有方、负责人、备注仍在它们原来的位置，没有被搬进这张卡。

### User Story 4 - 导入导出带上型号专属字段 (Priority: P3)

批量导入一批戴尔设备时，模板里有 ServiceTag 这一列；导出这个类别时，ServiceTag 也在列里。

**Why this priority**：批量路径的一致性，晚于交互路径。

**Independent Test**：下载某类别的导入模板，确认包含型号绑定字段列；导出同一类别，确认列一致。

**Acceptance Scenarios**：

1. **Given** 某类别下有型号绑定了 ServiceTag，**When** 下载该类别的导入模板，
   **Then** 模板里有 ServiceTag 列。
2. **Given** 导入文件某行 `model` 列填的是联想型号、ServiceTag 列却填了值，
   **When** 上传预览，**Then** 该行被标为错误，说明该字段对所选型号不适用，且不写入数据。
3. **Given** 导出某类别且本次结果里没有任何戴尔设备，**When** 打开导出的 CSV，
   **Then** ServiceTag 列仍然存在，只是每一行为空。
4. **Given** 勾选了同一类别下的戴尔和联想设备，**When** 导出，
   **Then** 得到一个 CSV 而不是按型号分开的多个文件。

### Edge Cases

- **资产没有型号**（`model_id` 为空）：型号模式字段一个都不出现，与「型号不匹配」同样处理。
- **型号被移出某个类别**（`CategoryIDs` 收缩）而该类别下仍有该型号的资产：这些资产的
  型号绑定字段仍按 `model_id` 命中，不受类别归属变化影响——绑定看的是型号，不是类别。
- **字段的型号绑定被全部解除**：走既有的解绑路径，存量值进 `archived_attrs`。
- **同一个键在两种模式下撞车**：新绑字段时要检查它即将覆盖到的资产范围内有无同键字段
  （类别模式查子树，型号模式查那几个型号各自所在的类别链），撞了就拒绝——`attrs` 是扁平
  map，两个不同字段定义抢同一个 key 在数据层面就是错的。
- **型号模式字段被勾必填**：dry-run 统计的台数从「类别子树」缩到「这个型号在其类别子树下的
  存量资产」，其余规则不变（存量不回溯校验，下次编辑才补）。

## Requirements

### Functional Requirements

- **FR-001**：字段绑定必须支持「型号」这一种目标，与既有的「类别」目标并列。
- **FR-002**：系统必须拒绝为同一个字段同时建立类别绑定与型号绑定；两种模式互斥。
- **FR-003**：一个字段在型号模式下必须能同时绑定多个型号（多对多）。
- **FR-004**：一台资产的有效字段集必须等于「命中其类别链的类别模式字段」与
  「命中其 `model_id` 的型号模式字段」之并集。
- **FR-005**：资产的 `model_id` 变更后，若原有值所属字段不再适用于新型号，该值必须转入
  `archived_attrs`，且不得阻断型号变更本身。
- **FR-006**：型号模式字段的唯一性范围必须是该字段绑定的全部型号之并集；类别模式字段的
  唯一性范围保持为绑定所在类别的子树。
- **FR-007**：类别的 `display_key` 候选必须排除全部型号模式字段。
- **FR-008**：型号模式字段必须支持「必填」，其影响面统计范围为该型号在相关类别子树下的
  存量资产。
- **FR-009**：管理型号绑定所需的权限必须沿用 `schema.manage`，不新增权限开关。
- **FR-010**：类别的有效字段集接口必须同时返回类别模式与型号模式字段，且每个字段条目要
  携带其绑定的型号标识，便于调用方判断适用范围。
- **FR-011**：某类别的导出列与导入模板列必须由该类别的完整有效字段集决定，与本次查询结果
  中出现了哪些型号无关。
- **FR-012**：同一类别内不同型号的资产导出时不得按型号分包。
- **FR-013**：导入预览必须拒绝「所选型号未绑定该字段、但该列填有值」的行，并说明原因。
- **FR-014**：资产列表必须提供型号筛选，其状态只反映在地址栏，不做跨会话持久化。
- **FR-015**：资产列表的显示列选择器中，型号模式字段仅在当前型号筛选命中其绑定时可选，
  其余情况禁用而非隐藏。
- **FR-016**：型号筛选清空或变更后，已选中但不再适用的列必须自动从表格中移除。
- **FR-017**：资产详情弹窗必须在最顶部（流转区之上）展示该设备全部动态字段的当前值，只读。
- **FR-018**：该只读卡片不得包含六个内建字段（类别、状态、持有方、负责人、备注、编号）。
- **FR-019**：既有的「编辑设备属性」折叠面板必须保持原有能力不变。

### Key Entities

- **字段定义（FieldDefinition）**：键、显示名、类型、是否唯一等。本轮不改其自身结构，
  改的是它的绑定方式。
- **字段绑定（Binding）**：把一个字段挂到某个目标上，并携带该次绑定的「必填」与排序。
  本轮从「只能挂类别」扩展为「挂类别或挂型号，二选一」。
- **型号（ProductModel）**：已有实体，含所属类别列表、名称、厂商、默认值等。
  本轮新增「哪些字段绑在我身上」这层关系，不改其自身字段。
- **资产（Asset）**：字段值仍存在其 `attrs` 中；不再适用的历史值存在 `archived_attrs` 中。
  本轮不改其结构。

## Success Criteria

### Measurable Outcomes

- **SC-001**：为某型号配置一个专属字段，从新建字段到该型号的录入表单上出现它，
  管理员在 2 分钟内可以独立完成，无需新建任何类别。
- **SC-002**：非该型号的设备，其录入表单、详情弹窗上不出现该字段——出现率为 0。
- **SC-003**：同一个类别连续导出两次，只要类别配置未变，两次的列集完全一致，
  与筛选条件无关。
- **SC-004**：导入一份含错配值的文件，全部错配行在预览阶段被列出，写入数据量为 0。
- **SC-005**：打开任意一台设备，无需任何额外点击即可看到它全部动态字段的当前值。
- **SC-006**：型号筛选清空后，表格中不会残留任何「有表头无内容」的列——残留数为 0。

## Assumptions

- **一个字段的绑定模式在其生命周期内可以改变**，前提是先把现有绑定全部解除（绑定数归零后
  下一次绑定重新决定模式）。这与「字段类型创建后不可改」是不同的轴，不冲突。
- **型号与资产类别的相容性由既有机制保证**：型号选择器按资产的类别过滤可选型号，
  本轮不额外校验 `asset.category_id` 是否在 `model.CategoryIDs` 内。
- **`attr_defaults` 不在本轮范围内**。型号上的默认值仍是选型号时的一次性复制，
  与型号绑定字段是两件独立的事。
- **不引入「厂商」实体**（决策 97），因此不存在「新型号自动继承同厂商字段绑定」的行为。
- **`GET /api/rows`（zenith 数据源）的列会随之变宽**，不匹配型号的行该列为空。
  这是加列不是改列，对面按列名取值，不会因此报错。
- **不改动 `archived_attrs` 的既有语义**：它一直是「不再属于当前有效字段集的历史值」，
  本轮只是多了一个进入它的触发路径。

## 实现顺序

三个提交，按依赖顺序：

1. **服务端：绑定模式与有效字段集**——绑定表新增型号目标、互斥校验、`EffectiveFields`
   并入型号模式字段、唯一性范围、`display_key` 候选过滤、必填统计范围、换型号归档；
   合约与文档同步。
2. **服务端：批量路径**——导入模板列、导入预览的错配拒绝、导出列集；`GET /api/rows` 随之。
3. **前端**——字段编辑器的绑定模式切换与型号选择、资产列表的型号筛选与显示列解锁、
   资产弹窗顶部只读属性卡。
