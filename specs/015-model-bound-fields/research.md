# Phase 0 · 调研：实现层面的未决项

spec 的决策 96–104 已经定死了**行为**。本文件只解决实现层面的几个「怎么落地」，
每条给出决定、理由与被拒方案。

## R1：型号绑定存哪里

**决定**：新增 `model_fields(model_id, field_id, required, sort)`，主键
`(model_id, field_id)`，结构与既有 `category_fields` 一一对应。

**理由**：绑定的语义（挂到一个目标上、带自己的必填与排序）在两种模式下完全一致，
表结构对齐能让读写代码保持同形，也让「一个字段的绑定只能是一种模式」这条互斥校验
退化成一句「另一张表里有没有这个 field_id」。

**被拒**：
- **在 `category_fields` 上加一个可空的 `model_id` 列**，用「哪一列非空」区分模式。
  拒绝原因：主键要跟着变成三元组且含可空列，SQLite 的唯一性语义会变得难解释；
  而且每一条既有查询都要多带一个 `model_id IS NULL` 条件，改动面反而更大。
- **一张通用 `field_bindings(target_kind, target_id, ...)` 表**（把类别绑定也迁进去）。
  拒绝原因：要迁移既有数据、要重写 `BindingsByCategory` 与 `Resolve` 这两个核心函数，
  收益只是表少一张。决策 96 已经规定两种模式互斥、不会共存于一个字段，
  合表带来的抽象没有使用场景。

## R2：型号模式字段的唯一性 `scope_id` 存什么

**决定**：`asset_unique_values.scope_id` 存 `f:<field_id>`（带 `f:` 前缀）。
类别模式不变，仍存类别 id。

**理由**：决策 99 规定型号模式的唯一性范围是「这个字段绑到的所有型号合起来」——
这恰好就是「这个字段自己的绑定 footprint」，而一个字段只有一个 footprint，
所以字段 id 就是这个范围的天然标识，不需要新表、不需要改索引
（既有唯一索引 `(scope_id, field_key, value) WHERE archived_at IS NULL` 直接适用）。
加 `f:` 前缀是为了让人在排查数据时一眼看出这一行的范围是「一个字段的型号集合」
而不是「一个类别子树」——两者都是 UUID，不加前缀只能靠猜。

**被拒**：
- **裸存 `field_id` 不加前缀**。拒绝原因：可读性。UUID 不会撞，但排查的人要多查一次表
  才知道这个 id 是类别还是字段。
- **新建一张「绑定组」表，scope_id 指向它**。拒绝原因：这张表会与
  「字段的型号绑定集合」一一对应，是纯粹的冗余中间层。
- **存型号 id**。拒绝原因：那会变成「每个型号各自一个命名空间」，
  正是决策 99 明确拒绝的方案（两个戴尔型号各有一台 `ABC1234` 却不报错）。

## R3：有效字段集怎么把型号模式字段并进来

**决定**：`EffectiveFields(categoryID)` 的返回值 = 既有的类别链解析结果
∪ 「注册在这条类别链上的型号所绑定的字段」。后半部分新起一个函数
`resolveModelFields`，一次性加载 `model_fields` 与 `product_model_categories`
（各数百行），在内存里取交集。

**理由**：与既有 `BindingsByCategory` 完全同一个模式（全量加载 + 内存解析），
不引入 N+1；也把新增复杂度关在一个新函数里，不把 `EffectiveFields` 推过圈复杂度上限。

**关键细节**：字段条目要带上 `ModelIDs`（该字段绑到的型号 id 列表，类别模式为空），
前端才能判断某一列该不该解锁（决策 103）。这是 `BoundField` 结构的一个加法，
不影响既有消费方——它们只读自己关心的字段。

**被拒**：
- **给 `EffectiveFields` 加一个 `modelID` 参数，只返回该型号适用的字段**。
  拒绝原因：五个消费方里有三个（导出、导入模板、显示列下拉）要的是
  「这个类别的完整列集」而不是「某一台设备的字段集」（决策 102、103），
  加参数会让它们各自传一个假值，或者需要两个函数。
  真正需要「某台设备的字段集」的地方（录入表单校验）在拿到全集后按
  `model_id` 过滤一次即可，过滤逻辑一行。

## R4：换型号时的归档在哪一层做

**决定**：在 `internal/asset` 的保存路径里做——已有 `model_id` 变更时，
比较新旧型号各自的有效字段集，把不再适用且有值的键移入 `archived_attrs`。

**理由**：`archived_attrs` 的写入本来就在这一层（解绑字段导致的归档走的是同一条路），
放在别处会出现两个地方写同一个字段。

**被拒**：
- **在 `internal/schema` 的解绑路径里做**。拒绝原因：换型号不是 schema 变更，
  是资产自身的一次写入；把它塞进 schema 层会让「资产保存」依赖「schema 写路径」。
- **触发器**。拒绝原因：本项目没有任何数据库触发器，隐式写入与
  「保存管线是唯一事实来源」的设计基线冲突。

## R5：导入的错配行怎么判定

**决定**：在既有的逐行解析（`internal/importer/resolve.go`）里，
拿到该行的 `model` 列解析出的型号后，对每一个有值的字段列检查
「这个字段是不是型号模式、如果是、这个型号在不在它的绑定里」，不在就把这一行标成错误。

**理由**：预览逐行报错的机制已经存在（决策 102 要求预览阶段拒绝），
这里只是多一条判定规则，落在已有的逐行循环里。

**被拒**：
- **在提交阶段才校验**。拒绝原因：违反决策 102 明确要求的「预览阶段拒绝」，
  也违反既有的「预览用与手工录入完全相同的规则逐行校验」这条承诺。
