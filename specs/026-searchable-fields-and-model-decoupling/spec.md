# 规格：可搜索字段、型号与类别解耦、下拉全面可搜

**分支**：`026-searchable-fields-and-model-decoupling` ｜ **决策**：175–195
**推翻**：015 决策 103 对「没有类别就没有列」的适用、016 关于型号归属类别的形态
**修复**：键冲突守卫少问两张表（既有缺陷）、023 决策 149 未落实到全站

## 概要

三件事，一条硬依赖把其中两件绑在一起。

### 一、搜索只搜三样，而人以为它搜全部

资产搜索今天只覆盖三处：`asset_unique_values` 里的值、型号名、资产 id 前缀。
**普通属性存在 `assets.attrs` 这个 JSON 里，搜索从未碰过它。**

代码把这个假设写得很明白：「a scanner finds a device by its asset tag, its MAC or
its vendor serial」—— **它认定「值得搜的 = 唯一的」**。
建一个「service tag」字段却不想让它唯一，就落进了这个假设的缝里：字段在、值在、
搜不到，而界面上没有任何东西解释为什么。

### 二、型号归属类别，把两件不相干的事绑在了一起

`product_model_categories` 今天决定三件事：录入表单提供哪些型号、
**类别的有效字段集包含哪些型号绑定的字段**、以及资产页的型号筛选是否出现。

第二件是真耦合：**把一个型号关联到某个类别，会改变那个类别的字段集。**

而它还藏着一个更难发现的后果 —— `EffectiveFields` 只收集「关联到该类别链」的型号绑定，
`ForModel` 补不回来，所以**一台设备的型号如果没关联到它的类别，那个型号的字段会静默消失**。
今天界面拦住了这条路（型号下拉按类别过滤），但那正是把两件事绑死的那道锁。

**这条依赖必须写在最前面：录入限制与词汇表包含必须同轮断开。**
只断前者，型号下拉给出全集，人选了个没关联的型号，字段就没了 —— 一个由「解耦」制造出来的 bug。

### 三、显示列扎根在类别上

资产页的显示列来自 `/categories/:id/schema`，而那个查询 `enabled: categoryId !== ""` ——
**没选类别时它根本不跑**，显示列菜单是空的。存储也按类别键。
所以「我只想按厂商筛一批设备，顺便看看它们的固件版本」这件事今天做不到。

### 附带：一条已经存在的洞，和一条没落实的规则

**键冲突守卫只问了三张绑定表里的一张。** `Bind` 只查 `category_fields`，
`BindModel` 只查绑定模式冲突，而 `EffectiveFields` 是三张表并集。
于是今天就能造出：类别绑 `sn`（文本）+ 该类别下某型号绑另一个 `sn`（数字），
**一台设备的 `attrs` 里 `sn` 这一个槽有两个定义**。守卫自己的注释说这正是它要防的。
与 `docs/rules/schema.md` 记着的 `boundPaths` 那个坑是同一形状。
**解耦不能修好它** —— 合并只是从「每类别一次」挪到「每设备一次」。

**023 决策 149 只落实到了资产页的筛选栏。** 它自己新建的流转审计页上，
「操作人」是无界候选却用了普通 `Select` —— 规则写进文档的当轮就漏了。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 想搜什么就能搜到什么（Priority: P1）

管理员建一个「service tag」字段、不勾唯一、勾上「可搜索」，录入几台设备，
在资产页搜 service tag 的一段，能搜到。已有的字段不需要任何人去勾就能搜。

**为什么是 P1**：这是本轮的报障。今天这件事**无解**，且界面不解释为什么。

**验收场景**

1. **Given** 一个勾了「可搜索」但没勾「唯一」的字段，**When** 搜它的值的一部分，**Then** 命中该设备
2. **Given** 升级前已存在的字段，**When** 升级后搜它的值，**Then** 命中 —— **无需任何人去勾**
3. **Given** 一个没勾「可搜索」的字段，**When** 搜它的值，**Then** 不命中
4. **Given** 一个已有很多设备的字段，**When** 打开它的「可搜索」，**Then** 旧设备**立刻**可搜，不需要再保存一遍
5. **Given** 打开过又关掉「可搜索」，**When** 搜它的值，**Then** 不再命中，且索引里不留残值
6. **Given** 一个标了「唯一」的字段，**When** 查看它的「可搜索」开关，**Then** 勾上且禁用，并说明为什么
7. **Given** 两台设备的可搜字段有相同的值，**When** 搜那个值，**Then** 列出两台，**MUST NOT 直接跳进其中一台**
8. **Given** 搜一个唯一字段的完整值，**When** 只命中一台，**Then** 仍然直接跳进那台（既有行为不变）

### User Story 2 - 型号不再从属于类别（Priority: P1）

录入设备时，型号下拉列出全部型号（关联过当前类别的排在前面）。
一台设备的字段 = 它的类别链 + 它自己的型号 + 那个型号的厂商，
**与「这个型号有没有关联到这个类别」无关**。

**为什么是 P1**：它与 US3 是同一件事的两半，且单独做任何一半都会制造缺陷。

**验收场景**

1. **Given** 一个没有关联到类别 X 的型号，**When** 在类别 X 下录入设备并选它，**Then** 该型号绑定的字段**出现在表单上**
2. **Given** 同上的设备已保存，**When** 读取它，**Then** 那些字段的值仍在，且参与校验
3. **Given** 录入表单的型号下拉，**When** 展开，**Then** 列出全部型号，关联过当前类别的**排在前面**
4. **Given** 类别 X 的有效字段集，**When** 查看，**Then** **不再**包含仅因某型号关联到 X 而来的字段
5. **Given** 删除一个类别，**When** 确认框出现，**Then** 仍然列出会被脱开关联的型号（该关联仍在，只是不再有强制力）

### User Story 3 - 一个键只能有一个定义（Priority: P1）

把两个不同的字段用同一个键分别绑到类别与该类别可达的型号上，会被拒绝。

**为什么是 P1**：这是唯一一处**会写坏数据**的地方 —— 一台设备的一个属性槽两个定义，
之后所有关于它的校验、计算、唯一性都在答不同的问题。

**验收场景**

1. **Given** 字段 A 键为 `sn` 已绑到类别 C，**When** 把键同为 `sn` 的字段 B 绑到任一型号，**Then** 拒绝并指出与什么冲突
2. **Given** 字段 A 键为 `sn` 已绑到某型号，**When** 把键同为 `sn` 的字段 B 绑到类别 C，**Then** 同样拒绝
3. **Given** 字段 A 已绑到厂商 V，**When** 把同键的字段 B 绑到 V 旗下的型号，**Then** 拒绝
4. **Given** 升级前数据里已经存在这样的冲突，**When** 升级，**Then** **说出来**（迁移或校验命令报告），MUST NOT 静默通过

### User Story 4 - 不选类别也能选列、也能筛型号（Priority: P2）

只按厂商筛一批设备，显示列菜单里能勾出那些设备有的字段；型号筛选不再需要先选类别；
选了厂商之后型号候选只剩它旗下的。

**验收场景**

1. **Given** 没有选择类别，**When** 打开显示列菜单，**Then** 列出全库字段（只绑某型号的仍需先筛到它，理由不变）
2. **Given** 没有选择类别，**When** 查看筛选栏，**Then** 型号筛选**存在**
3. **Given** 已选择厂商 V，**When** 展开型号筛选，**Then** 候选只剩 V 旗下的型号
4. **Given** 已选择型号 M，**When** 查看厂商筛选，**Then** 它**保持「全部」不被自动填上**
5. **Given** 在「无类别」下勾了几列，**When** 切到某个类别再切回来，**Then** 那几列还在（「无类别」是独立的记忆档位）

### User Story 5 - 候选多的地方都能搜（Priority: P2）

凡是候选会无界增长的单选下拉，都能输入筛选。

**验收场景**

1. **Given** 录入设备对话框，**When** 展开类别/型号/持有方/负责人，**Then** 都能输入筛选
2. **Given** 流转对话框与更正流转，**When** 展开持有方/负责人，**Then** 能输入筛选
3. **Given** 两个审计页，**When** 展开「操作人」，**Then** 能输入筛选
4. **Given** 状态颜色、语言、每页条数、字段类型、角色、动作类型、持有方类型，**When** 展开，**Then** 仍是普通下拉，**没有**搜索框
5. **Given** 有人给一个无界候选的下拉用了普通 `Select`，**When** 跑测试，**Then** 失败并指出是哪一处

### Edge Cases

- **可搜字段的值为空**：不进索引；否则空值会命中一切。
- **可搜的计算字段**：值由表达式推导，重算后索引要跟着更新。
- **同时关掉唯一与可搜**：两张表的残值都要清。
- **改字段的键**：索引按键存，键变了索引要跟着变。
- **删字段 / 解绑**：残值要清。
- **回填时数据量大**：要么在事务里一次做完，要么明确说明中途失败会留下什么。
- **型号没有厂商**：字段集只有类别链 + 型号自己的绑定。
- **一台设备换型号**：旧型号带来的属性按既有规则归档（决策 98），本轮不变。
- **导入模板列变多**：一行填了不属于本行型号的列 → 预览阶段拒绝该行（既有规则）。
- **无类别时全库字段很多**：显示列菜单会长，本轮接受；它已经是个可滚动的菜单。

## Requirements *(mandatory)*

### Functional Requirements

**可搜索字段**

- **FR-001**：字段 MUST 有一个「可搜索」属性，**创建后 MUST 可修改**。
- **FR-002**：升级时既有字段 MUST 全部置为可搜索 —— 没有人因升级失去现有能力。
- **FR-003**：标记为唯一的字段 MUST 恒为可搜索，且该开关 MUST 在界面上显示为勾选且禁用，并说明原因。
- **FR-004**：打开一个字段的可搜索时，MUST 立刻回填全部存量设备的值；关闭时 MUST 清除。
- **FR-005**：可搜索的值 MUST 存在**独立于 `asset_unique_values` 的一张表**。**理由必须写进代码**：精确命中跳转读的是唯一值表，把非唯一值放进去会让搜索把人直接送进某一台设备。
- **FR-006**：资产搜索 MUST 覆盖可搜索字段的值、型号名、资产 id 前缀。备注 MUST NOT 被搜。
- **FR-007**：精确命中直接跳转 MUST 仍只依据**唯一**值，MUST NOT 因为可搜索值恰好只有一条就跳转。
- **FR-008**：空值 MUST NOT 进索引。
- **FR-009**：计算字段重算、字段改键、解绑、删字段 MUST 让索引保持一致。

**型号与类别解耦**

- **FR-010**：一台设备的有效字段集 MUST 是：它的类别链绑定 ∪ **它自己的型号**的绑定 ∪ 该型号所属厂商的绑定。MUST NOT 依赖该型号是否关联到该类别。
- **FR-011**：类别的有效字段集 MUST NOT 再包含「仅因某型号关联到它」而来的字段。
- **FR-012**：录入表单的型号下拉 MUST 列出全部型号；关联过当前类别的 MUST 排在前面。
- **FR-013**：`product_model_categories` MUST 保留，作为**排序建议**与删除类别时的提示依据，MUST NOT 再有强制力。
- **FR-014**：FR-010 与 FR-012 MUST 同轮生效。**单独做 FR-012 会制造「型号字段静默消失」**。

**键冲突**

- **FR-015**：绑定字段到类别、型号、厂商这**三处** MUST 都检查键冲突，且每处 MUST 问**三张绑定表**。
- **FR-016**：冲突的判据 MUST 是「两个不同的字段，同一个键，可能落在同一台设备上」。
- **FR-017**：升级 MUST 报告存量数据里已经存在的冲突，MUST NOT 静默通过。

**列与筛选**

- **FR-018**：未选择类别时，显示列的候选 MUST 是全库字段。
- **FR-019**：015 决策 103 的解锁规则 MUST 保留：只绑在型号上的字段，要先筛到该型号或其厂商才能显示。
- **FR-020**：显示列的记忆 MUST 把「无类别」当作一个独立档位。
- **FR-021**：型号筛选 MUST 不再依赖是否选择了类别。
- **FR-022**：选择厂商 MUST 把型号候选收窄到该厂商旗下。选择型号 MUST NOT 反向填写厂商。

**下拉可搜**

- **FR-023**：候选会无界增长的**单选**下拉 MUST 使用可搜索下拉：类别、型号、厂商、持有方、负责人、操作人。
- **FR-024**：候选有界的 MUST 保持普通下拉：状态颜色、语言、每页条数、字段类型、角色、动作类型、持有方类型。
- **FR-025**：MUST 有一条源码级测试扫描全部普通下拉的使用处，不在白名单上的即失败；白名单每条 MUST 写明为什么候选有界。
- **FR-026**：导入页 MUST NOT 改动。
- **FR-027**：多选场合（型号的所属类别、字段绑定目标）MUST NOT 在本轮改动。

**导入导出**

- **FR-028**：类别的导入模板 MUST 列出该类别链的字段加上**全部**型号/厂商字段；每行按其自身的型号校验，填了不属于本行型号的列 MUST 拒绝该行。

### Key Entities

- **字段**：新增「可搜索」。唯一蕴含可搜索。
- **可搜索值索引**：设备 × 字段键 × 值。与唯一值表分开，因为一个管「找得到」，一个管「不能重复」。
- **型号**：属于一个厂商；与类别的关联降级为建议。
- **设备的有效字段集**：类别链 ∪ 自己的型号 ∪ 该型号的厂商。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：建一个非唯一字段并勾上可搜索后，搜它的值**立即**命中，包括**建字段之前**就录入的设备。
- **SC-002**：升级后，今天能搜到的每一个值仍然能搜到 —— **零能力回退**，由一条对比升级前后可搜集合的测试固定。
- **SC-003**：一台设备的字段集在「型号关联了本类别」与「没关联」两种情况下**完全相同**（读两条路径互相比较）。
- **SC-004**：同键冲突在三处绑定入口**都**被拒绝（三处各一条测试），且升级会报告存量冲突。
- **SC-005**：不选类别、只选厂商时，能勾出并看到该厂商字段的列 —— 今天这个操作的结果是**空菜单**。
- **SC-006**：全站无界候选的单选下拉**全部**可搜，由白名单测试固定；白名单之外为零。
- **SC-007**：精确命中跳转的触发次数不因本轮增加 —— 由「两台设备共享一个可搜值」的测试固定。

## Assumptions

- **回填在一个事务里做完。** 现有规模（数千台）一次写完是毫秒级；上万台时的进度反馈留到真的遇到时再说，而不是现在猜。
- **索引按字段键存，不按字段 id。** 与 `asset_unique_values` 一致，`attrs` 本来就是按键存的。
- **「可搜索」不做作用域** —— 一个字段要么全系统可搜，要么不可搜。按类别分别设置会让同一个字段在两处行为不同。
- **全库字段的显示列菜单会变长**，接受。它已经是可滚动的菜单，而替代方案（按当前筛选推断）会让人问「我的字段去哪了」。
