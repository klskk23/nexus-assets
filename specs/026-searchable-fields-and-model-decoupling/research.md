# 调研：可搜索字段、解耦、下拉可搜

## 一、可搜索的值存哪

**结论：新表 `asset_search_values`，只存当前值；搜索**同时读两张表**。**

不能塞进 `asset_unique_values`：`exactMatch`（搜到唯一一台就直接跳详情）读的正是那张表。
把非唯一值放进去，两台设备共享一个 service tag 就会把人甩进其中一台。

也不把唯一值复制一份进新表。搜索改成读两处的并集：

| 表 | 内容 | 为什么 |
|---|---|---|
| `asset_unique_values` | 唯一字段的值，**含已归档的** | 「旧编号仍能搜到」是既有行为：有人手里拿着旧标签 |
| `asset_search_values` | 非唯一可搜字段的**当前值** | 不留历史 |

**历史的不对称是有理由的，不是偷懒。** 一个唯一值是身份主张 —— 编号换了，
拿着旧标签的人仍然应该找得到那台设备。一个普通可搜值没有这层主张，
留着它的历史只会让搜索命中一堆「曾经是」。

## 二、键冲突的精确判据

**两个绑定冲突，当且仅当存在一台设备同时受两者作用。**

一台设备有：一条类别链，以及可选的一个型号（型号带一个厂商）。解耦之后型号与类别无关，
所以任意型号都可能出现在任意类别下：

| | 冲突条件 |
|---|---|
| 类别 C ↔ 类别 D | 同一条链（祖先或后代） |
| 类别 C ↔ 型号 M | **总是** —— 型号现在可以出现在任何类别下 |
| 类别 C ↔ 厂商 V | **总是** |
| 型号 M ↔ 型号 N | `M == N` —— 一台设备只有一个型号，两个不同型号永不同台 |
| 型号 M ↔ 厂商 V | `M.vendor == V` |
| 厂商 V ↔ 厂商 W | `V == W` |

「型号 ↔ 型号 只在同一个型号上冲突」这一条要留意：**两个不同型号可以各自绑一个同名键的字段**，
这是合法的，因为它们永不落在同一台设备上。把规则简化成「一个键全局只能绑一次」会误杀它。

**解耦让第二、三行从「同链才冲突」变成「总是冲突」** —— 这是解耦的代价，写下来。

## 三、有效字段集怎么改

今天：`FieldsOfPath(path)` 收集类别链绑定，再加上**关联到该链的型号**的绑定，
最后 `ForModel(fields, modelID)` 收窄。

改为：**类别链绑定 ∪ 该设备型号自己的绑定 ∪ 该型号厂商的绑定**，不经过类别关联。

- 写入（`pipeline.go`）与读取（`query.go`）都已经是 `ForModel(...)` 的形状，
  改的是**候选怎么来**，不是收窄怎么做。
- `EffectiveFields(categoryID)`（无型号）今后只答类别链 —— 这是 FR-011。
  它的调用方（`/categories/:id/schema`）本来就是「这个类别本身配了什么」，语义反而更准。
- 需要一个新的入口回答「这一台能填什么」：`FieldsForAsset(categoryPath, modelID)`。
