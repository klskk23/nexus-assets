# Feature Specification: 可配置的状态

**Feature Branch**: `001-asset-ledger-demo`（沿用主开发分支，未另开分支）

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "状态使用 Badge 组件了吗？单开一个状态功能页，
除了这几条状态，允许自定义，和上面一样支持删除自定义的状态，且允许设置状态的颜色。
你可以为当前这几个状态设置你认为合理的默认 custom color。"

> **语言规范**（章程原则 V）：本规格的全部正文内容必须使用**中文**撰写。
> 仅以下内容保留英文：API 路径与参数名、字段 key、错误码 `error.code`、
> 数据库标识符。用户可见文案（UI 文本、字段 label、`error.message`）使用中文。

> **与既有规格的关系**：本规格**修订**而非取代 001–003。设计层面的对应文档是
> `docs/design-baseline-v4.md`（决策 53–60）。

| 既有需求 | 本规格的处置 |
|----------|--------------|
| 001 的五个状态常量与 5×5 转换矩阵 | **保留不变**，改由数据承载 → FR-001、FR-006 |
| 001「在库的持有方必须是位置」 | **推广** → FR-004：任何状态都可以声明这条约束 |
| 001「类别分布不含已报废」 | **推广** → FR-005：由 `counts_as_available` 决定 |
| 003 FR-001~005 信息项可删除 | **沿用同一条规则** → FR-011：有资产使用则拒绝删除 |
| 001 状态标签由 `zh.status` 提供 | **取代** → FR-008：标签来自数据库，`zh.status` 撤销 |

> **一处被明确回答的问题**：用户先问「状态使用 Badge 组件了吗？」
> 答案是用了，但每个状态都是同一个 `variant="secondary"` 的灰色徽章 ——
> 也就是说这一列在被读之前不携带任何信息。本轮把颜色变成状态自己的属性（FR-007）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一眼分辨状态 (Priority: P1)

管理员打开资产列表，四十行里哪几台丢了、哪几台在修，靠颜色就能看出来，
不需要逐行读文字。

**Why this priority**: 这是用户第一句话直接指向的问题，也是**每次打开列表都在发生**的成本。
其余故事都是配置动作，一天做不了几次。

**Independent Test**: 打开资产列表，确认在库、丢失、维修中三种徽章颜色互不相同；
切换到浅色主题，确认三者仍然可读且仍互不相同。

**Acceptance Scenarios**:

1. **Given** 一页混合状态的资产，
   **When** 查看状态列，
   **Then** 每种状态的徽章使用它自己配置的颜色
2. **Given** 深色主题（本系统默认），
   **When** 查看任意状态徽章，
   **Then** 文字与背景对比充分，不出现浅色底上的浅色字
3. **Given** 切换到浅色主题，
   **When** 查看同一批徽章，
   **Then** 颜色语义不变（丢失仍是红系），可读性不下降
4. **Given** 资产详情页与概览页，
   **When** 查看状态，
   **Then** 与列表页使用同一套颜色，不存在某个页面仍是灰色

---

### User Story 2 - 加一个业务需要的状态 (Priority: P2)

公司开始把设备外借给客户试用。这既不是「已签出」（不是内部领用）也不是「在库」。
管理员自己加一个「外借中」，选一个颜色，立刻能在流转对话框里选到它。

**Why this priority**: 用户明确要求的能力。五个内置状态覆盖不了每家公司的流程，
而每加一个状态都要改代码、发版本，等于这个系统只能记录它作者想到的那些事。

**Independent Test**: 新建一个状态，把一台设备转入它，确认它出现在筛选框、
概览卡片与时间线上，且都显示配置的名字与颜色。

**Acceptance Scenarios**:

1. **Given** 状态管理页，
   **When** 填写键名、显示名与颜色并提交，
   **Then** 新状态出现在列表末尾，标记为「自定义」
2. **Given** 键名含空格、大写或中文，
   **When** 提交，
   **Then** 系统拒绝并说明键名的规则（**不是**报服务器错误）
3. **Given** 颜色填的是十六进制值而非色板里的名字，
   **When** 提交，
   **Then** 系统拒绝并说明只能从色板中选
4. **Given** 键名与已有状态重复，
   **When** 提交，
   **Then** 系统拒绝并指出该键名已存在
5. **Given** 一台在库设备与一个新建的自定义状态，
   **When** 把设备转入该状态，
   **Then** 流转成功，记为 `status_change`
6. **Given** 该设备处于自定义状态，
   **When** 查看首页概览，
   **Then** 该状态有自己的卡片，计数正确

---

### User Story 3 - 状态携带行为 (Priority: P3)

管理员新建的状态不只是一个标签：他可以声明「处于这个状态的设备必须放在某个位置」、
「这个状态不计入可用库存」、「这是终态，进去就不再转出」。

**Why this priority**: 五个内置状态之所以不只是标签，正是因为它们各自携带这三种行为。
如果自定义状态拿不到同样的能力，它就只是一个染了色的字符串，用户很快会撞到
「为什么我的『已核销』还能转回在库」。

**Independent Test**: 建一个标记为终态的状态，把设备转进去，确认再往外转被拒绝。

**Acceptance Scenarios**:

1. **Given** 一个勾选了「持有方必须是位置」的自定义状态，
   **When** 把一台由某个人持有的设备转入它，
   **Then** 系统拒绝，并说明该状态的持有方必须是位置
2. **Given** 一个取消了「计入类别分布」的自定义状态，
   **When** 该状态下有设备并查看首页类别分布，
   **Then** 这些设备不计入，但仍计入总台数
3. **Given** 一个标记为终态的自定义状态，
   **When** 把设备转入后再尝试转出，
   **Then** 系统拒绝
4. **Given** 任意一个内置状态，
   **When** 打开状态管理页，
   **Then** 这三个开关不可编辑；页面说明内置状态的行为由系统定义
5. **Given** 内置状态与自定义状态并存，
   **When** 尝试 `lost → in_use`（001 起就被禁止的一条），
   **Then** 仍然被拒绝 —— 引入自定义状态没有放松任何既有护栏

---

### User Story 4 - 删掉不再需要的状态 (Priority: P4)

外借业务停了。管理员把「外借中」删掉，前提是没有设备还处在这个状态。

**Why this priority**: 与 003 的信息项同一条规则。配置阶段的试错必然产生废弃条目，
不提供清理方式就等于让列表越用越脏。

**Independent Test**: 建一个自定义状态并删除；再建一个、放一台设备进去，
确认删除被拒绝且拒绝里报出台数。

**Acceptance Scenarios**:

1. **Given** 一个没有任何设备使用的自定义状态，
   **When** 执行删除，
   **Then** 删除成功，它从所有下拉框中消失
2. **Given** 仍有设备处于该状态，
   **When** 执行删除，
   **Then** 系统拒绝，并说明还有几台设备挡着
3. **Given** 任意一个内置状态，
   **When** 查看它所在的行，
   **Then** 没有删除入口；页面已说明原因
4. **Given** 一个只在流转历史里出现过、当前无设备使用的状态，
   **When** 执行删除，
   **Then** 删除成功；确认框事先说明它在多少条记录里出现过
5. **Given** 上述删除之后，
   **When** 查看那台设备的流转时间线，
   **Then** 相关记录显示原始键名而非标签，记录本身完整保留
6. **Given** 删除确认框，
   **When** 未输入该状态的键名，
   **Then** 确认按钮不可用

---

## Requirements *(mandatory)*

### 状态成为数据

- **FR-001**: 状态 MUST 存储为一张表，主键是 key。内置的五个由迁移写入并标记 `builtin`。
- **FR-002**: `assets.status` MUST NOT 加外键。应用层已有「有资产使用则拒绝删除」的检查，
  再做一次 `assets` 表重建换不到新的保证。
- **FR-003**: 状态的展示顺序 MUST 由 `sort` 列决定；新建状态排在现有全部之后。

### 行为由列承载

- **FR-004**: `requires_location` 为真的状态，其持有方 MUST 是位置实体。
  内置状态中仅 `in_stock` 为真。
- **FR-005**: `counts_as_available` 为假的状态，其设备 MUST NOT 计入首页的类别分布，
  但 MUST 计入总台数。内置状态中仅 `retired` 为假。
- **FR-006**: 转换规则 MUST 按以下方式切分：双方都是内置状态时沿用 001 的 5×5 矩阵，
  一条不改；任一方是自定义状态时放行，但 `from` 被标为终态的除外。
- **FR-007**: 「签出」「归还」的推导 MUST 继续绑定内置的 `in_stock ↔ in_use`。
  自定义状态之间的移动记为 `status_change`。

### 标签与颜色

- **FR-008**: 状态标签 MUST 来自数据库。前端的 `zh.status` 与导出器里的重复副本 MUST 移除。
- **FR-009**: 颜色 MUST 是色板里的名字，MUST NOT 是十六进制值。
  色板 MUST 在两套主题下各定义一次。
- **FR-010**: 内置五个的默认颜色为：在库绿、已签出蓝、维修中琥珀、丢失红、已报废石墨。

### 生命周期

- **FR-011**: 自定义状态在没有任何资产处于该状态时 MUST 可删除；有则 MUST 拒绝并报出台数。
- **FR-012**: 内置状态 MUST NOT 可删除，其三个行为开关 MUST NOT 可改；
  标签、颜色、排序 MUST 可改。
- **FR-013**: 状态只在流转历史里出现 MUST NOT 构成拒绝理由。删除前 MUST 告知出现次数。
- **FR-014**: 键名被拒绝、颜色不在色板、键名重复这三种情况 MUST 返回可操作的错误
  （422 或 409），MUST NOT 返回 500。

### 界面

- **FR-015**: 状态 MUST 有独立的管理页，形态与类别／信息项／型号／持有方一致：
  新建走按钮 + 对话框，列表为表格，删除走二次确认并要求输入键名。
- **FR-016**: 每一个渲染状态的界面 MUST 通过同一处解析标签与颜色：
  列表、详情、概览卡片、筛选框、录入与流转对话框、流转时间线。
- **FR-017**: 状态键在系统中不存在时（被删除、或数据来自更早的版本），
  界面 MUST 回退显示原始键名，MUST NOT 显示空白或报错。

## Success Criteria *(mandatory)*

- **SC-001**: 打开资产列表，五种内置状态的徽章颜色两两可区分，深浅两套主题下均如此。
- **SC-002**: 新建一个自定义状态到它能在流转对话框里被选中，全程不需要改代码或重启。
- **SC-003**: 001 起存在的每一条转换护栏，在引入自定义状态后逐条仍然生效。
- **SC-004**: 删除一个用过的状态之后，`nexus verify` 仍然全绿，流转历史一条不少。
- **SC-005**: 状态标签在系统中只有一处定义。

## Assumptions

- **色板固定为 8 个槽位**。用户说的是「允许设置状态的颜色」，不是「允许输入任意颜色」。
  固定槽位换来的是暗色主题下的可读性保证，这在一个默认深色的应用里不是可选项。
- **内置状态可以改名**。用户没有明确要求，但「允许设置颜色」已经承认这五个的呈现是可配的；
  只让改颜色不让改名字是一条没有理由的界线。行为开关是另一回事，它们有理由（FR-012）。
- **不做状态的拖拽排序**。`sort` 列存在且新建状态排在最后，够用。
  排序 UI 属于另一个故事，本轮不做也不留半成品入口。
