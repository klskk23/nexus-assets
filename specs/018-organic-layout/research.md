# 调研：Organic 版面重做

七个问题决定这一轮的形状。三个让工作量比预估小，两个把规格的措辞改准了，
一个把规格里唯一一颗钉子拔掉了，一个改变了验收方式。

---

## 一、居中列已经不存在了，真实差距是「没有上限」

参照稿的审视第 1 条说 `AppShell` 用 `mx-auto max-w-7xl` 两侧对称留白。
**实测：全站 `max-w-7xl` 与 `mx-auto` 零命中。** 017 换侧栏时已经拿掉了。

真实现状是另一回事：`<main>` 只有 `p-8`，**没有任何宽度上限**，
内容在宽屏上一路顶到右边。这不是「居中」，是「没有边界」——
但它同样不是稿子要的「贴左 960px 上限、右侧留白」。

**结论**：FR-001 的「MUST NOT 使用居中列」已经天然成立，
实际要做的是**加上限**。规格的 FR-001 与概要已按此改写（analyze 抓到过一次：
这句话原先声称改过而实际没改）。

## 二、地面分工的实际面：19 处，其中 1 处本来就是对的

| 位置 | 现状 | 应当 |
|---|---|---|
| `TableFrame` | `bg-card` | 地面色（容器与圆角保留，见第三节） |
| `AppShell` 外层 | `bg-card` | 见待定的侧栏两版 |
| `Login` 左列 | `bg-card` 整块面板 | 稿子的 `SignIn` 没有这块面板 —— 两列直接坐在地面上 |
| `StatCard` | `<Card>` | 地面色 + `--border-muted` 描边 |
| `Overview` ×3、`AssetDetail` ×5、`Import` ×3、`AssetHistory`、`EditEvent` | `<Card>` | 分区改用留白；只读值组改 `--well` |
| **`ActionBar`** | `<Card className="sticky bottom-4">` | **不动** —— 它真的浮在表格之上，`--card` 是对的 |
| `components/ui/card.tsx` | 定义 `bg-card` | **不动** —— Card 本身就是「浮起」这个原语 |
| `components/ui/alert.tsx` | `bg-card` | 待定：Alert 不浮起，但改它会波及全站提示 |

`ActionBar` 值得单独说：它是这一条规则唯一一处**判对了**的地方，
而且是规则真正起作用的证明 —— 同样叫「卡片」的东西，浮起的留下、不浮的换掉。

**结论**：地面分工不是全局搜索替换，是十九处逐个判断「它浮起来了吗」。

## 三、表格的差距比预期小：表头与行线 017 就对了

| | 现状 | 稿子 |
|---|---|---|
| 表头底 | `bg-well` | `background: var(--well)` ✅ **已对** |
| 行分隔 | `border-border-muted` | `1px solid var(--border-muted)` ✅ **已对** |
| 容器 | `rounded-[28px] border bg-card` | `border 1px + radius 28px + background: var(--background)` |
| 表头单元格 | `h-9 px-2 text-[13px] font-medium text-muted-foreground` | `padding:15px 20px; font-size:13px; font-weight:600; color: var(--secondary-foreground)` |
| 数据单元格 | `px-2 py-1.5` | `padding:15px 20px; font-size:14px` |

**行高 48px 来自内边距，不是显式高度。** `15 + 15 + 18` ≈ 48。
所以不需要给行设 `h-12`，把 `py-1.5` 换成 `py-[15px]` 即可 ——
后者对含芯片、含按钮的行也成立，前者会打架。

**结论**：表格三件套改的是 `TableFrame` 的一个类、`TableHead` 与 `TableCell`
各一串类。改完，**十个表格页一起变**。

## 四、`font-heading` 只有一处是错的

四处命中：`AppShell` 的产品名（拉丁 ✅）、`Login` 的产品名 ×2（拉丁 ✅）、
**`PageHeader` 的 h1（中文 ❌）**。

017 在 `PageHeader` 上写了一条注释解释为什么不加 `font-weight`
（「Caprasimo 只有一个字重，合成加粗会在中文回退字体上出现」）——
那条推理本身是对的，但它建立在一个错误前提上：Caprasimo 根本没有渲染那些中文字。

**结论**：改一个文件。`font-heading` 从中文 h1 上摘掉，
层级改由 `text-[40px]/1.2 font-bold` 建立。资产编号那类拉丁数字标题
（`AssetDetail` 的 h1）反过来**应当**加上 `font-heading`。

## 五、焦点环：机制可以换，数字不变（FR-017 的重测已完成）

`outline: 2px solid #8c491a; outline-offset: 2px`，实测：

| 底色 | 对比 |
|---|---|
| 页面 `#f5ead8` | **5.72:1** |
| 卡片 `#ebddc5` | **5.09:1** |
| 下沉 `#f9f4ed` | **6.22:1** |
| 次级 `#eee7db` | **5.54:1** |

WCAG 1.4.11 要 3:1 —— 最低 5.09，全过。2.4.13 要求周长至少 2 CSS px —— 2px 达标。

**为什么数字能跨机制沿用**：017 那次失败的原因是**半透明**（`ring/50` 只有 1.69），
不是机制。换成 outline 之后颜色仍是实心 `#8c491a`，而 `outline-offset: 2px`
让环的两侧都贴在底色上，不再半压在控件自己的描边上 ——
几何上比 017 的实心 ring **更干净**，不需要再算复合色。

**结论**：FR-017 的重测通过，可以换。**但这个结论是量出来的，不是推出来的** ——
规格坚持重测是对的，只是这次结果是好的。

## 六、零测试断言尺寸类 —— 这改变了验收方式

35 个测试文件、712 条角色断言，其中断言 `gap-6` / `max-w-` / `h-9` /
`bg-card` / `font-heading` 的：**0 条**。

两个方向的推论：

1. **纯版面改动应当一条测试都不打到。** 只要不动 DOM 结构与角色，367 个测试全绿。
   这大幅降低了这一轮的风险。
2. **但测试也守不住版面。** 行高从 48 退回 36、`bg-card` 被人加回来，
   测试一声不吭。

**结论**：这一轮的验收重量落在**截图走查**上，而 DOM 测试的职责是守住
**版面改动不得破坏的行为** —— 行点击仍进详情、选择模型七项仍在、
空态仍给清除筛选。写断言类名的测试是脆的，不写。

## 七、按钮 44px 与「控件高 48px」不冲突

`AssetList.dc.html` 里「显示列」按钮是 `height:44px`，而 README 的间距表写
「控件高 48px」。看起来矛盾，实际不是：README 那一行的原文是
**「输入/选择 `48px`（登录页 `50px`），按钮 `11–13px` 纵向内边距」**——
按钮从来不是按高度规定的，是按内边距。11–13px 内边距 + 18px 行高 = 40–44px，
和稿子一致。

**结论**：输入与选择走 48px，按钮走纵向内边距。README 与 HTML 没有冲突，
是我第一遍读漏了。

## 八、被拒绝的替代方案

| 方案 | 为什么不做 |
|---|---|
| 全局搜索替换 `bg-card` → `bg-background` | 会把 `ActionBar`（真的浮起）和 `ui/card.tsx`（浮起原语本身）一起改错。十九处要逐个判断 |
| 给 `TableRow` 设 `h-12` | 行高应当来自单元格内边距。显式高度会和含芯片、含按钮的行打架 |
| 为版面写断言类名的 DOM 测试 | 脆，且测的是实现不是行为。版面的守门人是截图，不是 `toHaveClass` |
| 把参照稿的内联样式搬进来 | 稿子自己说了它不是生产代码。实现要用仓库现成的组件与工具类重建 |
| 顺手修 `ui/alert.tsx` 的 `bg-card` | Alert 不浮起，但改它会波及全站每一条提示。留到计划阶段单独判断 |
