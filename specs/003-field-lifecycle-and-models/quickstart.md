迁移做三件事：`field_definitions` 去掉 `archived_at`、`product_models` 去掉 `category_id`

## 信息项：三条下线路径变成两条

| 想做的事 | 怎么做 |
|----------|--------|
| 建错了，删掉重建 | `/fields` 里直接**删除** |
| 不再需要，但存量数据要留 | 在 `/categories` 里从类别上**解绑** |
| ~~暂时不用，以后可能再启用~~ | ~~停用~~ —— 已移除 |

删除会在三种情况下被拒绝，提示各不相同：

```
被表达式键引用   →  表达式键「设备编号」正在引用「基准 MAC」，请先修改它们
被选作显示编号   →  类别「SDWAN 路由器」的显示编号正在引用它
有资产填了值     →  仍有 1,847 台设备填写了「基准 MAC」，此处仅列出前 5 台
```

第三条是**这一轮新增的判定**，它要扫一次全表。删除是低频操作，这个代价换来的是
「删除永远不会丢数据」。

**要记住的一件事**：一旦解绑，那个字段基本就永远删不掉了 —— 存量的孤儿值仍然算「有值」。
定义会一直留在信息项库里。这是设计上接受的终点（决策 44），不是缺陷。

## 型号：一个型号可以服务多个类别

```
/models  →  新建型号
           名称   X100
           厂商   Acme        ← 参与重名判定，留空也是一个独立的命名空间
           类别   ☑ SDWAN 路由器  ☑ 备件      ← 多选
           默认值 firmware = 2.1.3
                  ports    = 8
```

录入设备时，下拉里能看到**关联到本类别或其任一祖先**的型号。
关联在子类上的型号，父类的资产看不见 —— 想让它可见就显式勾上父类。

选中型号后，默认值只填当前类别有效字段集里的键。型号关联了两个类别、
而某个键只属于其中一个时，另一边会静默跳过 —— 默认值是「能填则填」，不是承诺。

## 验证

```bash
rm -f nexus.db nexus.db-wal nexus.db-shm
./nexus seed 20          # seed 现在会建一个带默认值、关联两个类别的型号
./nexus
```

```bash
# 1. 建一个没人用的信息项，删掉它 → 204
# 2. 给它绑到类别、录一台设备填上值，再删 → 409，列出那台设备
# 3. 解绑它 → 204；新建资产的表单不再有它，已有资产的详情页仍能读到旧值
# 4. 录入设备时展开型号下拉 → 非空，且能看到关联在祖先类别上的型号
# 5. 停用一个仍被设备持有的位置 → 界面逐台列出阻挡的设备（此前只有一句概括）
```

## 容易被静默做错的三处

001 的五条与 002 的四条仍然成立。本轮新增：

1. **`vendor` 必须 `NOT NULL`**。`UNIQUE(vendor, name)` 在 SQLite 里对 NULL 无效 ——
   NULL 被视为互不相等，任意多行 `(NULL, 'X100')` 都能插进去，而表结构看上去仍有 UNIQUE。
   哪天有人把它改回可空，重名约束会**静默失效**。

2. **删除判定要 `trim` 后判空，不是判 `IS NOT NULL`**。
   一个曾经被填过又清空的字段，`attrs` 里会留下 `""`。按 `IS NOT NULL` 判，它永远删不掉，
   而用户看到的界面上那一栏明明是空的。

3. **`archived_attrs` 不要跟着停用一起删掉**。它装的是**孤儿键** —— 由解绑产生，
   和信息项的停用是两回事。移除停用时很容易顺手把它也清理掉，
   那会让「解绑后仍能查看旧值」当场失效，而且没有任何测试会失败（001 的用例覆盖的是
   解绑路径，不是停用路径）。
