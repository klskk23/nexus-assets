## User Scenarios & Testing *(mandatory)*

### User Story 1 - 删掉建错的信息项 (Priority: P1)

管理员建信息项时打错了 key，或者建完发现类型选错了。他直接删掉它重建，
不需要留下一条永远躺在列表里的「已停用」记录。

**Why this priority**: 这是用户报告的核心诉求，也是唯一一个**每天都在制造垃圾**的问题 ——
配置阶段的试错必然产生废弃条目，而系统不提供任何清理方式。

**Independent Test**: 建一个信息项，不绑定到任何类别，删除它，确认它从列表中消失；
再建一个、绑定到类别但不录任何资产，同样能删。

**Acceptance Scenarios**:

1. **Given** 一个刚建好、未绑定到任何类别的信息项，
   **When** 执行删除，
   **Then** 记录从信息项库中消失
2. **Given** 一个已绑定到某类别、但没有任何资产填过值的信息项，
   **When** 执行删除，
   **Then** 删除成功，该类别上的绑定一并消失
3. **Given** 某台资产在该信息项上存有非空值，
   **When** 执行删除，
   **Then** 系统拒绝，并列出前若干台设备与受影响的总台数
4. **Given** 某个表达式键读取该信息项，
   **When** 执行删除，
   **Then** 系统拒绝，并指出是哪个表达式键在读它
5. **Given** 某个类别把该信息项选作显示编号，
   **When** 执行删除，
   **Then** 系统拒绝，并指出是哪个类别在用它
6. **Given** 任意一个信息项，
   **When** 打开它的编辑界面，
   **Then** 界面上只有「删除」，不存在「停用」

---

### User Story 2 - 下线一个仍在使用的字段 (Priority: P2)

某个信息项不再需要了，但上千台设备上还存着它的历史值。管理员把它从类别上**解绑**：
新录入的设备不再需要填它，存量数据保留下来可以查看。

**Why this priority**: US1 移除了停用机制，而停用原本承担的正是这个场景。
不把解绑做出来，US1 就是净损失 —— 管理员既不能停用也不能删除，一个用过的字段无路可走。

**Independent Test**: 在一个已录入资产的类别上解绑某个信息项，确认新建资产的表单不再显示它，
而已有资产的详情页仍能在「已归档字段」中读到旧值。

**Acceptance Scenarios**:

1. **Given** 一个已绑定且有存量数据的信息项，
   **When** 从类别上解绑它，
   **Then** 解绑成功；新录入表单不再包含它
2. **Given** 上述解绑之后的一台存量设备，
   **When** 查看详情，
   **Then** 旧值仍可读，标记为已归档字段，且不参与校验
3. **Given** 某个表达式键正在读取该信息项，
   **When** 尝试解绑，
   **Then** 系统拒绝，并指出是哪个表达式键在读它
4. **Given** 某个类别把该信息项选作显示编号，
   **When** 尝试解绑，
   **Then** 系统拒绝，并指出是哪个类别在用它
5. **Given** 类别配置页面，
   **When** 查看已绑定的信息项列表，
   **Then** 每一项都有可用的解绑入口

---

### User Story 3 - 一个型号服务多个类别 (Priority: P3)

同一款路由器既属于「SDWAN 路由器」，也属于「备件」。管理员建一次型号，
把它关联到两个类别，两边录入设备时都能选到它。

**Why this priority**: 用户明确报告的第二个模型问题。单值归属逼着管理员在两个都对的
答案里选一个，或者把同一款设备建两遍 —— 后者会让默认值维护立刻分叉。

**Independent Test**: 建一个型号并关联到两个互不相干的类别，分别在两个类别下录入设备，
确认型号下拉里都能看到它。

**Acceptance Scenarios**:

1. **Given** 一个型号，
   **When** 把它关联到两个类别，
   **Then** 两个类别下录入设备时都能选到它
2. **Given** 一个型号已关联某类别，
   **When** 解除该关联，
   **Then** 该类别下不再能选到它，另一个类别不受影响
3. **Given** 两家厂商都有一款叫 X100 的产品，
   **When** 分别建立这两个型号，
   **Then** 都能建成，因为重名判定包含厂商
4. **Given** 同一厂商已有一款 X100，
   **When** 再建一个同厂商同名型号，
   **Then** 系统拒绝
5. **Given** 一个型号关联在「网络设备」上，
   **When** 在它的子类「SDWAN 路由器」下录入设备，
   **Then** 该型号出现在下拉中
6. **Given** 一个型号只关联在子类「SDWAN 路由器」上，
   **When** 在父类「网络设备」下录入设备，
   **Then** 该型号**不**出现在下拉中

### User Story 4 - 型号真正可用 (Priority: P4)

管理员给型号配上默认值，录入设备选中它时这些值被自动填进去。

**Why this priority**: 型号的默认值能力从 001 起就在数据层存在，但**界面上从来没有过入口** ——
`attr_defaults` 至今没有被真实使用过一次。US3 让型号能对上类别，这个故事让它有内容可给。

**Independent Test**: 给一个型号配两条默认值，录入设备时选中它，确认空字段被填上、已填字段不动。

**Acceptance Scenarios**:

1. **Given** 型号管理页面，
   **When** 新建或编辑一个型号，
   **Then** 可以逐条增删该型号的默认值（键与值）
2. **Given** 一个带默认值的型号，
   **When** 录入设备时选中它，
   **Then** 尚未填写的字段被填入默认值，已填写的保持不变
3. **Given** 一个型号关联了两个类别，其默认值中有某个键只存在于其中一个类别，
   **When** 在另一个类别下选中该型号，
   **Then** 该键被静默跳过，其余默认值正常填入
4. **Given** 一个全新的演示库，
   **When** 执行 `nexus seed`，
   **Then** 库中含有带默认值的型号，型号下拉不为空

---

### User Story 5 - 界面说的和系统做的一致 (Priority: P5)

管理员停用一个仍被设备使用的位置，界面上直接列出是哪几台设备挡着 ——
而不是只给一句「仍被 5 台设备使用」然后让他自己去找。

**Why this priority**: 这一组是清查出来的既有不一致，单独看都不严重，
合起来是「界面在描述一个不存在的系统」。优先级最低，但都是低成本修复。

**Independent Test**: 触发一次持有方停用失败，确认阻挡设备被逐台列出；
通读类别页与首页的空状态文案，确认没有一处仍在说类别决定编号如何生成。

**Acceptance Scenarios**:

1. **Given** 一个仍被设备持有的位置，
   **When** 尝试停用它，
   **Then** 界面逐台列出阻挡的设备，形态与信息项的引用列表一致
2. **Given** 类别页与首页的空状态，
   **When** 阅读其提示文案，
   **Then** 没有任何一处说「类别决定编号怎么生成」
3. **Given** 前端的用户可见文案集合，
   **When** 检查每一条，
   **Then** 不存在没有任何代码引用的死文案

### Edge Cases

- **孤儿键让字段永远删不掉**：解绑之后存量值仍在，因此该定义此后基本无法删除。
  这是决策 44 的已知终点，不提供强制删除
- **删除判定的代价**：判断「有没有资产填过值」是一次全表扫描。删除是低频操作，接受
- **删除与解绑的先后**：一个字段被绑定在多个类别上，删除会连同全部绑定一起消失 ——
  前提是没有任何资产填过值
- **型号关联为空**：一个型号可以不关联任何类别。此时它在所有录入表单里都不出现，
  等同于草稿。不禁止
- **`vendor` 为空的型号**：空厂商是一个合法的命名空间，同名空厂商型号仍然互斥
- **导入时型号重名**：名称在全库命中多条时该行报错，提示改写为「厂商 型号」
- **默认值的键不属于任何类别**：允许存在（型号可能先配默认值后关联类别），套用时跳过
- **停用位置的阻挡列表很长**：仅列出前若干台并给出总数，与信息项的引用列表同一约定

## Requirements *(mandatory)*

### Functional Requirements

**信息项的删除**

- **FR-001**: 信息项必须支持删除；停用机制必须从信息项上移除
- **FR-002**: 当任何资产在该信息项上存有非空值时，删除必须被拒绝
- **FR-003**: 删除被拒绝时，必须列出前若干台受影响的设备与受影响的总台数
- **FR-004**: 当任何表达式键读取该信息项、或任何类别把它选作显示编号时，删除必须被拒绝
- **FR-005**: 删除成功时，必须一并移除它在全部类别上的绑定，以及资产 `attrs` 中可能残留的该键

**字段的下线**

- **FR-006**: 系统必须提供把信息项从类别上解绑的接口与界面入口
- **FR-007**: 解绑后，存量资产上的该键必须保留、可查看、不再参与校验与唯一性
- **FR-008**: 解绑必须沿用既有护栏：被表达式键读取、或被选作显示编号时拒绝

**一致性范围**

- **FR-009**: 持有方实体与账号必须继续只支持停用，不支持删除

**型号与类别**

- **FR-010**: 一个型号必须能同时归属于多个类别
- **FR-011**: 型号的重名判定必须以厂商与名称的组合为准；空厂商视为一个独立命名空间
- **FR-012**: 录入设备时，型号下拉必须列出关联到该资产类别或其任一祖先类别的型号
- **FR-013**: 已停用的型号不得出现在下拉中

**型号的默认值**

- **FR-014**: 型号管理界面必须提供逐条增删默认值的入口
- **FR-015**: 选中型号时，只填充当前类别有效字段集内的键，其余静默跳过
- **FR-016**: 演示数据必须包含至少一个带默认值的型号

**导入**

- **FR-017**: 导入仍按型号名称解析；名称在全库唯一命中则接受，命中多条时该行报错并提示改写为「厂商 型号」

**界面与 API 的一致**

- **FR-018**: 停用持有方被拒绝时，界面必须逐台列出阻挡的设备，形态与信息项的引用列表一致
- **FR-019**: 用户可见文案中不得描述系统已不再具备的行为
- **FR-020**: 用户可见文案集合中不得存在无任何代码引用的条目
- **FR-021**: 测试中的模拟响应数据不得包含服务端不会返回的字段

### Key Entities

- **型号与类别的关联**：一个型号可以出现在哪些类别的录入表单里。多对多，
  取代 001 中型号身上的单值 `category_id`
- **孤儿键**：从类别上解绑后，仍留在资产 `attrs` 中的键值。保留展示、不校验、不唯一。
  它是「下线一个用过的字段」的最终形态，也是那个字段此后无法删除的原因

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员建错一个信息项后，可在 30 秒内把它从系统中彻底移除，不留下任何残留条目
- **SC-002**: 任何一次被拒绝的删除，其提示都直接指出是哪些设备、哪个表达式键或哪个类别挡着，
  管理员不需要自行排查
- **SC-003**: 「不再需要某个字段」在界面上有一条可走通的路径（此前为 0 条）
- **SC-004**: 同一款设备在多个类别下可用，且只需维护一份默认值（此前必须建两遍）
- **SC-005**: 型号的默认值在录入设备时被实际使用（此前为 0 次）
- **SC-006**: 一个全新演示库执行 seed 后，型号下拉非空
- **SC-007**: 任何一次被拒绝的配置变更，界面呈现的阻挡对象数量与 API 返回的一致（0 处丢弃）
- **SC-008**: 用户可见文案中描述已废弃行为的条目数为 0
- **SC-009**: 测试模拟数据中服务端不返回的字段数为 0

## Assumptions

- 本规格的设计决策以 `docs/design-baseline-v3.md`（决策 41–52）为准；
  未被 v3 触及的部分依次以 v2（25–40）、v1（1–24）为准；
  开发与质量约束以 `.specify/memory/constitution.md`（v1.1.0）为准
- **不新增章程条款**。用户提出过「加一条章程要求对齐前端与 API」，
  澄清时确认先不加。本轮逐处手工对齐，并在设计文档中记录这个选择的代价：
  下次模型变动时同类漂移会原样重演，且同样全绿
- **不提供强制删除**。一个被解绑、留有孤儿值的字段此后基本无法删除，这是接受的结果
- 型号候选范围取「本类别或任一祖先」，导入仍按名称解析 —— 这两项在访谈中未获明确答复，
  按倾向实现并在此声明，以便后续推翻
- 以下能力明确不在本特性范围内：批量清空某个信息项在全部资产上的取值、
  持有方与账号的删除、前端与 API 一致性的机械门禁、
  型号默认值按类别分别配置、枚举选项的删除（当前仍是标记废弃）
