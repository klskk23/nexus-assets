# 数据模型：028

**本轮没有迁移。** 表结构一列不动，新增的只是两条读法。

## 已有的表，本轮怎么读

### `holder_entities`

| 列 | 本轮的用处 |
|---|---|
| `id` | 树的节点、地址里的 `:id`、计数的键 |
| `type` | `company` / `department` / `location`，行上的类型标识 |
| `name` | 行的文字、搜索的匹配对象、路径的组成 |
| `parent_id` | **树的唯一事实**。递归 CTE 沿它展开；前端也沿它爬出搜索命中行的完整路径 |
| `note` | 右栏单独一块 |
| `is_default_stock` | 全局唯一。页头那一行、右栏按钮的禁用判据 |
| `attrs` | 本轮不读 |

**没有 `path` 列，本轮也不加。** 类别有物化路径，持有方没有；给它加一列意味着每次改上级
都要重写子树的 path，而这张表最深三层、总量几十。理由见 research 第二节。

**层级规矩**（既有，服务端强制，本轮不改）：

| 类型 | 上级 | 必填 |
|---|---|---|
| `company` | 不能有 | — |
| `department` | 只能是 `company` | **是** |
| `location` | `company` 或 `department` | 否 |

推论：**根一级 = 全部公司 + 全部无上级的位置**；树最深三层；**环在结构上不可能**
（部门的父只能是公司，公司没有父）—— 但遍历仍加界，一份坏数据不该把页面挂死。

### `assets`

只读两列：`holder_type`（必须 `= 'entity'`）与 `holder_id`。
`status` **不参与**持有方的计数 —— 这是与类别口径故意不同的那一处。

## 新增的读法（不是新表）

### 持有方子树设备数

```
holderID -> int
```

- **含子树**：一个公司的数字包含它底下所有部门与位置的设备。
- **含全部状态**：报废的设备还堆在那个仓库里。
- **空节点写 0，不缺键**：`LEFT JOIN` 而非 `JOIN`；行尾留白读起来是「没加载」，
  与「没有」是两个不同的答案。
- **只数实体持有的**：设备也可以由账号持有，那一侧不在这棵树上。

### 资产筛选：持有方含下级

`ListFilter` 增加一个开关。为真时，持有方筛选从「就是这一个」变成「这一个及其全部下级」。
**默认为假** —— 既有链接与筛选栏里的 `holder_id` 一直是前者，改默认值会静默改变它们的含义。

## 前端的行模型

```ts
interface HolderRow {
  holder: HolderEntity
  depth: number          // 缩进；搜索态恒为 0
  hasChildren: boolean   // 决定这一行画不画折叠三角
  path?: string          // 只在搜索时有：「国药集团 / 研发部 / 三楼实验室」
}
```

与 `CategoryRow` 同形，因为它们是同一个问题。区别只有一处：类别的 `rootIDOf` 读物化
路径的第一段，持有方的得沿 `parent_id` 往上爬（带界）。

## 不变的东西

- `HolderUsage`（`assets` / `children` / `history`）结构不变，**只改什么时候问**：
  从页面加载时为每一行预取，改成打开删除确认时问那一个。
- 编辑与新建的请求体不变。
- `is_default_stock` 仍然只接受设为真：标记会移走，不会关掉。
