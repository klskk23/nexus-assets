# 调研：字段页与型号页主从化

四个问题。前两个是新计数，第三个是树的分页与折叠怎么落地，第四个是骨架能不能不动。

---

## 一、型号的设备数

**结论：新增一条批量查询，口径与类别计数相同 —— 排除 `counts_as_available = 0` 的状态。**

仓库里已经有两处按型号数设备，**都是逐个型号问一次的守卫，不是给列表用的**：

| 位置 | SQL |
|---|---|
| `schema/model_binding.go:252` | `count(*) FROM assets WHERE model_id = ? AND deleted_at IS NULL` |
| `schema/model_store.go:403` | `count(*) FROM assets WHERE model_id = ?` |

两句今天返回同一个数 —— `deleted_at` 这一列确实存在（001 建表时留的，注释写着
「reserved; demo uses hard delete」），而系统一直是硬删，所以它永远是 NULL。
**不是 bug，是同一件事的两种写法**；本轮不动它们，它们是守卫不是展示。

左栏要的是**一次问出全部型号**的数，逐个问会让一个带 60 个型号的厂商发 60 次请求 ——
`overview.go` 的注释已经为同一个理由写过一遍：「Counting each category with its own
query would look harmless at four categories and turn the landing page into the
slowest screen at forty」。

**口径跟类别走**：含义是「这类东西现在有多少台可用」，所以排除标了「不计入类别分布」
的状态。理由不是对称好看，是 024 立的那条规矩：**一个系统只能有一种「有多少台」**。
两个数字都在一个屏幕上出现过（型号页的行、类别页的行），差一个已报废设备就会有人来问。

## 二、字段的绑定数

**结论：三张绑定表各 `GROUP BY field_id` 一次，在内存里相加。**

`docs/rules/schema.md` 已经写死了这件事的形状：「**`boundPaths` 要问三张表** ——
少问一张，那类字段就答『没绑』，所有按绑定路径收窄的删除守卫当场静默失效」。
计数是同一个陷阱的轻量版：少问一张表，某些字段会显示 0，而 **0 恰恰是这一列最有用的
那个值**（「这个字段还有人用吗」是删它之前必问的），于是错得最像对的。

三条查询，不是 `UNION`：三张表的行数量级不同，且以后若有第四种绑定目标，
`UNION` 里漏加一条与三条里漏加一条一样容易，但前者更难读出来。

---

## 三、树按根分页 + 按节点折叠

### 分页

`flattenCategories` 现在返回全部行。改成：**先取根节点，按根节点分页，再把选中那些根的
子树压平**。

```
roots = items.filter(无父)          // 或：厂商 / 字段组
page  = roots.slice(offset, offset+limit)
rows  = page.flatMap(subtreeOf)
```

**一页的行数因此不固定** —— 一个带 60 个型号的厂商自己就是一页里的 60 行。这是接受的
代价，换来的是 014 决策 91 那个坑不存在：任何一行的父都在同一页上。

**分页条放哪**：左栏 300px 宽，而 `Pager` 是一整行（区间 + 页码 + 每页条数），
为表格下方设计的。**左栏用简化的一条**（上一页/下一页 + 第 n/N 页），不套 `Pager` ——
把一个为另一种位置设计的部件塞进来，就是把它的假定一起塞进来（024 对 `ListToolbar`
下过同样的判断）。

### 折叠

**判据是单个节点的子项数**，不是全树总行数。写死一个常数在代码注释里，不做配置：
可配置意味着两个部署长得不一样，而这是视觉节奏不是策略。

**取 12。** 依据是行高 38px + 左栏可见高度约 700px ≈ 18 行；一个节点占满可见区
之前折起，才谈得上「还能看见别的节点」。

**默认折起，不是永久折起**：`FR-021` 要求手动展开在本次浏览中保持，所以组件里存一份
「使用者手动改过的节点」集合，它压过默认规则。**不进地址** —— 折叠是一次浏览中的姿势，
不是一个可分享的位置。

**这是折叠第三次被讨论。** `CollapsibleTree` 删过一次，024 又删过一次，两次的理由都是
「一个把答案藏起来一半的控件」。这次能成立，只因为条件变了：那两次是**无条件**折叠，
这次只在一个节点大到会把别人挤出屏幕时才折，且行上写着「N 个」——
**读者知道自己没看到什么**，这正是前两次缺的东西。

## 四、骨架要不要改

**结论：预期零改动。若发现必须改，按 FR-029 报告而不是顺手改。**

逐条核对这两页要的东西落在谁身上：

| 要的 | 谁负责 | 骨架要改吗 |
|---|---|---|
| 右栏两种形态 | 调用页渲染的 `detail` 节点 | 否 |
| 左栏分页 | 调用页渲染的 `list` 节点 | 否 |
| 折叠 | 调用页自己的树组件 | 否 |
| 一个 id 空间里两种东西 | 调用页查两张表 | 否 —— `useMasterSelection` 只认 `ids: string[]` |
| 选中项不在当前页仍要显示 | 调用页把「全部 id」而不是「本页 id」传给钩子 | 否 |
| 两个新建按钮 | 调用页 | 否 |

最后一行是唯一需要想一下的：`useMasterSelection(ids, id)` 的 `ids` 要传**全部**可选项，
不是当前页的。传当前页会让翻到第二页时选中项被判成「不存在」——
这不是骨架的缺陷，是调用方传错参数。

024 的调研里我写过一句预测：「第二个调用方进来时最可能要改的是左栏宽度」。
**三页都用 300px，连这个都不需要。** 若实现中打脸，如实写下来。
