# 规格：字段页与型号页改主从两栏，页签合并

**分支**：`025-master-detail-fields-models` ｜ **决策**：161–174
**推翻**：014 对 `/fields` 与 `/models` 的 `CrudPage` 形态、016 决策 107 对这两对的适用
**修订 024**：类别页也加分页；折叠有条件地回来

## 概要

024 把类别页改成了「左边一棵树，右边是选中那一个的全部配置」。字段与型号是同样的
形状被同样地误放着：**它们各自被拆成两个页签两条路由**，而两边讲的是同一件事的两半。

- `/fields` 与 `/fields/groups`：一个字段组就是一把字段。要知道「采购与财务这个组里
  有什么」，得切到另一页；要知道「这个字段属于哪些组」，得回到这一页再开对话框。
- `/models` 与 `/models/vendors`：一个型号属于一个厂商。**这是一条真的层级**，
  却被摊成两张互不相干的表。

### 两页看起来一样，底下的关系不一样

**厂商 → 型号是一对多**（`product_models.vendor_id` 可空）。这是一棵真的树，
`Vendor.ModelCount` 服务端读取时就已经填好。左栏放成两层，没有任何代价。

**字段 ↔ 字段组是多对多。** `field_group_members` 的主键是 `(group_id, field_id)`，
还有一条 `ORDER BY field_id, group_id` 的反查 —— **一个字段可以同时属于多个组，
也可以一个组都不属于**。把组当父节点，同一个字段就会在树上出现多次。

**本轮接受这个重复，并把它变成信息**：地址 `/fields/:id` 选中的是**那个字段**，
不是树上某一行，所以它出现的每一处**同时高亮**。一眼就能看出它同时在两个组里 ——
而如果只亮一处，两行长得一模一样却只有一行亮着，读起来像两个不同的东西。

**但搜索结果里只出现一次。** 搜索会把树压平，组的层级随之消失；同一个字段在一个
没有层级的列表里出现两遍，就只剩重复，没有那份信息了。

### 规模：024 的假设在这两页不成立

024 的左栏敢不分页，前提写在它的 Assumptions 里：「类别是配置而非数据，一屏到几十个」。
字段与型号没有这个上限 —— 它们今天都在分页（`CrudPage` + 信封）。

所以本轮要给左栏一条退路。**但树不能按行分页**：014 决策 91 记过这个坑 ——
「第 2 页开头的子类别会失去它在第 1 页的父，缩进就成了没有出处的悬空」。
**树按根节点分页，子树跟着它的根走**：一页是 N 个根，不是 N 行。缩进永远有出处。

**折叠也回来了，但只在一处、只按一个条件**：子项超过阈值的**那一个节点**默认折起，
并在行上写明「N 个」。不看全树总数 —— 那样新建一个类别会让整棵树突然全部合上，
读起来像坏了。**这是折叠第三次被讨论**（`CollapsibleTree` 删过一次，024 又删过一次），
所以这次的条件必须写死，而不是「太长就折」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一个字段属于哪些组、绑在哪儿，一眼看全（Priority: P1）

管理员打开字段页，左边是按组分层的字段树，点任意字段，右边显示它的键、类型、
是否唯一、是否必填、属于哪些组，以及**它被绑在哪些类别、型号、厂商上**。

**为什么是 P1**：这是本轮的动因。今天「这个字段绑在哪儿」要开对话框，
而「这个组里有什么」在另一个页签。

**独立测试**：造若干字段与组（含一个属于两组的、一个不属于任何组的），逐个点选。

**验收场景**

1. **Given** 存在字段组与字段，**When** 打开字段页，**Then** 左栏按组分层，未分组的字段在一个**不可选**的「未分组」标题下
2. **Given** 某字段同时属于两个组，**When** 选中它，**Then** 它在树上出现的**每一处都高亮**
3. **Given** 选中一个字段，**When** 查看右栏，**Then** 列出它被绑到的全部目标（类别、型号、厂商）与各自是否必填
4. **Given** 选中一个**组**，**When** 查看右栏，**Then** 显示组名、成员、以及这个组被绑到哪些目标
5. **Given** 左栏每一行，**When** 看行尾，**Then** 字段行显示**绑定数**（三张绑定表之和），0 也写出来

### User Story 2 - 型号与厂商在同一棵树上（Priority: P1）

管理员打开型号页，左边是「厂商 → 它旗下的型号」，没有厂商的型号在一个不可选的
「无厂商」标题下。点型号看型号详情，点厂商看厂商详情。

**为什么是 P1**：与 US1 同一个动因，且这里是一条真层级，今天却被摊成两张表。

**独立测试**：造两个厂商各带几个型号，再造一个无厂商的型号，逐个点选。

**验收场景**

1. **Given** 存在厂商与型号，**When** 打开型号页，**Then** 型号排在各自厂商之下，无厂商的在「无厂商」标题下
2. **Given** 选中一个型号，**When** 查看右栏，**Then** 显示厂商、所在类别、在册设备数、以及这个型号的字段（标出哪些**继承自厂商**）
3. **Given** 选中一个厂商，**When** 查看右栏，**Then** 显示型号数、绑给旗下全部型号的字段
4. **Given** 左栏，**When** 看行尾，**Then** 厂商行显示型号数，型号行显示**在册设备数**

### User Story 3 - 权限按控件各管各的（Priority: P1）

只有 `model.manage` 的人能改厂商的名字，但不能改厂商的字段绑定；
只有 `schema.manage` 的人反之。两种情况下页面内容都完整可见。

**为什么是 P1**：023 刚刚把厂商的增删改从 `schema.manage` 拆给 `model.manage`，
**就是为了让管型号的人能改厂商名**。把这两件事合回一个开关会当场撤销那个决定。

**独立测试**：分别以只带 `model.manage`、只带 `schema.manage`、两者都无的身份打开厂商详情。

**验收场景**

1. **Given** 只有 `model.manage`，**When** 打开某厂商，**Then** 「编辑厂商」可用，字段绑定区禁用并说明需要「管理类别与字段」
2. **Given** 只有 `schema.manage`，**When** 打开某厂商，**Then** 字段绑定区可用，「编辑厂商」禁用并说明需要「管理型号」
3. **Given** 两个权限都没有，**When** 打开厂商，**Then** 全部内容可见，两处都禁用且各自说明缺什么
4. **Given** 任何权限状态，**When** 查看右栏，**Then** 没有破坏性动作（删除仍在编辑对话框里）

### User Story 4 - 列表长起来之后仍然能用（Priority: P2）

字段或型号增长到几百个时，左栏仍然可用：扁平列表分页，树按根节点分页，
子项过多的节点默认折起。

**为什么是 P2**：今天数量还不多，但这是唯一一处「数据长大之后页面直接不能用」的风险。

**独立测试**：造超过一页的字段、超过一页的厂商、以及一个带很多型号的厂商。

**验收场景**

1. **Given** 字段数超过一页，**When** 翻页，**Then** 左栏换一批字段，选中的那个若不在本页则右栏仍显示它
2. **Given** 厂商数超过一页，**When** 翻页，**Then** 一页是 N 个**厂商及其全部型号**，不是 N 行 —— 不会出现看不到厂商的型号行
3. **Given** 某厂商旗下型号数超过阈值，**When** 打开页面，**Then** 该厂商默认折起，行上写明「N 个」，其余厂商不受影响
4. **Given** 一个默认折起的节点，**When** 点开它，**Then** 展开，且**这个选择在本次浏览中保持**
5. **Given** 全树总行数很多但每个节点子项都不多，**When** 打开页面，**Then** 没有任何节点被自动折起

### User Story 5 - 搜索（Priority: P2）

左栏顶部搜索。有搜索词时切成平展命中列表，**同一个字段只出现一次**。

**为什么是 P2**：与 024 一致；但去重是这一页独有的，因为只有这一页会重复。

**验收场景**

1. **Given** 某字段属于两个组，**When** 搜索命中它，**Then** 它在结果里**只出现一次**
2. **Given** 处于搜索结果，**When** 清空搜索，**Then** 恢复成树，该字段又在两处出现
3. **Given** 搜索无命中，**When** 查看左栏，**Then** 说明没有匹配

### User Story 6 - 旧地址不失效（Priority: P3）

`/fields/groups` 与 `/models/vendors` 重定向到新页。

**验收场景**

1. **Given** 打开 `/fields/groups`，**When** 页面加载，**Then** 落到新的字段页
2. **Given** 打开 `/models/vendors`，**When** 页面加载，**Then** 落到新的型号页

### Edge Cases

- **一个组都没有**：树退化成一列未分组字段，「未分组」标题仍然是唯一的分段标题。
- **一个空组**：组行显示「0 个」，展开后什么都没有 —— 而不是看起来无法展开。
- **一个字段都没有**：左栏空态指向「新建字段」，右栏不画空框架。
- **选中的字段不在当前页**：右栏照常显示它。选中来自地址，与左栏这一页显示什么无关。
- **删除当前选中的组**：选中落到确定且存在的地方。
- **把字段移出它所在的唯一一个组**：它移动到「未分组」下，选中不丢。
- **无厂商的型号**：在「无厂商」下，不可选中那个标题。
- **一个型号都没有的厂商**：厂商行显示 0，展开后为空。

## Requirements *(mandatory)*

### Functional Requirements

**页面形状**

- **FR-001**：`/fields` MUST 是主从两栏，左为按组分层的字段树，右为选中项的详情。`/fields/groups` MUST 不再是独立页面。
- **FR-002**：`/models` MUST 是主从两栏，左为「厂商 → 型号」树，右为选中项的详情。`/models/vendors` MUST 不再是独立页面。
- **FR-003**：两页的左栏 MUST 各有一个**不可选的分段标题**收容没有归属的条目（「未分组」「无厂商」）。它 MUST NOT 可选中 —— 它不是一个对象。
- **FR-004**：两页的左栏底部 MUST 有**两个并排的新建入口**（新建字段/新建组、新建型号/新建厂商），各自按自己的权限禁用并说明。

**字段树的重复**

- **FR-005**：属于多个组的字段 MUST 在每个组下各出现一次。
- **FR-006**：选中一个字段时，它出现的**每一处 MUST 同时高亮**。选中的语义是「哪个字段」，不是「树上哪一行」。
- **FR-007**：搜索结果中，同一个字段 MUST 只出现一次。平展之后组的层级已经消失，重复不再携带任何信息。

**右栏**

- **FR-008**：右栏 MUST 能显示**两种形态**（字段/组、型号/厂商），由选中项决定。
- **FR-009**：字段详情 MUST 显示键、类型、是否唯一、是否必填、所属组，以及**被绑到的全部目标**（类别、型号、厂商）与各自是否必填。
- **FR-010**：组详情 MUST 显示成员与这个组被绑到哪些目标。
- **FR-011**：型号详情 MUST 显示厂商、所在类别、在册设备数、以及这个型号的有效字段，并**标出哪些继承自厂商**。
- **FR-012**：厂商详情 MUST 显示型号数与绑给旗下全部型号的字段。
- **FR-013**：右栏 MUST NOT 包含删除或其他破坏性动作。
- **FR-014**：四种「修改」入口 MUST 打开各自现有的编辑对话框。本轮 MUST NOT 改动这些表单的字段构成。

**计数**

- **FR-015**：字段行 MUST 显示**绑定数** —— 类别、型号、厂商三张绑定表之和。0 MUST 写出来。
- **FR-016**：厂商行 MUST 显示型号数（复用既有的 `model_count`）。
- **FR-017**：型号行 MUST 显示**在册设备数**，且 MUST 与系统其他地方回答「有多少台」的口径一致（024 决策 154–155 已定的那一条）。

**规模：分页与折叠**

- **FR-018**：扁平的左栏列表 MUST 可分页。
- **FR-019**：**树 MUST 按根节点分页** —— 一页是 N 个根节点及其全部后代，不是 N 行。MUST NOT 出现父节点不在本页的子节点。
- **FR-020**：**子项数超过阈值的节点 MUST 默认折起**，并在行上写明子项数。判据 MUST 是**单个节点的子项数**，MUST NOT 是全树总行数 —— 后者会让新增一个节点把整棵树合上。
- **FR-021**：折叠状态 MUST 可由使用者手动改变，且改变 MUST 在本次浏览中保持。
- **FR-022**：当前选中项 MUST 在右栏显示，**与它是否在左栏当前这一页无关**。
- **FR-023**：以上分页与折叠 MUST 同样适用于类别页（修订 024）。

**权限**

- **FR-024**：厂商详情的权限 MUST 按控件区分：名称等属性看 `model.manage`，字段绑定看 `schema.manage`。MUST NOT 合并成一个开关 —— 那会撤销 023 的拆分。
- **FR-025**：任何权限状态下页面内容 MUST 完整可见；不可用的入口 MUST 禁用并说明缺少哪个权限，MUST NOT 隐藏。

**地址与迁移**

- **FR-026**：`/fields/:id` MUST 是**一个 id 空间**，组与字段共用。页面 MUST 自行判断选中的是哪一种。
- **FR-027**：未指定时 MUST 默认显示树上第一个可选项，**地址 MUST 保持不带 id**（与 024 一致，且窄屏的树因此仍可达）。
- **FR-028**：`/fields/groups` 与 `/models/vendors` MUST 重定向到各自的新页面。

**骨架**

- **FR-029**：本轮 MUST NOT 为接入这两个调用方而修改主从骨架（`MasterDetail`、`useMasterSelection`）。**若发现必须修改，MUST 在实现报告中说明改了什么、为什么，而不是顺手改掉** —— 024 的 SC-005 把「第二个调用方接入时骨架零改动」定为成功标准，本轮是它唯一一次能被真正验证的机会。
- **FR-030**：骨架的「只有一个调用方」测试 MUST 更新为三个具名调用方，MUST NOT 改成不检查。

**连带**

- **FR-031**：`MetadataTabs` 在移除型号/厂商与字段/字段组两组后只剩审计一组，MUST 移入审计自己的目录并改名 —— 一个只服务一处的「通用」组件会被下一个人当成全站约定。
- **FR-032**：`docs/rules/web-tables.md` MUST 记下：树按根分页、按节点折叠的判据、以及字段树重复与去重的两条规则。

**范围之外**

- **FR-033**：本轮 MUST NOT 改动字段绑定模型或字段组语义（016 决策 105、v6 决策 72 不动）。
- **FR-034**：本轮 MUST NOT 把审计页改成主从两栏 —— 它的两栏都是带筛选带分页的长表，不是「列表 + 当前项」。

### Key Entities

- **字段**：键、标签、类型、选项、唯一、必填。被绑到类别/型号/厂商三种目标。可属于任意多个组。
- **字段组**：名字与一把字段。绑定时展开的糖，绑定表上没有它（016 决策 105）。
- **厂商**：名字，一对多地拥有型号，可绑字段并被旗下型号继承。
- **型号**：名字、一个可空的厂商、多个类别、默认值。
- **左栏的一行**：一个可选中的条目、或一个不可选的分段标题。同一个条目可以对应多行。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：查清「某个字段绑在哪些地方、属于哪些组」，**零次**页签切换、**零次**打开对话框。今天是 1 次切换 + 1 次开关。
- **SC-002**：查清「某个厂商旗下有哪些型号」，**零次**页签切换。
- **SC-003**：主从骨架文件在本轮的改动量为 **0 行**（`MasterDetail.tsx`、`useMasterSelection.ts`）。这是 024 SC-005 的真正验证；不为 0 即为该目标未达成，且必须说明。
- **SC-004**：一个属于两个组的字段，在树上出现 2 次、在搜索结果里出现 1 次 —— 两个数都由测试固定。
- **SC-005**：型号行的设备数与系统其他地方对同一问题给出的数**完全相等**（读两条路径互相比较，不与常量比）。
- **SC-006**：任一权限组合下，页面可见信息量为 **100%**，且每个禁用入口都能说出缺哪个权限。
- **SC-007**：字段或型号增长到 200 个时，找到任意一个仍只需**一次搜索输入**，且没有任何一行的父节点不可见。

## Assumptions

- **阈值取一个具体数字并写进代码注释**，不做成配置。可配置的阈值意味着两个部署长得不一样，而这是个视觉节奏问题，不是策略问题。
- **折叠状态不进地址**：它是一次浏览中的姿势，不是一个可分享的位置。刷新后回到默认。
- **搜索仍是客户端过滤**：树要靠全量数据才建得出来；分页取的是「显示哪一页」，不是「服务端筛掉什么」。
- **型号的设备数与类别的设备数共用同一条服务端路径**，理由与 024 相同：一个系统只能有一种「有多少台」。
