# Feature Specification: 资产归属与表格规范

**Feature Branch**: `001-asset-ledger-demo`（沿用主开发分支，未另开分支）

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "1. 默认库存点我认为应该设置为录入设备时的默认选择，
但设备自身要绑定一个自身的默认持有方和用户，归还则默认归还到该持有方和用户
（归还也需要可以选择持有方和用户）。 2. 规范前端页面设计，表格的风格应该统一和资产一样
（除了没有勾选），需要都改为点击行进入修改，而不是外部展示按钮，表格区域添加 Context Menu，
右键打开可选择操作，信息项型号持有方至少要包含编辑和删除操作，根据不同的特性增加不同的按钮。
3. 语言模式等设置收纳进 shadcn 的下拉按钮，资产页面的勾选后的弹出框高度还是太长，需要缩短。"

> **与既有规格的关系**：本规格**修订**而非取代 001–006。

| 既有需求 | 本规格的处置 |
|----------|--------------|
| 001/002：归还指向唯一的全局默认库存点 | **降为兜底** → FR-001~FR-006：归还先看设备自己的归属 |
| 003 FR-030 型号只能新建 | **补齐** → FR-011~FR-014：型号可编辑、可删除 |
| 006 持有方的编辑/删除是行内按钮 | **取代** → FR-007~FR-010：改为行点击 + 右键菜单 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 设备回到自己的家 (Priority: P1)

上海的设备借出去又还回来，应该回上海，不是回北京 —— 哪怕北京是默认库存点。

**Independent Test**: 两台归属不同仓库的设备一起归还，确认各回各家。

**Acceptance Scenarios**:

1. **Given** 录入一台设备，**Then** 它的默认归属自动是录入时选的持有方与负责人
2. **Given** 一批归属不同仓库的设备，**When** 一次归还，**Then** 各自回到各自的归属
3. **Given** 一台没有设过归属的设备（升级前录入的），**When** 归还，**Then** 回到全局默认库存点
4. **Given** 既没有归属、也没有全局默认库存点，**When** 归还，**Then** 提示选择位置而不是失败
5. **Given** 资产详情页，**Then** 可以修改默认归属的持有方与负责人，也可以清空
6. **Given** 清空归属后归还，**Then** 回到全局默认库存点

### User Story 2 - 归还时也能指定去处 (Priority: P2)

**Acceptance Scenarios**:

1. **Given** 归还对话框，**Then** 目标默认是「各自的默认归属」
2. **Given** 选定一个具体持有方，**When** 提交，**Then** 全部设备去那里，忽略各自的归属
3. **Given** 归还对话框，**Then** 负责人默认「不变」—— 归属已经回答了这个问题
4. **Given** 指定负责人，**When** 提交，**Then** 覆盖归属带来的负责人

### User Story 3 - 表格操作统一 (Priority: P3)

**Acceptance Scenarios**:

1. **Given** 任一元数据表格，**When** 点击一行，**Then** 打开该条的编辑界面
2. **Given** 任一元数据表格，**When** 右键一行，**Then** 打开操作菜单
3. **Given** 表格中不再有成列的操作按钮
4. **Given** 信息项、型号、持有方的右键菜单，**Then** 至少含「编辑」与「删除」
5. **Given** 某项操作对该行不适用（内置状态不能删、已停用的账号不能再停用、
   当前默认库存点不能再设为默认），**Then** 该菜单项**呈现为禁用**而非消失
6. **Given** 不可撤销的操作，**Then** 确认框要求输入该行的标识

### User Story 4 - 型号可以修改和删除 (Priority: P4)

**Acceptance Scenarios**:

1. **Given** 一个型号，**When** 点击它，**Then** 可改名称、厂商、所属类别与默认值
2. **Given** 只提交了部分字段，**Then** 其余字段保持不变
3. **Given** 改名后与同厂商的另一款重名，**Then** 拒绝并指出厂商与名称
4. **Given** 没有设备使用的型号，**When** 删除，**Then** 成功，类别关联一并解除
5. **Given** 仍有设备是该型号，**When** 删除，**Then** 拒绝并给出台数

### User Story 5 - 界面收纳 (Priority: P5)

**Acceptance Scenarios**:

1. **Given** 顶栏，**Then** 语言、主题、退出登录收在一个下拉里
2. **Given** 该下拉的触发按钮，**Then** 它的可访问名是当前用户名，不是「设置」
3. **Given** 勾选资产后的操作栏，**Then** 高度贴合按钮，不含多余留白

## Requirements *(mandatory)*

### 资产归属

- **FR-001**: 资产 MUST 可以记录一个默认归属：持有方与负责人，两者均可为空。
- **FR-002**: 录入时未指定归属的，MUST 以录入时的持有方与负责人作为归属。
- **FR-003**: 归还未指定目标时，MUST 逐台解析：设备的归属 → 全局默认库存点 → 提示选择。
- **FR-004**: 归还未指定负责人时，MUST 采用该设备归属的负责人（若有）。
- **FR-005**: 归还 MUST 可以指定持有方与负责人，指定后对整批生效。
- **FR-006**: 归属 MUST 可以在资产详情页修改与清空。清空后回退到全局默认库存点。

### 表格规范

- **FR-007**: 元数据表格 MUST 支持点击行打开编辑界面。
- **FR-008**: 元数据表格 MUST 支持右键打开操作菜单，MUST NOT 保留成列的操作按钮。
- **FR-009**: 信息项、型号、持有方的菜单 MUST 至少含编辑与删除；其他对象按其特性增减。
- **FR-010**: 不适用于该行的菜单项 MUST 呈现为禁用而非消失 ——
  「为什么没有这个操作」比一个灰掉的条目更难回答。

### 型号生命周期

- **FR-011**: 型号 MUST 可编辑名称、厂商、所属类别与默认值。
- **FR-012**: 未提交的字段 MUST 保持不变。
- **FR-013**: 编辑造成同厂商重名 MUST 被拒绝。
- **FR-014**: 型号在无设备使用时 MUST 可删除，类别关联一并解除；有则拒绝并给出台数。

### 界面

- **FR-015**: 语言、主题与退出登录 MUST 收在一个下拉菜单里。
- **FR-016**: 该下拉的触发按钮 MUST NOT 用 `aria-label` 覆盖用户名。
- **FR-017**: 资产选中栏的高度 MUST 贴合其内容。

## Success Criteria *(mandatory)*

- **SC-001**: 两台归属不同仓库的设备一次归还，各回各家。
- **SC-002**: 每个元数据页的操作都能从行点击或右键到达，表格里没有操作按钮列。
- **SC-003**: 型号可以改完再删，删除在被使用时被拒绝并说明。
- **SC-004**: 全部变更后 `nexus verify` 仍然全绿。

## Assumptions

- **归属在详情页改，不在录入表单里问。** 录入时它就等于你刚选的持有方 ——
  再问一遍是一个答案已定的问题，而录入对话框刚因为太长被抱怨过。
- **类别页不改成表格。** 它是一棵树加一个详情面板，不是列表；套用表格规范会把它变差。
- **账号不加删除。** `actor_id` 从每条审计记录指向它，永远删不掉。菜单里只有停用。
- **归还的「各自的默认归属」是唯一能逐台不同的选项。** 一旦选了具体持有方，
  整批都去那里 —— 一次操作只有一个目标是可预期的。
