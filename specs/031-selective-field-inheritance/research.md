# 研究与技术裁定：类别字段可选继承

## R1：独立正向选择，不复制绑定

**决定**：新增 category_field_selections(category_id, field_id)，仅存明确选择。category_fields 继续只代表直接绑定。来源由父类有效结果递推，最终保留原始绑定类别。

**理由**：复制 category_fields 会让继承变成直接绑定，父级撤回无法传播，category_ids、唯一 scope 和管理入口同时失真。排除表或旧类别兼容模式均不符合已确认的新旧统一正向选择。

**替代方案**：整类别继承开关不能逐字段选择；默认继承加排除表会让未来新增字段自动下传；复制字段定义会分裂字段规则，均拒绝。

## R2：统一快照解析，但保留三种查询语义

**决定**：批量加载类别、直接绑定、继承选择及设备侧绑定形成同一读取快照，类别解析从根向下按选择裁剪；EffectiveFields 回答类别有效集，FieldsForAsset 再加实际型号与厂商字段，EveryPossibleField 保留混合型号的完整可能列。

**理由**：不能为了入口统一而把三个业务问题混成一种集合。批量快照可供预览、提交、verify 和按行适用性共同使用，并避免每台资产单独查 schema。

**替代方案**：各 SQL 继续用祖先 path 拼字段会遗漏选择；只给 Resolve 增加过滤而保留消费者原 SQL 会造成读取与守卫分歧。

## R3：归档值可查看，不等于可搜索

**现状证据**：internal/asset/query.go 的 exactMatch 先查 live 唯一行，再查 archived 唯一行；普通搜索也查整张 asset_unique_values。persist.go 的 syncUniqueValues 只设置 archived_at，故单纯归档无法满足撤回后不可搜。

**决定**：asset_unique_values 增加 search_suppressed 标记，默认 0 保留既有历史搜索。继承失效时，相关 asset_id + field_key 的全部当前及历史行置 1，当前行同时归档。唯一精确查询和普通搜索统一排除标记行；ValueHistory 保留它们供查看。恢复时新建有效行默认 0，不重新启用此前被抑制的历史行。

**理由**：保留原始历史值，又能区分普通改号与字段撤回。恢复后的当前值能搜，不代表恢复所有被撤销的旧身份主张。

**替代方案**：删除唯一历史行会损失现有历史查看；统一不搜所有 archived 行会推翻与本轮无关的历史编号规则；仅加 archived_at 无效。

## R4：对帐必须核对字段身份、scope 与实际到达

**现状证据**：cmd/nexus/verify.go 的 verifyUniqueValues 用 ancestor path 检查缺项，仅比较 key/value，不核对正确 scope 或完整设备侧字段。verifyKeyConflicts 按全库 key 分组，会把合法兄弟类别和不相交设备侧同名键也报告为冲突。

**决定**：加载一致读取快照，为资产推导预期 live 唯一值及搜索值，与实存索引双向比对，核对 value、scope、缺项、残留及 live 行不得 suppressed。选择合法性、编号依赖和类别树完整性另行校验。冲突验证按既有绑定冲突矩阵执行：同链类别保守冲突，兄弟类别和不相交设备字段合法，类别与设备侧同 key 冲突。

**理由**：继承撤回后 raw attrs 仍存在，raw JSON 相等不能证明 live 索引合法。不能复用旧祖先查询让 verify 在合法撤回上报漏项。

**历史限制**：仅凭当前字段集无法准确判断每一条历史行的失效原因；保留类型标记并测试写入边界，verify 不擅自清理正常型号变更或普通改号的历史。

## R5：导出与打印必须逐行检查类别适用性

**现状证据**：internal/importer/export.go、rows.go 使用选中类别 EveryPossibleField 生成表头，但单元格只检查 AppliesTo(fd, modelID)。父类筛选包含后代时，子类可以不继承父字段，因此只检查型号不足。

**决定**：表头仍按请求类别 schema 生成，不随匹配数据变化；每行用快照中的该资产类别和型号有效字段 ID 验证单元格。无效字段为空，不把 raw attrs 的归档值当当前值。跨类别勾选导出仍按类别分包。

**替代方案**：按本次资产并集拼表头会改变现有 schema 决定列的约定；逐行网络或数据库查 schema 会产生 N+1。

## R6：字段搜索重建不能绕过继承状态

**现状证据**：internal/schema/field_store.go 的 reindexField 按 field_key 全库删除并从 raw attrs 重建，既可能重新索引已撤回值，也会波及兄弟类别同 key 的其他字段。

**决定**：按字段 ID 和有效到达集合重建，只更新该字段真实适用资产的索引；无法继续使用裸 key 全库操作。搜索开关变更、绑定与继承变更都使用同一实际适用性规则。

**理由**：只在继承保存时清掉索引不够，后续开关 searchable 会把漏洞恢复。

## R7：现有字段删除守卫必须保留归档值

**决定**：撤回不删除 raw attrs；字段定义删除须包含归档值保护，不能因最后一个直接绑定消失就认定无存量取值。现有属性只存 key，不新增本轮未批准的字段值身份迁移；对于同 key 归档值无法证明属于另一字段的情况，保守拒绝删除，不按 key 全库 json_remove。

**理由**：错误多拦可给出原因，错误删除会丢失已明确承诺保留的历史值。精确历史 provenance 属于另一个数据模型变更，不隐式引入。

## R8：事务编排与旧 Prepared 防护

**决定**：schema 定义变更与资产效果窄接口，asset 实现，由应用组装注入；预览使用一致读事务和内存草稿，提交在单一写事务内重做规划、校验及效果落库。绑定、解绑、字段/组创建附带绑定收口，组以完整最终集合校验。

普通 Prepare 保存相关 schema 指纹，Persist 在任何写入前于当前写事务核对，不一致返回 `409 schema_stale`；覆盖新增资产和批量导入，不仅是已有资产版本。批量 Persist 共用事务快照和已核验指纹缓存。指纹包含字段身份/来源/规则、类别计算上下文、编号以及型号/厂商默认值和上下文。

**理由**：旧 Prepare 在事务外运行；即使继承变更自身原子，旧 Prepared 仍能重新写入撤回索引。版本守卫无法保护尚不存在的新资产。单独修继承服务不足以保证一致性。

**替代方案**：schema 导入 asset 会构成循环依赖；用普通 Save 传播会嵌套事务、执行无关流转行为。提交时静默重准备可能改变用户确认的导入结果，因此拒绝并要求刷新。

## R9：完整草稿与无状态确认

**决定**：沿用类别 POST/PATCH，一次保存父级、选择、编号和打印配置；增加只读预览及直接解绑预览。presence 解码区分 omitted、[]、null，null 选择非法。预览业务依赖问题返回 issues，供用户继续修正。进程内随机密钥 HMAC-SHA256 绑定规范草稿、schema、完整影响、资产身份/版本与校验数据；分页不削弱确认。

**理由**：前端多个写请求无法保证统一回滚；只签资产数量不能发现同数量不同资产的竞争；凭据不是授权，写请求仍重新校验权限及业务。

**替代方案**：预览写后回滚会占用写锁且容易触发副作用；持久化预览记录或密钥配置并无本轮需要。缺少或过时确认均零写入，前端保留草稿并重新由用户确认，不自动换 token 重试。

## R10：草稿界面与有效属性筛选

**决定**：现有新建及编辑类别入口共用继承草稿行为，shadcn Checkbox/Field 组合显示候选，受控 AlertDialog 展示撤回影响。分页保留页外选择，换父按 ID 交集保留，忽略迟到响应，编号来自草稿最终字段。所有改变废弃旧确认。字段编辑器解绑采用同等流程。

属性过滤在 SQL 分页/count 前，同时应用 raw JSON 值条件和快照推导的实际类别/设备适用范围，使用参数化集合；不在分页后剔除，也不允许归档值命中。

**理由**：只修改 CategoryEditor 会漏掉独立的新建表单；只有数量的前端解绑对话框无法处理后代影响。仅修自由文本搜索却继续以 raw attrs 过滤，会保留另一条把归档值当有效值的查询路径。

**替代方案**：加载失败视为 [] 会无声清空选择；仅按 modelID 判断字段适用性会漏掉后代拒绝继承。每行查询 schema 会引入 N+1，分页后再过滤会使计数和分页失真。

## R11：性能与验证边界

**决定**：读取快照使用常数种批量查询，在内存按类别及型号缓存解析结果；大资产集合分页扫描，预览明细分页，确认绑定完整集合而非当前页。提交保持一个写事务，不能按后代或资产分事务。

**理由**：事务外规划后直接落库会接受旧 schema；按资产提交会在中途冲突时留下部分新状态。性能通过万级数据实际测量；若失败，在计划偏离表中登记，不擅自转为异步最终一致。
