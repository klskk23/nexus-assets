# 031 万级性能验证

日期：2026-10-08。真实 SQLite 临时库，Go 1.26.2、GOMAXPROCS=2、Ryzen 9 6900HX。临时库位于 tmpfs，**不是持久磁盘 fsync 或十人并发基线**。

## 方法与执行

```sh
NEXUS_PERF=1 GOMAXPROCS=2 go test ./internal/httpapi \
  -run '^TestInheritancePerformanceAtTenThousandAssets$' \
  -count=1 -v -timeout=3m
```

最终退出 0，23.585s，日志 `/tmp/nexus-031-perf-final.log`。通过真实 Prepare/Persist 生成 10,000 台资产；4 类别、3 层、4 型号、2 厂商，含唯一、搜索、计算及真实有值的属性过滤。每项 HTTP 30 个顺序样本；p95 使用 nearest-rank，第 29 个样本。p95 辅助函数原取第28个，回归先红后绿修正。

## 发现、真红与修复

首次完整测量日志 `/tmp/nexus-031-perf.log`：首批3334恢复预览237.65s、保存231.90s；第二批恢复时10分钟超时，不能标为通过。瓶颈为 checkSchemaClaims 对每条现存claim相关扫描整批 json_each slots，**常数 SQL 不代表执行复杂度合理**。

新增 `TestSchemaClaimCheckLargePartialRestore`：真实SQLite3000条现存claim、3000个最终slot，最后一个slot故意冲突。旧查询5秒deadline失败（`/tmp/031-claims-red.log`）；改为 slots 外层 CROSS JOIN，按 live 唯一索引查找后通过（`/tmp/031-claims-green.log`），并保留最后slot冲突、批内冲突、合法交换与完整回滚回归。首批恢复保存由231.90s降至719.819ms。

`scanSchemaAssets` 同时落实单 SQL 游标、128条同步批次，Plan/Recompute共用；测试覆盖259条分为128/128/3、回调错误停止、迟发扫描错误。最终 effects/claims、重算规划仍 O(N)，不能声称整体常数内存；721.84MiB累计分配依然是实测边界。

## 保留限制

- 批量继承变更保持单写事务，阻塞写入约0.72–2.78s，取舍与后续收敛见 plan 的复杂度记录。
- 没有持久磁盘或十并发数据，不外推生产尾延迟。
- 原有万级测试也通过（`/tmp/nexus-031-basic-perf.log`），但旧 custom firmware 夹具无字段/零匹配，不拿它替代本次真实继承属性筛选证据。
- 没有异步提交、多事务拆分、放宽唯一性或降低正确性断言。
