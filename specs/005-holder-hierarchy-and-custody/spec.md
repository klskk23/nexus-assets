# Feature Specification: 持有方层级与保管责任

**Feature Branch**: `001-asset-ledger-demo`（沿用主开发分支，未另开分支）

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "前端使用流转功能，在库设备无法转移到其他位置的文案是
在库状态的持有方必须是一个位置，文案和实际行为不符合，去掉这个限制，因为实际上可能有多仓库。
签出的目标是账号时行为正确，但是当签出目标是公司/部门/位置时，还需要加入负责人选择
（默认当前账号），包括归还转移也需要可以选择负责人。持有方需要可以定义备注，
部门应该属于公司，必须要有公司才能添加部门，位置可以选择属于公司部门或者不选。
资产页面筛选加入持有方筛选。"

> **语言规范**（章程原则 V）：本规格的全部正文内容必须使用**中文**撰写。
> 仅以下内容保留英文：API 路径与参数名、字段 key、错误码 `error.code`、
> 数据库标识符。用户可见文案（UI 文本、字段 label、`error.message`）使用中文。

> **与既有规格的关系**：本规格**修订**而非取代 001–004。

| 既有需求 | 本规格的处置 |
|----------|--------------|
| 001「在库的持有方必须是位置」；004 FR-004 将其变为 `requires_location` 列 | **降级为策略** → FR-001~FR-003：出厂关闭，任何状态（含内置）可自行开关 |
| 004 FR-012 内置状态的三个行为开关不可改 | **部分取代** → FR-003：`requires_location` 改为可编辑；另外两个仍不可改 |
| 001 持有方实体有 `parent_id` 但从不校验、从不使用 | **补全** → FR-008~FR-012 |
| 001/002 流转只在「改负责人」时设置 owner | **扩展** → FR-004~FR-007 |
| 001 `GET /assets` 已支持 `holder_id` 筛选，但界面没有入口 | **补前端** → FR-013 |

> **一处需要更正的前提**：用户说「在库设备无法转移到其他位置」。
> 实测**位置到位置的转移一直是可以的**（见 research.md D1）。真正被拒绝的是
> 转移到**公司或部门** —— 而流转对话框的目标下拉把三类实体混在一起，
> 于是这条拒绝看起来像是「不能换仓库」。要去掉的限制确实存在，
> 只是它挡住的是另一件事。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把库存交给部门保管 (Priority: P1)

设备还在库，但现在由运维部保管而不是躺在某个仓库货架上。管理员用「转移」把它交给运维部，
状态不变。

**Why this priority**: 用户报告的第一个问题，且当前**完全做不到** ——
系统会以一条谈论状态的消息拒绝一次改变持有方的操作。

**Independent Test**: 对一台在库设备执行转移，目标选公司或部门，确认成功且状态仍是在库。

**Acceptance Scenarios**:

1. **Given** 一台在库设备，**When** 转移到某个部门，**Then** 成功，状态仍为在库
2. **Given** 一台在库设备，**When** 转移到另一个仓库，**Then** 成功（这一条此前也是成功的）
3. **Given** 状态管理页，**When** 查看「持有方必须是位置」一列，
   **Then** 五个内置状态都未勾选，且该勾选框可以操作
4. **Given** 管理员重新勾选「在库」的这一项，**When** 再把在库设备转移到公司，
   **Then** 被拒绝，且提示挂在**持有方**字段上，而不是状态字段上

---

### User Story 2 - 交给组织时仍然有人负责 (Priority: P2)

设备签出给「XX 集团」。集团不会接电话，所以还得有一个人是被问到的那个 ——
管理员在同一个对话框里选负责人，默认是他自己。

**Why this priority**: 目标是账号时「谁负责」自明；目标是实体时，
当前的行为是**沿用上一个负责人**，而那个人可能已经跟这台设备没有任何关系了。

**Independent Test**: 签出到一个公司并指定负责人，确认资产详情页的负责人随之变化。

**Acceptance Scenarios**:

1. **Given** 流转对话框，目标选「账号」，**Then** **不**出现负责人选择 —— 已经有答案了
2. **Given** 目标选「公司 / 位置 / 部门」，**Then** 出现负责人选择，默认当前登录账号
3. **Given** 选定负责人并提交签出，**When** 查看资产，**Then** 负责人已更新
4. **Given** 归还操作，**Then** 同样出现负责人选择 —— 归还的目标总是一个位置
5. **Given** 转移操作，**Then** 同样出现
6. **Given** 负责人选择里选「不变」，**When** 提交，**Then** 请求不携带负责人，原负责人保留
7. **Given** 已停用的账号，**Then** 不出现在负责人选项里

---

### User Story 3 - 持有方记录它自己的事 (Priority: P3)

「上海仓库」需要写明是 B 座三层、A01–A24 号货架。管理员在备注里写下来，列表上看得见。

**Why this priority**: 用户明确要求。持有方此前只有名字，而名字塞不下这些。

**Independent Test**: 建一个带备注的持有方，确认列表显示；改备注，确认更新。

**Acceptance Scenarios**:

1. **Given** 新建持有方对话框，**Then** 有备注输入框，可留空
2. **Given** 一个带备注的持有方，**When** 查看列表，**Then** 备注可见
3. **Given** 通过 API 只提交备注，**Then** 备注更新，上级与名称不受影响

---

### User Story 4 - 持有方是一棵有规则的树 (Priority: P4)

部门属于公司。管理员在没有建公司之前根本建不了部门 —— 界面直接说明原因，
而不是让他填完再被拒绝。仓库可以属于公司、属于部门，也可以什么都不属于。

**Why this priority**: 用户明确要求。`parent_id` 从 001 起就存在却从不校验，
是一个看起来能用、实际什么都不保证的字段。

**Independent Test**: 在没有公司的库里打开新建对话框，确认「部门」不可选并给出原因；
建一个公司后再试，确认可选且必须选上级。

**Acceptance Scenarios**:

1. **Given** 库中没有公司，**When** 打开新建持有方，**Then** 「部门」选项禁用并说明原因
2. **Given** 库中有公司，**When** 选择类型「部门」，**Then** 上级必填，选项只有公司
3. **Given** 类型「部门」且未选上级，**Then** 提交按钮不可用
4. **Given** 类型「位置」，**Then** 上级可选，选项含公司与部门，另有「无上级」
5. **Given** 类型「公司」，**Then** 不出现上级选择
6. **Given** 通过 API 直接提交一个无上级的部门，**Then** 422，消息挂在 `parent_id` 上
7. **Given** 把某个部门移到它自己的下级位置之下，**Then** 拒绝 —— 成环会让树无法遍历
8. **Given** 升级前就存在的、没有上级的部门，**Then** 保持原样，不被迁移强行安一个公司

---

### User Story 5 - 按持有方筛资产 (Priority: P5)

「XX 集团那边现在有哪些设备？」管理员在资产页选一下持有方就能看到。

**Independent Test**: 选中某个持有方，确认列表与导出链接都带上了它。

**Acceptance Scenarios**:

1. **Given** 资产页筛选栏，**Then** 有持有方下拉，默认「全部持有方」
2. **Given** 选中一个持有方，**Then** 列表只显示它持有的设备
3. **Given** 同上，**When** 点导出，**Then** 导出链接同样带上该筛选

## Requirements *(mandatory)*

### 位置约束降级为策略

- **FR-001**: `requires_location` MUST 对全部内置状态出厂关闭。
- **FR-002**: 该开关 MUST 对任何状态可编辑，包括内置状态，并在状态管理页可见可操作。
- **FR-003**: `counts_as_available` 与 `terminal` 对内置状态 MUST 仍不可改。
  三者的区别是：只有持有方校验读第一个，而后两个被概览与转换矩阵依赖。
- **FR-004**: 该约束触发的拒绝 MUST 挂在 `to_holder_id` 上，MUST NOT 挂在 `to_status` 上。

### 保管责任

- **FR-005**: 目标是实体（公司 / 部门 / 位置）的签出与转移 MUST 提供负责人选择，
  默认当前登录账号。
- **FR-006**: 归还 MUST 同样提供 —— 它的目标总是默认库存点，也是一个实体。
- **FR-007**: 目标是账号的签出 MUST NOT 提供负责人选择。
- **FR-008**: 负责人选择 MUST 提供「不变」，且 MUST 只列出启用中的账号。

### 持有方

- **FR-009**: 持有方 MUST 有备注字段，可留空，列表可见。
- **FR-010**: 部门 MUST 有上级，且上级 MUST 是公司。
- **FR-011**: 位置的上级 MUST 可选，且 MUST 是公司或部门。
- **FR-012**: 公司 MUST NOT 有上级。
- **FR-013**: 移动持有方 MUST 拒绝成环。
- **FR-014**: 新建界面 MUST 只提供合法的上级选项；当部门不可能合法时（库中无公司），
  该类型 MUST 呈现为禁用并说明原因，MUST NOT 从列表中消失。
- **FR-015**: 迁移 MUST NOT 为存量的无上级部门补一个公司。

### 筛选

- **FR-016**: 资产页 MUST 有持有方筛选，并 MUST 与 `holder_type=entity` 一同提交。
- **FR-017**: 导出链接 MUST 携带该筛选。

## Success Criteria *(mandatory)*

- **SC-001**: 一台在库设备可以被交给公司、部门或任意仓库，全程无需改状态。
- **SC-002**: 交给实体之后，资产详情页上的负责人是本次操作指定的那个人。
- **SC-003**: 在没有公司的库里，无法通过界面或 API 建出一个部门。
- **SC-004**: 位置约束重新打开后，001 起的原行为逐条恢复。
- **SC-005**: 全部变更后 `nexus verify` 仍然全绿。

## Assumptions

- **不做多级公司**。用户说「部门应该属于公司」，没有说公司可以属于公司。
  集团 / 子公司结构留到有人真的需要时再谈；现在加会让上级选择多一层没人用的递归。
- **迁移不回填 `parent_id`**。存量部门没有公司可指，编一个比留空更糟。
  规则对此后写入的数据生效。
- **持有方不做「编辑」对话框**。备注与上级通过 API 可改，界面本轮只在新建时提供 ——
  用户要求的是「可以定义备注」，行内编辑是另一个故事，不做也不留半成品入口。
