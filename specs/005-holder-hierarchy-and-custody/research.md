# Phase 0 Research: 持有方层级与保管责任

本文记录 6 项实现级决策。

---

## D1：报告的现象与实际的原因不是一回事

**报告**：「在库设备无法转移到其他位置……因为实际上可能有多仓库。」

**实测**（对着跑起来的服务）：

| 操作 | 结果 |
| --- | --- |
| 在库设备 → 另一个仓库 | **成功**，`kind=transfer`，状态仍是 `in_stock` |
| 在库设备 → 公司 | 拒绝：`illegal_transition` / 「在库状态的持有方必须是一个位置」 |
| 在库设备 → 部门 | 同上 |

多仓库一直是可以的。真正被挡住的是把库存交给**公司或部门**保管，
而流转对话框的目标下拉标着「公司 / 位置 / 部门」，三类混在一起 ——
所以这条拒绝在使用者那里看起来就是「不能换仓库」。

**决定**：按用户的实际诉求去掉限制，但在文档里说清楚它挡住的是什么。
如果照着「多仓库」的说法去修，会去改一个没有坏的地方。

**顺带**：拒绝被挂在 `to_status` 字段上，而操作者动的是持有方。
这就是「文案和实际行为不符合」的另一半，见 D2。

## D2：位置约束是规则还是策略

**问题**：004 把「在库必须放位置」变成了 `requires_location` 列，
并把内置状态的三个开关锁死，理由是「系统其他部分依赖它们」。现在要去掉其中一个，
那条理由还成立吗？

**核对**：`requires_location` 的读取点只有两处 —— `asset.ValidateHolderForStatus`
与 `transfer.checkHolderForStatus`，两者都是这条约束本身。
没有第三方依赖它。`counts_as_available` 被概览的类别分布读，
`terminal` 被转换矩阵读 —— 那两个的理由仍然成立。

**决定**：`requires_location` 降级为**策略**，对任何状态可编辑；另外两个保持锁定。

**为什么不直接删掉这一列**：一个自定义状态可能真的想要它（「在维修站」必须是位置）。
删掉是不可逆的，关掉是可逆的，而且状态管理页上看得见。
迁移里静默翻一个标志位、界面上没有任何痕迹，才是更糟的做法。

## D3：拒绝挂在哪个字段上

**问题**：持有方类型的拒绝以前靠在错误文本里找「位置」两个字来识别，然后报到 `to_status`。

**决定**：给它一个哨兵 `transfer.ErrHolderKind`，报到 `to_holder_id`，
并把「位置」从 `isTransitionError` 的关键词表里删掉。

**理由**：字符串嗅探决定字段归属，本身就是这个 bug 的成因。哨兵是这个仓库里
其他每一条可操作拒绝的做法（`ErrStatusInvalid`、`ErrCategoryHasAssets`…）。

**没有做的事**：`isTransitionError` 剩下的四个关键词仍然是字符串匹配。
把它们全部换成哨兵是对的，但不属于这一轮 —— 本轮只动了会误导的那一条。

## D4：负责人在哪些操作里出现

**问题**：用户说「签出目标是公司/部门/位置时需要负责人，包括归还转移」。

**决定**：

| 操作 | 目标 | 是否询问 |
| --- | --- | --- |
| 签出 | 账号 | 否 —— 拿着设备的人就是答案 |
| 签出 | 实体 | 是 |
| 转移 | 账号 | 否 |
| 转移 | 实体 | 是 |
| 归还 | （总是默认库存点） | 是 |
| 改负责人 | — | 本来就是 |
| 改状态 | — | 否 —— 持有方没动 |

默认当前登录账号；另有「不变」，因为仓库到仓库的调拨不见得要换责任人。

**为什么归还也问**：归还的目标是默认库存点，一个位置。设备回到货架上之后
「找谁问」这个问题不会消失，只是答案不再是上一个使用者。

## D5：层级规则写成数据

**决定**：`allowedParents` 是一张 `map[EntityType][]EntityType`，前后端各一份。

```
company    → 无上级
department → 公司
location   → 公司 或 部门（可空）
```

**理由**：写成 if 链的话，加第四种持有方要改三处分支（校验、表单选项、必填判定）。
写成表则是一行。前端那份不是为了替服务端把关 —— 服务端仍然校验 ——
而是为了让表单**只提供合法选项**，而不是让人填完再拒绝。

**成环检查**单独做：类型规则允许「位置在部门下」和「部门在公司下」，
但移动时仍可能构造出环，而环会让祖先遍历不终止。

## D6：迁移不回填 `parent_id`

**问题**：升级前建的部门没有公司。迁移要不要给它们造一个？

**决定**：不。规则对此后写入的数据生效，存量的无上级部门原样保留。

**理由**：造出来的「默认公司」是一条谁也没同意过的数据，而且它会立刻出现在
每一个持有方下拉里。留空的代价是这些部门暂时不符合新规则 ——
但它们本来就不符合，掩盖这一点不会让它变好。

`ALTER TABLE ADD COLUMN` 与一条 `UPDATE` 就是这次迁移的全部，
没有表重建，Down 完整可逆（SQLite 3.35+ 支持 `DROP COLUMN`，实测环境为 3.53）。
