# 快速开始：持有方层级与保管责任

**Feature**: 005-holder-hierarchy-and-custody | **Date**: 2026-08-31

环境准备与开发流程沿用 [001 的 quickstart](../../001-asset-ledger-demo/quickstart.md)。
本文只讲**本轮有什么不一样**。

## 升级已有数据库

```bash
./nexus            # 启动时自动跑 migrations/005_holder_hierarchy.sql
```

迁移做三件事：`holder_entities` 加 `note` 列、加 `parent_id` 索引，
并把「在库」的「持有方必须是位置」开关关掉。**不动任何既有数据**，Down 完整可逆。

升级后立刻可见的变化：在库设备可以直接转移给公司或部门。

## 建持有方的顺序

现在有顺序了：

```
公司  →  部门（必须先有公司）
      ↘  位置（可以挂在公司或部门下，也可以不挂）
```

没有公司时，新建对话框里的「部门」是**禁用**的，下面写着原因。
这比让它从列表里消失好 —— 「为什么没有部门」是个更难回答的问题。

## 「在库必须放在位置」去哪了

它还在，只是默认关了。`/statuses` 页面上多了一列勾选框，
任何状态都可以自己决定要不要这条约束，内置的五个也可以。

想恢复 001 起的原行为，把「在库」那一行勾上即可。勾上之后，
把在库设备交给公司会被拒绝 —— 而且提示挂在**持有方**那一栏，不再是状态栏。

## 交给组织时的负责人

流转对话框里，目标选「公司 / 位置 / 部门」会多出一个负责人选择，默认是你自己。
选「账号」时不会出现 —— 拿着设备的人就是答案。

归还也会问：设备回到货架上，「找谁问」这个问题不会消失。

不想改责任人时选「不变」，请求就不带这个字段。

## 排错

**建部门报 422，说要先建公司** —— 就是字面意思，先建一个公司。

**改了备注，上级没了** —— 不该发生。`parent_id` 字段缺席表示「不动」，
显式的 JSON `null` 才表示「脱离上级」。如果真的看到，是 `handlers_metadata.go`
里 `RawMessage` 那段被改回了 `**string`。

**转移被拒绝，说持有方必须是位置** —— 有人把该状态的位置约束勾上了。
去 `/statuses` 看那一列。
