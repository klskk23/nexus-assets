# 调研：类别页主从两栏与骨架

五个问题。前两个决定服务端形状，第三个决定路由，后两个决定抽象的边界。

---

## 一、每节点的设备数从哪来

**结论：服务端返回**每个类别的子树合计**，而概览的根类别数字改为读同一张表里的根条目。**

三条路都试着推演过：

| | 做法 | 为什么否 |
|---|---|---|
| 甲 | 在 `Category` 上加 `asset_count` | 类别对象出现在十几个下拉里。给每一次读类别都挂上一次计数，是为一个页面的需要向全系统收税；而且 `Category` 是打印服务解析的对象，往里加字段要考虑对面 |
| 乙 | 前端拿「每类别直挂数」自己按树累加 | 累加规则会同时存在于 Go 与 TS 两份。**FR-007 要求两处永远相等，而两份实现只能靠纪律相等** |
| **丙** | **服务端算好子树合计，概览与类别页读同一份** | 选它 |

**丙的关键不是「共用一个函数」，是「共用同一组数」。**

共用函数仍然可以漂移 —— 概览今天在 `overview.go` 里自己做根节点归并
（`roots[ids[0]].Count += n`），如果只是把计数抽成函数、归并各做各的，两处照样能得出
不同的数。所以做法是：**算出全部类别的子树合计，概览的根类别数字就是这份结果里
根类别的那几条**。两处不是「口径一致」，是**同一个数字被读了两次**，构造上不可能不等。

口径沿用现有的：含子树、排除 `counts_as_available = 0` 的状态（今天只有已报废）。
这不是新定的规矩，是概览已经在用的那一条。

**端点**：`GET /categories/counts` → `{"<category_id>": n, ...}`。
不带筛选、不分页 —— 它回答的是「每个类别多少台」，类别数量本身就是一屏到几十的量级
（规格的 Assumptions 已把这条写死）。**读默认全开放**，与 `/categories` 一致。

## 二、子树合计怎么算

现有 `availableByCategory` 返回的是**直挂**数（`GROUP BY category_id`）。子树合计要把
每个类别的数加到它自己以及全部祖先上。

`categories.path` 是 `/root/child/` 形式，`schema.AncestorIDs(path)` 已经存在且
`overview.go` 正在用它取链首（`ids[0]`）。子树合计只是把「加给链首」换成「加给链上每一个」：

```
for id, n := range direct {
    for _, anc := range AncestorIDs(pathByID[id]) { subtree[anc] += n }
}
```

**`AncestorIDs` 的返回值包含类别自己**（函数注释：「root first, including the category
itself」）。所以上面这个循环已经同时加给了自己与全部祖先 —— **不要再 `append(..., id)`**。
这份调研的初稿就是这么写的，会让每个类别把自己算两遍；叶子类别翻倍，而根类别因为
本来就在链上、看起来还「差不多对」，是最难从数字上看出来的那种错。

**在内存里做，不写递归 SQL。** 类别是配置不是数据，全量取出来是几十行；
SQLite 的递归 CTE 能写，但会把一段人人都要读懂的归并逻辑变成一段人人都要重读的 SQL，
而它没有换来任何东西。

**必须有测试的两处**（都是读代码看不出来的）：
1. **根类别把自己直挂的设备算进去了** —— 上面那个「加两遍」的错，反过来写就是「漏算自己」。
2. **多层链上每一层都只加一次** —— 三层树，叶子放一台，根、中、叶三处都应是 1。

## 三、`/categories/:id` 是子路由还是路由参数

**结论：同一个组件挂两条路径，读 `useParams`。不用 `<Outlet />`。**

022 把 `/assets/:id` 做成**顶层路由**、`Assets.tsx` 里没有 `Outlet`，理由是详情是一整页，
列表不需要活在它背后。类别页正相反：**左栏必须一直在**，切换类别时只换右栏。

若用父子路由 + `Outlet`，左栏活在父路由里、右栏活在子路由里，那么「没选中任何类别」
（`/categories`）与「选中了」（`/categories/:id`）会是两个不同的组件树，而它们要共享
搜索词、树数据与选中态。**共享状态跨越路由边界正是 016 决策 107 警告的那种形状。**

所以：

```
{ path: "categories",     Component: Categories }
{ path: "categories/:id", Component: Categories }
```

一个组件，`useParams().id` 为空就是「未选中」。FR-021 的自动选中第一个根类别用
`<Navigate replace>` 完成 —— **`replace` 而不是 push**：自动跳转不是用户去过的地方，
push 会让「后退」退回一个立刻又把自己跳走的地址，形成退不出去的循环。

## 四、骨架拿什么，不拿什么

**结论：一个布局组件 + 一个选中钩子，不是一个万能组件。**

最容易犯的错是做一个 `<MasterDetailPage items renderRow renderDetail onSelect ...>`。
那正是 `CrudPage` 的形状，而 `web-tables.md` 已经写下它的代价：
「它会长出『没有新建按钮』『勾选列』『树』三个特例开关」。**渲染回调是伪装成参数的分支** ——
每多一个调用方就多一个回调，最后骨架变成一张所有调用方需求的并集清单。

拆成两件：

- **`MasterDetail`（布局）**：两栏栅格、各自滚动、窄屏塌一栏。
  只有一个与内容有关的入参：`selected: boolean` —— **窄屏时要知道该显示哪一栏**。
  它不知道条目是什么、有几个、怎么排。左右两栏的内容以 `children` 形式传进来。
- **`useMasterSelection`（行为）**：从地址读当前选中、未选中时给出「该跳到哪一条」。
  它只要一个 `ids: string[]` 与当前 `id`，**不碰条目本身长什么样**。

判据（FR-018）：**骨架里不允许出现「类别」「树」「计数」这三个词。** 这是一条可以被
测试的、语法层面的约束，而不是一个见仁见智的评价。

**本轮不做的**：不加「左栏宽度」参数（一个调用方，写死 300px，第二个来了再说）、
不加空状态插槽（左右两栏的空状态是内容，由调用页自己画）、不加键盘上下键移动选中
（没人要求，且树与列表的键盘语义不同，现在定会定错）。

**第二个调用方进来时最可能要改的是什么** —— 诚实地写下来：左栏宽度。
若那时它需要不同的宽度，加一个参数是十行改动，且不影响任何既有行为。
这是可接受的，因为它是**形状**参数，不是内容参数。

## 五、有没有该用而没用的 shadcn 组件

**结论：没有新组件，也没有新依赖。**

章程要求组件必须来自 shadcn/ui。逐个核对本轮要画的东西：

| 要画的 | 用什么 | 说明 |
|---|---|---|
| 两栏栅格、滚动容器 | Tailwind 类 | 布局不是组件。`AppShell` 的两栏也是这么写的 |
| 左栏搜索框 | 现有 `ListToolbar` 或 `Input` | 搜索框已有；但 `ListToolbar` 是为表格页工具条设计的（带筛选插槽），左栏只需要一个输入框 |
| 树的行 | `Button`（`asChild` 包 `Link`） | 与侧栏导航同一形状：行本身就是可点击控件 |
| 右栏属性带 | 现有写法 | 资产详情页的属性块已是既成写法（`--card`） |
| 右栏字段表 | `Table` | 与全站一致 |
| 「修改」禁用态 | `Button` + `deniedReason` | 既有做法 |

**唯一需要判断的是搜索框**：`ListToolbar` 假定自己在表格上方、占满宽度、可带筛选控件。
左栏 300px 宽、没有筛选。**用 `Input` 直接画，不套 `ListToolbar`** —— 把一个为
另一种位置设计的部件塞进来，就是把它的假定一起塞进来。

## 附：本轮不碰的东西，以及为什么要写下来

- **类别停用**：`categories.archived_at` 有列、`categoryCols` 里也在扫，但**没有任何代码写过它**。
  它是个从没接上的挂钩。接上它意味着新端点 + 守卫 + 每一处列类别的地方
  （录入、导入、筛选、树、下拉）都要决定要不要过滤 —— 漏一处就是静默 bug。
  规格 FR-025 已排除，这里记下它为什么看起来「只差一点」却不是。
- **字段组**：016 决策 105 不动。绑定表上没有组这一列，「这个类别引了哪几个组」
  数据库答不出来。
- **解绑**：v6 决策 72 不动。
