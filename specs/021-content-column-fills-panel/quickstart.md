# 实机走查：内容列铺满面板

这一轮的验收是**一组像素**，而像素只有在真实布局里才存在 ——
jsdom 不做布局，`getBoundingClientRect()` 恒返回 0。所以走查不是补充，**它就是验收**。

```
CGO_ENABLED=0 go build -o /tmp/nexus ./cmd/nexus
NEXUS_JWT_SECRET=... NEXUS_ADMIN_EMAIL=... NEXUS_ADMIN_PASSWORD=... \
NEXUS_ALLOWED_EMAIL_DOMAINS=example.com NEXUS_DB_PATH=/tmp/qs.db /tmp/nexus seed 60
```

> 二进制里 embed 的是 `web/dist`。**改了前端一定要先 `npm --prefix web run build` 再
> `go build`**，否则跑的还是上一版界面 —— 本轮踩过一次：走查实例是旧二进制，
> 三张对比图只能靠注入 CSS 才成立。
> 不想动现有实例就换端口：`NEXUS_ADDR=:8819`。

## 0. 先跑脚本

```sh
NEXUS_URL=http://localhost:8819 node specs/020-fluid-content-column/measure.mjs
```

脚本住在 020 的目录里 —— **同一条规则的同一个探针，不分叉成两份**。它已改写为本轮的断言：
量八档窗口的留白与右缘距离，**不通过就退出码 1**。

**通过时的读数**：

| 视口 | 版式 | 包含块 | 内容列 | 留白 | 距屏幕右缘 |
|---|---|---|---|---|---|
| 3840 | 桌面 | 3484 | 3484 | 0 | 52 |
| 2560 | 桌面 | 2204 | 2204 | 0 | 52 |
| 1920 | 桌面 | 1564 | 1564 | 0 | 52 |
| 1440 | 桌面 | 1084 | 1084 | 0 | 52 |
| 1366 | 桌面 | 1010 | 1010 | 0 | 52 |
| 1280 | 桌面 | 924 | 924 | 0 | 52 |
| 700 | 移动 | 660 | 660 | 0 | **20** |
| 390 | 移动 | 350 | 350 | 0 | **20** |

**52 = 40（面板 `pr-10`）+ 12（井槽 `p-3`）**，不是新设的常量。

**移动版式是 20，不是 52**：`md` 以下面板去掉圆角与井槽（`max-md:p-0`）、
内边距改 `max-md:p-5`。**分档的是常数，不是规则** —— 留白为 0 在八档里都成立。
规格 FR-002 / FR-002a 是分开写的，因为「恒定 52px」不限定断点就是一句假话。

**1. 双向验证（这一步不能省）。**

给 `AppShell` 内容列那个 `div` 加回**任何**宽度类 —— `w-[min(100%,max(960px,76%))]`、
`max-w-[960px]`、`max-w-4xl` 都行 —— 重新构建，重跑脚本，**必须全部报错**。
去掉，重新构建，**必须全部通过**。

一条只见过它通过的版面断言，不构成任何证据。（SC-003）

参考：贴回 020 的规则时，桌面五档留白分别是 836 / 529 / 375 / 124 / 50px。
**最小的偏差是容差的 50 倍**，所以 1px 容差不掩盖任何真实规则。

**2. 窄屏：宽度会变，别的都不能变。**

1440 / 1366 / 1280 三档打开全部路由，与 020 的截图逐张对。

- **内容列应当更宽**（1440 下 960 → 1084）—— 这是预期，**不是回归**，不要改回去
- **其余必须逐像素相同**：字号、行高、圆角、间距、控件高度、表格行高 48px
- 表格在自己的框内横向滚动；**页面本身不出现横向滚动条**（SC-007）
- 对话框仍按各自的 `sm:max-w-*` 收口，不受本轮影响

020 承诺过「≤1548 与 018 逐像素一致」，**本轮明确作废这条承诺**。

**3. 右边缘的收边。**

2560 下打开资产页，量右上角 `Export CSV` / `Add device` 到面板右缘的距离 —— 应为 40px，
与左侧的 56px 读作同一套收边。

> **不要用「会不会切进圆角」当理由。** 调研里 C 变体（右内边距 12px）最初就是这样被
> 否掉的，而实测推翻了它：按钮距面板上缘 46px，圆角方框只占上缘 28px，
> 两种内边距下都进不去。C 该否的真实理由是 56 : 12 读作没对齐，以及贴那么近本身局促。（US2）

**4. 一条规则，一处都没有。**

```sh
grep -rn "max-w-" web/src/routes web/src/features --include='*.tsx' | grep -v "sm:max-w-"
```

命中集合必须恰为白名单两项（搜索框的 640、备注列的截断宽度）。
`AppShell` 里**不应有任何宽度类**。

```sh
npm --prefix web test -- --run --maxWorkers=4 tests/contentColumn.test.ts
```

> **这条测试现在是唯一拦截。** 018 与 020 时期 `AppShell` 里还有一个数字，
> 漏进来的 `max-w-` 会与它打架、版面明显出错、人能看见。
> 现在没有数字可抵消了，漏进来的 `max-w-` 会直接生效，
> 而且看起来像是有人特意收窄了这一页，不像 bug。（NFR-001）

**5. 服务端零改动，且本轮没有新增文案。**

```sh
git diff --stat main -- internal/ cmd/                    # 必须为空（SC-004）
git show --stat --format="" 6ca7139 -- web/src/i18n/      # 必须为空（FR-010）
git diff --stat 6ca7139 -- web/src/i18n/                  # 必须为空（FR-010）
```

FR-010 说「本轮新增文案为零」—— 那不是一句形容，是一条能跑的检查。

> **基线要选对，否则这条检查会一直假红。** FR-010 的范围是**本轮**，
> 基线是 021 的实现提交 `6ca7139`，不是 `main` —— `main` 在 50 个提交之前，
> 对它 diff 会显示 `zh.ts` 改了 36 行，那些是 017/018/020 的工作。
> SC-004 反过来：服务端**跨全部 50 个提交**对 `main` 都是零 diff，所以那条用 `main` 更强。

**6. 全量测试与静态检查。**

```sh
npm --prefix web test -- --run --maxWorkers=4
npm --prefix web run lint
npx --prefix web tsc --noEmit -p web/tsconfig.json
```

**一定要加 `--maxWorkers=4`。** 默认并发会把这台机器的负载打到 80，
worker 互相饿死后集体 45 秒超时，看起来像十几个测试同时坏了。

> **ESLint 会扫到 design-sync 生成的目录。** `web/.ds-types`、`web/.ds-css`、
> `web/ds-src`、`web/index.d.ts` 四处都是生成的、都已 gitignore，但 gitignore 不等于
> eslintignore —— 它们已加进 `eslint.config.js` 的 `ignores`。
> 如果哪天 lint 又报出 `.d.ts` 里的 `any`，先看是不是又多了一个生成目录，
> 而不是去改那个文件。

**7. 文档不能与代码相反。**

```sh
grep -rn "76%\|min(100%,max(960px" docs/ web/src CLAUDE.md --include='*.md' --include='*.tsx'
```

只应命中 `docs/rules/web-tables.md` 的**历史对照表** —— 那是有意保留的上下文，
用来解释同一条规则为什么改了三次。任何其他命中都是没同步干净的文档。（SC-006）
