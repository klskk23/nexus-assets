# 实施计划：内容列铺满面板

**分支**：`021-content-column-fills-panel` ｜ **规格**：[spec.md](./spec.md) ｜ **决策**：135

> **本轮是追认。** 代码已在 `6ca7139` 落地并双向验证。本计划记录的是**已做出的技术选择
> 及其理由**，以及补规格时剩下的复核工作。阶段二写成「已执行」而非「将执行」。

## 概要

删掉内容列 `div` 上的宽度类，不换成别的。留白由面板自己的内边距承担。
**服务端零改动，字号行高圆角间距一律不动，本轮新增文案为零。**

调研（[research.md](./research.md)）把这一轮缩到极小，也定下了两个不能省的判断：

1. **右内边距必须留 40px**，不能压到井槽的 12px —— 理由是左右差（56 : 12 读作没对齐），
   **不是圆角**：实测按钮距面板顶 46px，两种内边距下都清开 28px 弧线
2. **960 地板一起去掉**，否则规则会退化成「宽屏铺满、窄屏 960」，又出现一个只在两档
   生效的隐形数字，而那正是 018 与 020 各自栽过的形状

## 技术背景

沿用既有技术栈。**零依赖变动、零新组件、零新文案、零新常量**
（52px 是既有的 40 + 12，不是新设的值）。

| | |
|---|---|
| 前端 | React 19 · Vite 6 · Tailwind v4 · shadcn/ui |
| 服务端 | **一行不动**（SC-004 把这条写成验收标准，已核实 `internal/` `cmd/` 无 diff） |
| 令牌 | `index.css` 一个字不改 |
| 测试 | 现有 375 例全过；本轮更新 1 例的文档注释，断言未变 |

**没有 NEEDS CLARIFICATION。** 六条裁定由开发者看过 2560 三档截图后逐条决断。

## Complexity Tracking（章程偏离登记）

| 违反项 | 必需性理由 | 被拒绝的更简方案 |
|---|---|---|
| **原则二**：「任何触及 UI 的变更必须新增或更新至少一条 DOM 测试」。本轮更新的是**源码不变量测试**（`tests/contentColumn.test.ts`）的文档，其断言未变，且它不是 DOM 测试 | **本轮的改动在 jsdom 里没有任何可观察行为。** jsdom 不做布局，`getBoundingClientRect()` 恒返回 0，任何关于宽度的断言都会无视 CSS 恒真。真正的验收是 `measure.mjs`，在真实浏览器里量，**双向验证过**（贴回旧规则五档全红，去掉后五档全过） | **写一条断言类名的 DOM 测试**：它看起来满足条文，实际什么也不守 —— 而且本轮尤其荒谬，因为**要断言的恰恰是「没有类名」**，那样的测试会在任何人加回任何宽度类时依然通过。018 的概览页测试就是这类假测试的实例 |

**与 020 的登记同因**，但本轮多一层理由：这次连可断言的类名都不存在了。
NFR-001 因此把 `contentColumn.test.ts` 的地位单独写进规格 —— 它现在是唯一拦截。

## 风险

| 风险 | 应对 |
|---|---|
| **有人把 1440 下变宽当成回归修回去** | 规格 US3 与走查第 2 步都写明「宽度应当不同，其余逐像素相同」；020 的「窄屏零回归」承诺已明确作废并写进被取代横幅 |
| **有人把导入页那张空卡当缺陷修掉** | 规格「不在范围内」首条明确裁定：导入页只是 demo、后续大改，**不要为此加任何控件或宽度上限** |
| **`max-w-` 悄悄复辟且无人察觉** | `AppShell` 里已无数字与之抵消，漏进来会直接生效且看起来像有意收窄。NFR-001 把这条测试的地位写进规格；`contentColumn.test.ts` 已双向验证（加一条 `max-w-` 立刻报出文件名） |
| **实测脚本被改回代理指标** | research 问题四写明为什么不用代理；脚本头部注释记录了断言变更的日期与原因 |
| **文档留下与代码相反的数字** | FR-011/FR-012、SC-006 三条写成验收标准；收口时全仓 grep 过 `76%` 与 `min(100%,max(960px`，只剩历史对照表 |
| **半成品被误发布** | 017+018+020 的提交仍未推，021 在其上继续；中途不打 tag、不合 main、不推送 |
