# 规格：内容列铺满面板

**分支**：`021-content-column-fills-panel` ｜ **决策**：135
**推翻**：020 的 FR-001（76% 比例）、FR-004（960 地板）、SC-001（留白恒占 24%）、SC-002（≤1548 与 018 逐像素一致）

> **本轮是追认。** 代码已在提交 `6ca7139` 实现，双向验证通过，375 个前端测试全过。
> 这份规格记录的是**已经成立的事实**与做出它的理由，不是待办。任务清单里的实施项因此
> 标注为「已完成，附证据」；本轮真正剩下的工作是复核与文档收口。
> 之所以仍然补规格：这是同一条规则的第三次修订，而前两次的规格是唯一能解释
> 「为什么又改了」的东西。少一版，下一个人就只能从 git log 里猜。

## 概要

内容列那个 `div` 上**一个宽度类都没有**。块级元素本来就等于容器宽度，所以规则不是
「铺满」这个新数字，而是**不再有数字**。内容与屏幕右缘之间只剩面板自己的内边距。

同一个问题问了三遍，这是第一个不含数字的答案：

| | 规则 | 2560 下右边留白 | 毛病 |
|---|---|---|---|
| 018 | 固定 `960px` 上限 | 1244px | 留白随窗口**无界生长**：1440 下占面板 11%，3840 下 72% |
| 020 | 比例流动 `76%` | 581px | 生长治住了（恒 24%），**留白本身没治** |
| **021** | **无** | **0** | —— |

**020 的指标完全达成，目标完全没达成。** 留白占比确实锁死在 24%，`measure.mjs`
双向验证过，规格与调研都自洽 —— 然后开发者在 27 寸 1440p 上打开页面，说「感觉右边
留白感还是不对」。

原因是诊断只做了一半。018 的观察是「留白**随窗口长大**」，那是真的；由此推出的指标是
「让占比恒定」，而恒定的 24% 在 2560 上仍是 581px 的空白，页面读起来像没加载完，
而不是像被排版过。**一个从半个诊断里推出来的指标，可以在完全达标的同时完全跑偏。**

这一条比版面本身更值得记住，已同时记入
`docs/design/organic-layout/README.md` 第四处。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 宽屏上没有那片空白（Priority: P1）

管理员在 27 寸 1440p（2560×1440）上打开任意一页。内容从面板左缘一直铺到右缘，
右上角的操作按钮就在屏幕右侧该在的位置，页面右半边不再有一整块什么都没有的区域。

**为什么是 P1**：这是本轮唯一的动因。020 之后仍然存在的正是这个问题。

**独立测试**：在 2560 下打开概览与资产页，量内容列右缘到屏幕的距离 —— 应为 52px，
而不是 581px。

**验收场景**

1. **Given** 2560 宽的窗口，**When** 打开资产页，**Then** 内容列宽度等于面板内容盒宽度，留白为 0
2. **Given** 3840 宽的窗口，**When** 打开同一页，**Then** 留白仍为 0，右缘距屏幕仍为 52px
3. **Given** 任意受支持宽度，**When** 量内容右缘到屏幕的距离，**Then** 该值恒定，不随窗口变化

### User Story 2 - 右边缘留得住（Priority: P1）

内容不是贴死到面板边界，而是停在面板自己的内边距上，左右两侧的差读得出是有意的。

**为什么是 P1**：与 US1 是同一次改动的两面。只做 US1 不做这条，就会得到内容贴死在
面板边界上的版面 —— 草案 C 的截图已经排除过。

**独立测试**：在 2560 下量右内边距为 40px，且与左侧 56px 读作同一套收边。

**验收场景**

1. **Given** 任意宽度，**When** 量内容右缘到屏幕，**Then** 为 40px（面板 `pr-10`）+ 12px（井槽）= 52px
2. **Given** 右上角有操作按钮的页面，**When** 量按钮到面板右缘与上缘的距离，**Then** 至少一个方向 ≥ 圆角半径（实测右 40 / 上 46，半径 28），按钮不进入圆角方框
3. **Given** 左内边距 56px、右内边距 40px，**When** 观察整体，**Then** 这点差读作有意的收边，而非未对齐

### User Story 3 - 窄屏只变宽度，别的什么都不变（Priority: P1）

笔记本（1440 / 1366 / 1280）上内容列比 018 与 020 更宽 —— 1440 下从 960 变成 1084。
**这是预期变化，不是回归。** 要保证的是：除了宽度，其余一切不动。

**为什么是 P1**：020 承诺过「≤1548 与 018 逐像素一致」，本轮明确作废这条承诺。
承诺作废必须写明，否则下一个人会把变宽当成 bug 修回去。

**独立测试**：1440 / 1366 / 1280 三档打开全部路由，与 020 的截图逐张对：宽度应当不同，
其余（字号、行高、圆角、间距、控件尺寸）应当逐像素相同。

**验收场景**

1. **Given** 1440 宽的窗口，**When** 打开资产页，**Then** 内容列为 1084px（面板内容盒宽度），不是 960
2. **Given** 同一窗口，**When** 对比 020 的截图，**Then** 字号、行高、圆角、间距、控件高度均无变化
3. **Given** 任意窄档，**When** 打开列过多的表格，**Then** 表格在自己的框内横向滚动，页面本身不出现横向滚动条

### User Story 4 - 规则只有一处，而且已经没有数字了（Priority: P2）

全站没有任何一处内容列宽度声明。控件自己的宽度（搜索框、备注列截断）不受影响。

**为什么是 P2**：不影响观感，影响的是这条规则能不能活过下一次改动。

**独立测试**：`tests/contentColumn.test.ts` 的 `max-w-` 命中集合等于白名单。

**验收场景**

1. **Given** `routes/` 与 `features/` 下全部源码，**When** 搜 `max-w-`（不含 `sm:` 前缀的对话框上限），**Then** 命中集合恰为白名单两项
2. **Given** 有人给某页加了 `max-w-*`，**When** 跑测试，**Then** 报出文件名并失败
3. **Given** `AppShell`，**When** 读内容列那个 `div`，**Then** 上面没有任何宽度类

### Edge Cases

- **面板比内容窄**：内容列等于面板，表格靠自己的框横向滚动，页面不产生横向滚动条。
- **移动端**（`max-md`）：面板去掉圆角与井槽，内边距变 `p-5`；内容列仍等于面板 ——
  **规则不分档，只有右缘常数分档**（52 → 20）。见 FR-002a / SC-002a。
- **对话框与抽屉**：它们不在内容列里，各自的 `sm:max-w-*` 不受影响，也不该受影响。
- **超宽屏（3840 及以上）**：不封顶。天花板只是把 018 的失效模式往外挪。
- **列极多的表格**：列被拉开而不是提前结束 —— 见「已接受的代价」。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：内容列的宽度必须**完全由容器决定**。承载它的元素上不得有任何宽度声明
  （`width`、`max-width`、`min-width` 及其等价工具类）。**取代 020 的 FR-001。**
- **FR-002**：在**桌面版式**（`md` 断点及以上，面板带圆角与井槽）下，内容与屏幕右缘之间的
  距离必须**恒定且与窗口宽度无关**，其值为面板右内边距加外层井槽，实测 52px。
- **FR-002a**：在**移动版式**（`md` 以下）下，面板去掉圆角与井槽、内边距改为 20px，
  右缘距离因此为 20px。**这不是 FR-002 的例外，是另一套版式的常数** ——
  FR-001（内容列等于容器）在两套版式下都成立，只有这个常数分档。
  写成两条而不是一条，是因为「恒定 52px」如果不限定断点就是假的：实测 700px 与 390px
  下都是 20px，而规格的 Edge Cases 一直承认这件事。**一条自相矛盾的需求比一条啰嗦的需求坏。**
- **FR-003**：面板右内边距必须与左内边距（56px）读得出是同一套收边。当前 40px。
  **不得压到井槽的 12px** —— 56 : 12 读作没对齐，且内容贴到面板边界本身就局促。
  > 本条最初写的理由是「12px 会让内容切进 28px 圆角」。**实测推翻**：右上角按钮
  > 距面板上缘 46px，圆角方框只占上缘 28px，两种内边距下它都进不去。
  > 真实理由只有左右差与局促感，改写如上 —— 一条经不起测量的理由不该留在规格里。
- **FR-004**：**不得存在宽度地板。** 取代 020 的 FR-004（960 地板）。窄窗口下内容列
  等于面板，允许小于 960。
- **FR-005**：**不得存在宽度上限**，任何宽度下都不封顶。（承自 020 FR-003，未变。）
- **FR-006**：不得有任何单页内容列宽度声明。（承自 020 FR-006，未变。）
- **FR-007**：控件自身的宽度声明必须保留且不受本轮影响 —— 判据是
  **「它在决定这一页多宽，还是这个部件自己多宽」**。搜索框的 640、备注列的截断宽度属后者。
- **FR-008**：字号、行高、圆角、间距、控件尺寸**一律不变**。本轮只动宽度。
- **FR-009**：服务端零改动。
- **FR-010**：本轮不新增任何用户可见文案，两份目录不动。
- **FR-011**：`docs/rules/web-tables.md` 的内容列一节必须描述现行规则，并保留三条规则的
  实测对照，使「为什么改了三次」可读。
- **FR-012**：020 的 `spec.md` 正文**不得修改**，只在顶部加被取代横幅 —— 与 020 当初
  未回头改 018 的做法一致。`handoff.md` 同样不编辑，不一致只记入 README。
- **FR-013**：实测脚本必须断言**留白为 0 且右缘距离恒定**，并且在任何宽度规则被贴回时
  失败（双向验证）。

### 非功能性约束

- **NFR-001**：`tests/contentColumn.test.ts` 是防止宽度规则复辟的**唯一拦截**。
  018 与 020 时期 `AppShell` 里还有一个数字，一个漏进来的 `max-w-` 至少会与它抵消而露出破绽；
  现在 `AppShell` 里没有数字了，漏进来的 `max-w-` 会直接生效且无人察觉。这条测试的地位
  因本轮而上升，必须保留。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：在 3840 / 2560 / 1920 / 1440 / 1366 / 1280 六档窗口下，内容列宽度等于面板
  内容盒宽度，留白为 0（容差 1px，用于分数像素取整）。**取代 020 的 SC-001。**
- **SC-002**：同六档（均为桌面版式）下，内容右缘到屏幕的距离恒为 52px（容差 1px）。
  **取代 020 的 SC-002。**
- **SC-002a**：移动版式抽查两档（如 700 / 390），留白同样为 0，右缘距离为 20px。
  验证的是 FR-002a：分档的是常数，不是「内容列等于容器」这条规则。
- **SC-003**：把任意宽度规则贴回内容列后重跑实测，**六档全部报错**；去掉后六档全过。
  （双向验证 —— 一条只见过它通过的版面断言不构成证据。）
- **SC-004**：`internal/` 与 `cmd/` 对 `main` 无 diff。
- **SC-005**：前端测试全量通过，ESLint 与 `tsc --noEmit` 零错误。
  **本轮的红绿证据由 SC-003 承担** —— 本轮没有新增或修改任何测试断言
  （`contentColumn.test.ts` 只改了文档注释），所以「断言被还原时会红」这句话
  在本轮为空转，不作为验收。
- **SC-006**：全仓搜索不出与代码相反的版面数字；提到 76% / 960 的地方只剩历史对照表。
- **SC-007**：任意宽度下页面本身不出现横向滚动条（`documentElement` 与 `main` 均不横向滚动）。

## Assumptions

- 面板左内边距保持 `pl-14`（56px）。FR-003 的 40px 是相对它成立的 ——
  左边若变，右边要重新判断，否则「读作同一套收边」这句话失去参照。
- 侧栏宽度（236px）与井槽（12px）保持固定值。它们是「恒定 52px」这个结论的组成部分。
- 支持的窗口宽度下限沿用现有断点，本轮不引入新断点。
- 「留白感不对」是观感判断，无法自动化。SC-001/002 量的是它的**可证伪替身**
  （留白为 0、右缘恒定），最终确认仍靠开发者看截图 —— 本轮已确认。

## 已接受的代价

看过 2560 三档截图后逐条裁定，**都不修**：

1. **宽表格的列被拉开。** 2560 下 `Model`、`Note` 等窄内容的列会占到很宽，
   列与列之间出现大段空白。修它需要给表格另设一条内部宽度规则，那是另一条规则，
   本轮不引入。
2. **960 地板消失，窄屏不再等同 018。** 1440 下内容列 960 → 1084。
   看上去更饱满，但 020 的「窄屏零回归」承诺就此作废，已在 US3 写明。
3. **时间线的分隔线横贯整幅宽度。** 承自 020 的同一项裁定，未变。

## 不在范围内

- **导入页那张铺满的空卡不修。** 2560 下步骤卡宽 2204px，卡内只有一个下拉与一个按钮，
  右侧一千七百余像素为空。**开发者裁定：导入页目前只是 demo，后续还要大改，
  不要为此加任何控件、占位内容或宽度上限。** 写在这里是为了让它不被后来者当作缺陷修掉 ——
  它是已知的、被接受的、且即将随整页重做而消失的。
- 表格内部的列宽策略（等宽、按内容、可拖拽）—— 与本轮无关，代价 1 若要修属于那条线。
- 字号、间距、圆角的任何缩放。018 的结论未变：半缩放的版面比不缩放更难看。
- 侧栏宽度与布局。
- 移动端断点的重新划分。
