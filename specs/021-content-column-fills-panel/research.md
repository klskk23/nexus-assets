# Phase 0 调研：内容列铺满面板

**结论先行**：要改的是一个类名的删除；真正需要调研的是**为什么 020 的验收全绿而观感不对**，
以及右内边距该留多少。两个问题都是量出来的，不是推出来的。

---

## 问题一：020 全部达标，为什么还不对？

### 做法

同一份构建、同一份数据、同一个页面，只用一条 CSS 覆盖切换宽度规则，在 2560 / 1920 / 1440
三档各出一张图。**不重新构建**，否则三张图之间会混进别的差异。

三个变体：

| | 规则 |
|---|---|
| A | 现状 `w-[min(100%,max(960px,76%))]` |
| B | `width: 100%` |
| C | `width: 100%`，且面板右内边距压到井槽的 12px |

### 实测（`main` 内容盒 vs 内容列）

| 视口 | 变体 | 包含块 | 内容列 | 留白% | 右缘距屏幕 |
|---|---|---|---|---|---|
| 2560 | A | 2204 | 1675 | 24.0 | **581** |
| 2560 | B | 2204 | 2204 | 0 | 52 |
| 2560 | C | 2232 | 2232 | 0 | 24 |
| 1920 | A | 1564 | 1189 | 24.0 | 427 |
| 1920 | B | 1564 | 1564 | 0 | 52 |
| 1440 | A | 1084 | 960 | 11.4 | 176 |
| 1440 | B | 1084 | 1084 | 0 | 52 |

### 结论

**020 的指标是从半个诊断里推出来的。**

018 的观察「留白随窗口无界生长」是对的，020 据此把占比锁死在 24%，也真的做到了 ——
1920 / 2560 / 3840 三档占比一致，`measure.mjs` 双向验证过。

但 24% 在 2560 上是 **581px**。占比恒定与「这片空白可以接受」是两回事：
前者是关于**变化**的性质，后者是关于**大小**的判断，020 只处理了前者。
开发者的原话是「感觉右边留白感还是不对」—— 那不是对占比的意见，是对绝对量的意见。

**这一条是本轮最该留下的东西**，因为它不是版面问题：一个指标可以完全达成而目标完全没达成，
只要它是从不完整的诊断里推出来的。已同时记入 `docs/design/organic-layout/README.md` 第四处。

### 顺带否掉的一个假设

调研之初考虑过「封一个更大的上限」（如 1400）。**不成立**，而且 020 已经算过：
封在 1400，3840 下留白回到 61%。天花板只是把同一个失效模式往外挪，不是修它。
本轮沿用 020 这个结论，不重复论证。

## 问题二：右内边距留多少？

### 做法

C 变体把右内边距压到井槽的 12px，看能否再抢回 28px。出图对比。

### 发现

**不能，但最初写下的理由是错的，这里如实记下。**

初判：「面板圆角 28px，退到 12px 时右上角按钮会与弧线相交」。这是**看截图看出来的**，
在 implement 阶段被实测推翻 —— 按钮距面板上缘 **46px**，而圆角方框只占上缘 28px，
所以两种内边距下它都进不到弧线所在的区域。C 变体的按钮**没有**压在弧线上。

真实理由只剩两条，但都成立：

1. **左右差**：左内边距 `pl-14`（56px）。**56 : 40 读作有意的收边，56 : 12 读作没对齐。**
2. **局促**：内容贴到距面板边界 12px，无论是否碰到曲线，看上去都是挤在边上。

**记在这里是因为它是本轮第二次「看起来对、量出来不对」** —— 第一次是 020 的留白占比。
一条经不起测量的理由，哪怕结论碰巧正确，也不该留在规格里。

### 结论

保留 `pr-10`（40px）。恒定右缘距离 = 40（面板内边距）+ 12（井槽 `p-3`）= **52px**。

这个 52 不是新设的数字，是两个既有值相加的结果 —— 本轮没有引入任何新常量。

## 问题三：960 地板要不要留？

### 做法

看 1440 / 1366 两档的读数。

### 发现

020 的地板在这两档是**唯一起作用的地方**：1440 下内容列 960、留白 124px，
与 018 完全相同；1366 下 960 / 50px，同样相同。这正是 020 能承诺「窄屏零回归」的原因。

留着地板 + 上面铺满，规则会变成「宽屏铺满、窄屏 960」，也就是**又出现一个数字**，
而且是一个只在两档窗口生效、其余时候看不见的数字 —— 那正是 018 与 020 各自栽过的形状。

### 结论

**一起去掉。** 代价是 1440 下内容列 960 → 1084，020 的「≤1548 逐像素一致」作废。
截图确认 1440 下 B 变体观感不劣于 A（见 US3 的走查）。

代价写进规格，而且要写进走查步骤 —— 否则下一个人对比 018 截图会把变宽当回归修回去。

## 问题四：验收怎么写才不会重蹈 020？

### 分析

020 的 `measure.mjs` 没有错，它诚实地量了它被要求量的东西。问题在于**被要求量的东西是代理指标**
（占比），而代理指标可以在真实目标失败时通过。

本轮不找代理：直接量**留白为 0** 与**右缘距离恒定**。这两个量的好处是**能被眼睛证伪** ——
如果脚本说留白是 0 而截图上明显有一片空白，那是脚本坏了，一眼就能看出来；
而「占比 24%」这种数字，眼睛无法判断它对不对。

### 落地

- 桌面六档（3840 / 2560 / 1920 / 1440 / 1366 / 1280），断言 `void ≤ 1px` 且 `edge = 52 ± 1px`。
- 移动两档（700 / 390），断言 `void ≤ 1px` 且 `edge = 20 ± 1px` ——
  **两套版式都断言「铺满」，只有常数不同**，这正是 FR-002 / FR-002a 的分界。
  最初只写了桌面五档，1280 与移动端是 analyze 阶段补上的缺口。
- 1px 容差用于分数像素取整，**不足以掩盖任何真实的宽度规则** ——
  反向验证时最小的偏差是 1366 档的 50px，是容差的 50 倍。
- 双向验证：贴回任何宽度规则必须全红。

### 反向验证实测（贴回 020 的规则后）

| 视口 | 留白 | 右缘距屏幕 | 结果 |
|---|---|---|---|
| 3840 | 836 | 888 | ✗ |
| 2560 | 529 | 581 | ✗ |
| 1920 | 375 | 427 | ✗ |
| 1440 | 124 | 176 | ✗ |
| 1366 | 50 | 102 | ✗ |

去掉规则后五档全过。**双向都跑过了**，不是只见过通过的那一半。

## 问题五：jsdom 里能守住什么？

**守不住版面**，这一点 018 与 020 已各证明过一次，本轮不再重新论证：
jsdom 不做布局，`getBoundingClientRect()` 恒返回 0。

但本轮有一个**新的**、必须记下的变化：

`tests/contentColumn.test.ts` 守的是源码不变量（`routes/`、`features/` 下的 `max-w-`
命中集合等于白名单）。018 与 020 时期，就算一个 `max-w-` 漏进来，`AppShell` 里还有一个
宽度规则与它抵消 —— 两条规则打架，版面会明显出错，人能看见。

**现在 `AppShell` 里没有数字了**，漏进来的 `max-w-` 会直接生效，而且看起来「像是有人特意
收窄了这一页」，不像 bug。这条测试因此从「防回归」升级为**唯一拦截**，规格里单列为 NFR-001。
