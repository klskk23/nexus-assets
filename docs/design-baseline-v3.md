# 设计基线 v3 —— 信息项生命周期与型号归属

本文承接 `docs/design-baseline.md`（决策 1–24）与 `docs/design-baseline-v2.md`（决策 25–40），
记录第三轮访谈确定的决策 **41–52**。凡与 v1/v2 冲突之处，**以本文为准**，并注明被推翻的原决策。

> 适用范围：feature `003-field-lifecycle-and-models`。前两版中未被本文触及的部分继续有效。

---

## 缘起

v2 上线后暴露四件事，其中两件是模型层面的：

| 问题 | 性质 |
| --- | --- |
| 信息项只能停用不能删除，建错一个就永远留在库里 | **模型错误** |
| 型号只能属于一个类别 | **模型错误** |
| 型号在界面上仍然不可用（没有种子数据、没有默认值入口） | 功能缺口 |
| 前端与 API 在若干处对不上，且测试全绿 | 缺陷 |

第一件的根因是 001 定下的「元数据只增不减」被推得太远。那条原则要保护的是**已经产生了数据的
配置**；一个刚建错、还没人用过的信息项不在保护范围内，却被同一条规则挡住。

---

## 一、信息项的生命周期

### 决策 41：信息项从「只停用」改为「可删除」，停用机制移除

**推翻 v1 决策 20**（「信息项只能停用不能删除」）。

`field_definitions.archived_at` 列删除。`ArchiveField` 让位给 `DeleteField`。
界面上的「停用」按钮改为「删除」。

理由：停用与删除并存会给管理员两个看起来一样的按钮，而两者的区别（有没有存量数据）
恰恰是系统自己就能判断的。让系统判断，比让人记住规则更可靠。

### 决策 42：拦截线是「有资产填了非空值」

删除一个信息项时，扫描全部资产的 `attrs`：只要有任何一台设备在该 key 上存有非空值，
即拒绝删除，并报出前若干台设备与总数。

**不以「是否绑定到类别」为拦截线**。绑定但从没人填过值的字段，正是「建错了想删掉」
的典型场景，拦住它就等于没解决问题。

代价：判定是一次全表 `json_extract` 扫描。删除是低频操作，可接受。

### 决策 43：删除时一并清掉 `attrs` 中的残留键

在同一事务内对全部资产执行 `json_remove`。

**实际上这只会清掉空串与 null 这类残渣** —— 有非空值的字段在决策 42 处就已经被拒绝了。
写出来是为了让「删除」这个词名副其实：库里不留该 key 的任何痕迹。

### 决策 44：下线一个仍在使用的字段，路径是解绑

不再需要某个字段、但存量数据要保留时，从类别上**解绑**它。存量值变成孤儿键：
保留展示、不再校验、不参与唯一性（沿用 v1 决策 22 的 `archived_attrs` 机制）。

**必须接受的终点**：解绑之后，那个字段定义**基本上永远删不掉了** ——
孤儿值仍然算「有资产填了值」。定义会一直留在信息项库中。这是本路径的实际结果，
不是缺陷；替代方案（提供「强制删除并清空全部取值」）是一个不可恢复的批量数据删除，
与决策 42 自相矛盾。

### 决策 45：补齐解绑的 HTTP 端点与界面

`Store.Unbind` 自 001 起就存在，v2 还为它加了反向依赖护栏，但**从来没有路由与入口**。
决策 44 把它变成唯一的下线路径，因此本轮必须补出 `DELETE /api/categories/:id/bindings/:field_id`
与类别页上的解绑按钮。

没有它，「不再需要某个字段」在界面上三条路全断：停用（已移除）、删除（有值）、解绑（无入口）。

### 决策 46：持有方实体与账号维持「只停用」

**不推广决策 41**。三类元数据在这一点上行为不同，理由要写清楚，否则下一个人会以为是漏改：

- **信息项**是纯配置，删掉它不影响任何历史记录的可读性
- **持有方实体**被流转历史的 `from_holder_id` / `to_holder_id` 按 id 引用，删掉会让时间线
  出现无法解释的 id
- **账号**被 `asset_transfers.actor_id` 外键引用，实际上永远删不掉 ——
  给一个永远会被拒绝的按钮比不给更糟

## 二、型号的归属

### 决策 47：型号与类别改为多对多

**推翻 v1 决策 13** 中「型号隶属于某个类别」的单值假设。

`product_models.category_id` 列删除，新建关联表：

```
product_model_categories(
  model_id    TEXT NOT NULL REFERENCES product_models(id) ON DELETE CASCADE,
  category_id TEXT NOT NULL REFERENCES categories(id),
  PRIMARY KEY (model_id, category_id)
)
```

理由：同一款设备可能同时是「SDWAN 路由器」和「测试设备」，也可能既是在用设备又是备件。
单值归属逼着管理员在两个都对的答案里选一个，或者把同一款设备建两遍。

### 决策 48：型号重名规则改为 `UNIQUE(vendor, name)`

原规则 `UNIQUE(category_id, name)` 随 `category_id` 一并消失。

型号本来就是厂商命名空间里的东西：Acme X100 与 Beta X100 是两款不同的设备，
而同一个厂商不会有两款同名产品。

**`vendor` 必须同时改为 `NOT NULL DEFAULT ''`** —— SQLite 的 UNIQUE 把 NULL 视为互不相等，
两个 `vendor IS NULL` 的同名型号都能插进去，约束等于不存在。空厂商当作一个命名空间。

### 决策 49：`attr_defaults` 套用时静默跳过当前类别没有的键

型号关联了多个类别之后，它的默认值里可能有某个类别不认识的 key。
套用时只填当前类别有效字段集内的键，其余忽略。

**不在关联时校验键必须存在**：那会逼着管理员为了共享一个型号先去对齐两个类别的字段集，
而默认值本来就是「能填则填」的东西，不是承诺。

### 决策 50：型号候选范围 = 关联到本类别或其任一祖先

与字段继承同一套心智模型：型号关联在「网络设备」上，它的子类「SDWAN 路由器」也能选。
反方向不成立 —— 关联在子类上的型号，父类的资产看不见。

有了多对多之后，想让某个子类单独可选，显式关联上去即可，不必依赖推断。

### 决策 51：导入仍按型号名解析，歧义时报错

导入模板保持单列型号名（沿用 v1 决策 18 的双行表头形态）。
名称在全库唯一命中则接受；命中多条时该行报错，提示改写为「厂商 型号」。

**不改为按 id 解析**：模板里要人手填 UUID，与「首行中文可读」的初衷直接冲突。
**不拆成两列**：单厂商环境下多一列冗余，而重名是少数情况 —— 让少数情况付出代价。

## 三、前端与 API 的对齐

### 决策 52：本轮逐处手工对齐，不引入机械门禁

清查发现八处前端与 API 不一致，其中最有代表性的两类：

1. **后端专门附带、前端从不读取的数据**：停用持有方失败时，`failHolder` 会把阻挡的设备
   列表放进错误响应（`blockers`），而 `ApiError` 只解析 `referrers`。
   `zhMeta.holders.blocked` / `blockedBy` 两句文案就是为它准备的，一次也没用过。
   本轮把它渲染出来，与信息项的引用列表同一形态。

2. **测试 fixture 捏造后端不返回的字段**：6 个测试文件仍在传 `sn_template`、
   3 个传 `sn_template_from`、2 个传 `archived_at`，测试全绿。

**本轮只手工修掉这八处，不加机械门禁。** 记录这个选择的代价：
下次模型变动时，同类漂移会原样重演，而且同样全绿。
把 fixture 声明为带类型的常量（让 `tsc` 拒绝多余字段）是已知的解法，本轮不做。

## 四、迁移

`migrations/003_field_lifecycle.sql`：

1. `field_definitions` 去掉 `archived_at`（表重建 —— 该列参与了若干查询但无索引，
   仍走重建以保证列顺序确定）
2. `product_models` 重建：去掉 `category_id`，`vendor` 改 `NOT NULL DEFAULT ''`，
   `UNIQUE(vendor, name)`
3. 新建 `product_model_categories` 并把原有的 `category_id` 搬进去
4. 索引 `ix_pmc_category` 供候选查询使用

与 002 一样，表重建需要 `PRAGMA foreign_keys=off`，因此该迁移不在事务内执行。
