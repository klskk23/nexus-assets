# 字段、绑定与解析

改 `internal/schema` 之前读这一份。每条都是踩过的坑，不是风格偏好。

- **绑定目标有三个，互斥的是「类别 vs 设备」**（016 决策 110）。类别一侧是
  `category_fields`；设备一侧是 `model_fields` 与 `vendor_fields`，**两者可以并存**
  （都在回答「哪些设备」，并集仍是一个集合），但不能与类别侧混。
  `bindTx` 一条查询同时问两张设备表；`bindModelTx` 与 `bindVendorTx` 只问类别表。
  **`binding_mode` 的取值是 `category | device | unbound`**，不再有 `model`。

- **厂商是实体，型号实时继承它的字段**（016 决策 107/108）。`product_models.vendor_id`
  指向 `vendors`，改名改一行、每次读都 join —— 以前它是一列字符串，改名意味着挨个改型号，
  或者不改，然后过一阵子才发现。绑到厂商的字段**在每次读时摊到旗下全部型号上**
  （`resolveVendorFields`），所以下个月新建的型号开箱即有，解绑一次从所有型号撤走。
  **唯一索引必须是表达式** `UNIQUE(ifnull(vendor_id,''), name)` —— SQLite 把 NULL 当彼此
  不同，普通的 `UNIQUE(vendor_id, name)` 会让迁移 003 修掉的那个 bug 当场复活。
  **`model.vendor` 在表达式引擎里仍然解析为厂商名字符串**，实体化不能让已有编号静默变值。
  厂商入口是 `/models` 与 `/models/vendors` **两条独立路由**加页签 —— 一个地址两张
  `CrudPage`，`q` 与 `offset` 会互踩。字段组同理：`/fields` 与 `/fields/groups`。
  **这两对都只占导航栏一格**：厂商是型号的一个属性、组是一把字段，都不是独立的去处，
  各给一格只会让导航更长而不是更好找。页签是 `features/metadata/MetadataTabs.tsx`。

- **`model_ids` 有两个含义，看它从哪来。** `GET /categories/:id/schema` 里是**到达集**
  （直绑 ∪ 厂商展开）—— 列解锁、`ForModel`、`AppliesTo`、导入不匹配拒绝四处判定本来
  就该按它判，016 一行没改。`GET /fields` 的行里是**绑在哪些型号**，配 `vendor_ids`
  一起看 —— 绑定列与字段编辑器要显示的是有人选了什么，不是它长成了什么。别把两者混用。
  **但绑定列里，厂商已经覆盖的型号不单独列出**：绑了型号又绑了它的厂商，两条记录都在，
  一栏写「Dell、Dell VEP-4600」是对同一个问题给两个答案。行没删 —— 解绑厂商之后那款
  型号会重新出现，之前那次明确的选择不会被悄悄花掉。
  **025 之后这条只管「表格里的那一格」**：面板有地方，字段详情里每个绑定目标各占一行
  并写明是哪一种，那是列出两个不同的目标，不是同一行画两遍。

- **型号详情里，一个字段只占一行，来路全写出来**（028 决策 208）。
  字段可以同时绑到型号和它的厂商 —— 两条到达路径，但**只有一个字段**：
  录入表单问一次，`GET /categories/:id/schema` 也只返回一次。
  型号面板曾把它列两遍（一遍「厂商」一遍「本型号」），**两行还用了同一个 React key**，
  这也是它一直没被发现的原因。
  **不能留一条丢一条**，因为那个来源标记是有承重的：只写「厂商」等于告诉人
  「解绑厂商这个字段就从本型号消失」—— 而它不会，直绑还在；只写「本型号」则反过来骗人。
  所以那一行**把每条来路都列出来**，解绑其中一条显然不是故事的全部。

- **「可搜索」在界面上要显示实际结果，不是那个开关的裸值**（028 决策 211）。
  服务端是 `Findable() = Searchable || IsUnique`，字段编辑表单也据此把唯一字段的
  勾选框**勾上并锁死**。所以字段详情里读 `field.searchable` 就会在一个搜得到的字段上
  写「否」—— 这是最坏的一种错，读者会跑去查「我的搜索为什么坏了」。
  **而且要说清是哪一种来路**（「是」还是「是（唯一字段自带）」），
  与旁边「唯一」那一格写的是**哪种唯一**而不是「是」同一个道理：
  一个自身开关为假、只因唯一才可搜的字段，被取消唯一之后会悄悄搜不到，
  而屏幕上没有任何东西提醒过。

- **字段组是绑定时展开的糖，解析路径不认识它**（016 决策 105）。绑一个组 = 往对应绑定表
  插入组内每个字段一行；**任何绑定表上都没有组这一列**，`EffectiveFields` 不因组而变。
  组内任一成员违反互斥则**整组回滚**并点名该字段（决策 106）。
  **没有「解绑一个组」**：展开不留痕迹，那个动作无从定义；删除组也不解除任何已展开的绑定。
  已接受的代价：往组里加字段，已绑对象不会跟着变 —— 有测试盯着，别顺手「修」成结构。
  **组绑定与字段绑定是同一件事的两种说法，形状必须一致**：新建组与新建字段一样收
  `category_ids` / `model_ids` / `vendor_ids` 三个列表，一个事务、多目标、
  任一 (成员, 目标) 对被拒则整体回滚且**组也不创建**。组只是「把成员逐个绑」的简写，
  而成员本来就能一次绑五个类别 —— 曾经组只能绑一个目标，那不是规则，是我把接口写窄了。
  界面上两处共用 `features/fields/BindingPicker.tsx`，这样它们没有地方可以再走偏。
  给已存在的组补绑走 `POST /field-groups/:id/bindings`，同样收三个列表、同样一个事务；
  既有的三个绑定端点接受 `group_id` 是它的单目标反方向。这与字段同形：
  `POST /fields` 收列表，`POST /categories/:id/bindings` 收单个。
  **组的三个对话框（新建、编辑、绑定到…）是同一个表单**（`GroupForm`），
  「绑定到…」就是打开编辑对话框 —— 一个组只有一张表。
  编辑对话框里的绑定勾选是**动作不是状态**：组绑出去不留痕迹，读不回来「它绑在哪」，
  取消勾选也不解绑。这句话必须一直可见（`FieldDescription`），不能藏进问号。
  **绑组的入口在字段组页的行右键菜单里**，不在字段编辑器里 —— 绑一个组是对某个目标做的事，
  不是某个字段的属性。它一开始放在字段表单里，结果那个控件从来没被渲染过：
  `groups` 属性没人传，`bindGroup` 也没人读，整整一个版本没有任何地方能绑组。

- **删除字段要删三张绑定表**：`category_fields`、`model_fields`、`vendor_fields`。
  后两张的 `field_id` **故意不带 cascade**，漏删就是 500（v0.8.3 那次）。
  `field_group_members` 两侧都 cascade，不在 `deleteFieldTx` 里，也不该在。
  同理 **`boundPaths` 要问三张表** —— 少问一张，那类字段就答「没绑」，
  所有按绑定路径收窄的删除守卫当场静默失效。

- **型号不属于类别**（026 决策 182–185，029 决策 213 收尾，推翻 016 的形态）。
  一台设备能记录的字段 = **它的类别链 ∪ 它自己的型号 ∪ 那个型号的厂商**，
  与「这个型号有没有关联到这个类别」无关。入口是 `FieldsForAsset(path, modelID)`；
  `EffectiveFields(categoryID)` 今后**只答类别链**，`/categories/:id/schema` 也是 ——
  想要「这一台能填什么」就带上 `?model_id=`。

  **`product_model_categories` 已经删表**（029 决策 213，迁移 023）。026 当时把它
  降级为「建议」—— 录入时关联过的型号排前面、删类别时提示会脱开哪些 —— 留了下来。
  留着的代价远超过那点提示：它还留在**四处守卫的 WHERE 里**，而 026 没走到那四处。
  其中最要命的是 `boundPaths`（**决定一个字段的删除守卫管到哪里**）：
  型号绑定的字段，若那个型号没关联任何类别，它答「哪儿都没绑」，
  **所有按路径收窄的守卫当场全部静默关闭**。026 之后「没关联任何类别」不是边角，是常态。

  还有一个连带的坑：`fieldsInScope` 从前**只读 `category_fields`**，
  于是绑在型号上的计算字段**永远不会被算作引用者** —— 同一个型号上两个字段、
  一个算另一个，删掉被算的那个直接放行，这个型号的每台设备从下次编辑起都存不进去。
  **设备侧的绑定没有路径，就等于在任何路径下都成立**：两处都按这条改了。
  代价是跨型号的两个绑定会被当成可能相撞而多拦一次 —— 多拦一次是改个名，
  少拦一次是一个谁也存不进去的类别。

  **录入时的型号列表因此不再有任何排序偏好**，`CandidateModels` 不再收类别参数，
  导入解析型号名也一样（从前：文件里写了一个没关联到该类别的型号，那一列被报成未知列，
  等于导入拒绝了一台录入表单会接受的设备）。

  **为什么必须一起改**：`EffectiveFields` 从前只收集「关联到该类别链」的型号绑定，
  `ForModel` 补不回来 —— 所以**一台设备的型号如果没关联到它的类别，那个型号的字段会静默消失**。
  界面从前用「型号下拉按类别过滤」挡住了这条路。**只解开下拉不改字段集，等于亲手制造这个 bug。**

  **CSV 的列是例外**：`EveryPossibleField(categoryID)` = 类别链 + **全部**型号/厂商字段。
  一个文件一套列而一批设备通常是混的，所以列是「所有可能」，
  再由每行按自己的型号拒绝不属于它的值（015 决策 102，规则未变）。

- **键冲突要问三张表**（026 决策 186–188）。两个绑定冲突，当且仅当**存在一台设备同时受两者作用**：

  | | 冲突条件 |
  |---|---|
  | 类别 ↔ 类别 | 同一条链 |
  | 类别 ↔ 型号 / 厂商 | **总是** —— 型号现在可以出现在任何类别下 |
  | 型号 ↔ 型号 | 同一个型号（两个不同型号永不同台，各自绑同名键是合法的） |
  | 型号 ↔ 厂商 | 该型号属于该厂商 |
  | 厂商 ↔ 厂商 | 同一个厂商 |

  **这个洞在 026 之前就存在**：`Bind` 只查 `category_fields`，`BindModel` 只查绑定模式，
  而 `EffectiveFields` 是三张表并集 —— 两个同名键的字段能落到一台设备上，
  `attrs` 里那一个槽就有两个定义。`nexus verify` 现在会报告存量里已有的冲突。

- **「可搜索」是字段的属性，与「唯一」分开**（026 决策 175–181）。
  从前只有唯一字段能被搜到，所以「想让 service tag 能搜」的唯一办法是承诺它唯一。
  **唯一蕴含可搜且不可关**（一个搜不到的唯一字段没有用处），其余可随时改，
  **改了立刻回填全部存量** —— 半填充的索引会让搜索对一部分设备有效、对另一部分无效，
  而界面上分不出来。

  **索引在 `asset_search_values`，不在 `asset_unique_values`**：
  `exactMatch`（搜到唯一一台就直接跳详情）读的是后者，
  把非唯一值放进去，两台设备共享一个 service tag 就会把人甩进其中一台。
  搜索读两张表：唯一表**含已归档的**（旧编号仍是身份主张），搜索表只存当前值。

- **有效字段集只有一个来源**（015 决策 101，入口在 026 换成 `FieldsForAsset`）。
  它返回的是**这一台设备的完整词汇表**（类别链绑定 ∪ 它自己的型号 ∪ 该型号的厂商），
  录入表单、写入校验、导入模板、导出、显示列下拉五处都读它，改一处五处一起对。
  **要"某一台设备看到哪些字段"，再用 `schema.ForModel(fields, modelID)` 收窄**——
  前端同名的是 `features/assets/modelFields.ts` 的 `fieldsForModel`，两边口径必须一致。
  **换型号导致的归档不需要写路径**：`archived_attrs` 是读时用有效字段集切出来的，
  收窄口径一改，决策 98 自动成立。
  **导出/导入模板的列由完整 schema 决定**，不随本次筛选结果里有没有该型号的设备而变
  ——列是 schema 的事，行才是查询的事；同类别不同型号**不分包**。
  **导入时某行型号没绑某字段却填了值 → 预览阶段拒绝该行**，不静默丢值也不静默写入。

- **唯一性是关于类别的**（v6 决策 71）。字段 `key` 只需在**一条链/子树内**不重复，
  `field_definitions.key` 的全局 UNIQUE 已删除；`is_unique` 的取值在
  **绑定所在类别的子树内**唯一，`asset_unique_values.scope_id` 记的就是这个类别。
  键可以重复之后，**任何「按键名找」的查询都在答错问题** —— 删除字段的三道守卫
  （表达式引用、显示编号、存量取值）都必须先取该字段的绑定路径再收窄，
  没有绑定的字段谁也挡不住。

- **字段绑定类别，不是类别绑定字段**（v6 决策 72）。**新建字段时就能勾类别**，
  绑定与创建在同一个事务里 —— 绑定被拒则字段也不创建；解绑在**字段编辑对话框**里做，
  且是**行上可见的按钮**，不是只有右键（那张表的行本身没有点击行为，
  藏进右键菜单等于没有）。
  类别对话框里的字段表是**只读**的。字段页有类别筛选与翻页，
  `GET /fields` 返回 `{items,total,offset,limit}` 且每项带 `category_ids`。

- **「必填」是写入时的规则，不是数据不变量**（v6 决策 70）。可以给已有设备的类别
  绑定必填字段：存量资产不回溯校验，列表、详情、流转、重算都照常，
  但**下次编辑那台设备时必须补上**。勾「必填」时要显示会波及的资产台数 ——
  能力一直都在，缺的是让勾的人知道自己给同事埋了什么。
  **必填在字段自己身上，不在绑定上**（018）。`field_definitions.required` 是唯一来源，
  勾上就是它绑到的**每个**类别与型号都要求填；`category_fields.required` 与
  `model_fields.required` 两列还在，但**没有任何代码再写它们**，只留着给 down 迁移回填。
  以前它是逐条绑定设的，于是「这个字段必填吗」有不止一个答案，表格只能写「部分必填」，
  谁都得点进去才知道是哪几条。迁移按**任一条绑定必填即为必填**回填 ——
  那保住了别人明确表达过的意图，代价是把一个局部的必填放大到该字段的其余绑定上。

- **字段的键名、类型与唯一性建好之后不能改。** 前两个是因为存量的值就记在那个键下、
  按那个类型写进去的；**唯一性**是更硬的一条：打开它得先证明存量的值不重复，
  再为每台持有该值的设备补一条 `asset_unique_values`，那是一件事，不是一个勾。
  `PATCH /fields/:id` 只认 `label`、`options`、`required`，传了 `is_unique` 也不读。

- **改表达式即重算**（v6 决策 68）。字段编辑器里保存一个表达式变了的计算项，
  会先确认再 `PATCH` + `POST /fields/:id/recompute?dry_run=false`；**取消确认就不保存**。
  冲突时一台也不写，前端把 `options` 改回原值并列出冲突 ——
  否则留下的正是这套流程要消灭的状态：新设备按新规则、旧设备按旧规则。
  类别页**没有**重算按钮，也不要再加回去。

- **字段类型只剩八种**（v6 决策 64）：`text`、`number`、`boolean`、`date`、
  `mac`、`ip`、`url`、`computed`。**`enum`（单选）与 `reference`（引用）已撤回** ——
  领域层把它们当未知类型拒绝，不是只在界面里藏起来。存量字段由迁移 010
  转成 `text` 并清空 options，值一个不丢。别再看到「选项/废弃/引用目标」就以为还在。
  **每种类型只显示它自己的配置**：`text` 显示正则与校验提示（新建与编辑都要有），
  `computed` 显示表达式。

- **字段没有「停用」。** 只有删除（无关联时）与解绑（有存量数据时）。
  `archived_attrs` 是**解绑**产生的孤儿键，与停用无关，不要跟着一起清理掉 ——
  删掉它会让「解绑后仍能查看旧值」当场失效，且没有任何现有测试会失败。

## 历史原文：015 的两模式互斥

已被上面的「类别 vs 设备」取代，保留是因为代码注释里还引着 015 的决策号。

- **字段绑定有两种模式，互斥**（015 决策 96–100，已被 016 拓宽为上面那条，
  历史原文保留在此）。一个字段要么全绑类别
  （`category_fields`），要么全绑型号（`model_fields`），**不能混**——混绑会撞上三件事：
  被类别覆盖的型号再绑一次没有效果、两条绑定的必填开关对同一台资产各说各话、
  唯一性范围变成算不清的并集。两边各查对方一次即可拦住，写在 `bindTx` 与 `bindModelTx`。
  **值仍然属于每台资产**（`attrs`），型号绑定改的只是"这个字段出不出现在这台设备上"。
  别跟型号上的 `attr_defaults` 搞混——那是选型号时的一次性复制，是另一回事。
  **唯一性范围各算各的**：类别模式存类别 id（子树），设备模式存 `f:<field_id>`
  （该字段到达的全部型号合起来，016 起含厂商展开的那些）。按型号各自一个命名空间是错的——
  戴尔 ServiceTag 在整个产品线内唯一，不是每个型号内唯一。
  **`display_key` 只认类别模式字段**：设备字段（型号或厂商）只覆盖部分设备，
  其余的会永远退回 UUID 前 8 位。守卫要同时查 `model_fields` 与 `vendor_fields`，
  否则厂商字段会掉到最后一个分支被告知「未绑定」—— 而它绑着，用户在类别 schema 里看得见它。
