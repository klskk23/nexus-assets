# 资产、状态、持有方与导入导出

改 `internal/asset`、`internal/holder`、`internal/importer` 之前读这一份。
这里是「这套系统里的东西长什么样」，改动它们会波及存量数据。

- **资产的内建字段是六个**：类别、状态、持有方、负责人、**备注**、以及编号（派生）。
  备注在 `assets.note` 上，与任何类别的字段集无关 —— 别为了"能写一句话"去给某个类别
  加一个 text 字段，那样每个类别一份、谁也搜不到一起。**它不是流转上的备注**：
  写入接口里 `note` 是设备的，`transfer_note` 是这次流转的。
  `note` **字段缺席 = 不动**（流转或改属性不该抹掉它），给空串才是清空。
  导入模板的 `note` 列落到设备上，导出多一列「备注」，`/api/rows` 多一列 `sys_note`。

- **`assets` 没有 `sn` 列。** UUID 是唯一内部标识；人能读的编号是类别的
  `display_key` 指定的字段值，字段可以非唯一，因此多台设备可能显示相同编号；查看、编辑、
  流转与删除始终按 UUID 区分。未设置或字段值为空时回退 UUID 前 8 位。
  031 起编号字段须在最终类别有效集内；只在祖先绑定、但未逐层选中的字段不能作为编号。
  显示编号不唯一，继承恢复的冲突对象、确认及操作目标都用 UUID，不能按显示值去重或定位。
  v2 只用于追溯编号背景；与 031 正向选择和此前非唯一编号裁定冲突时，以最新规则为准。

- **类别字段以正向选择的有效集为准，不以祖先路径或 raw `attrs` 为准**（031）。
  `EffectiveFields` 是类别有效集的唯一来源；每层只按 field ID 选择直接父类的有效字段，
  再加自身直接绑定，来源与唯一 scope 保留最初绑定类别。`FieldsForAsset` 另加实际型号与
  厂商字段，设备侧实时传播不变。父类新增或恢复不等于子类已选择，不能从 path 猜适用性。
  归档属性由有效集在读取时切出，**撤回只使值只读，不删除 raw 值**；不能当成当前可编辑值，
  更不能把旧值带回有效导出、rows 或打印单元格。

- **继承撤回既释放有效唯一值，也抑制该字段的历史搜索**（031 对普通改号历史规则的明确例外）。
  同资产、同字段的当前及历史唯一行都置 `search_suppressed = 1`，当前行同时归档，
  当前搜索索引按最终有效字段重建。普通搜索和唯一精确匹配均排除抑制行，`ValueHistory`
  仍可查看；仅设置 `archived_at` 会被旧历史搜索再次命中，不算完成撤回。
  普通资产改号的未抑制历史仍可搜，资产另有有效字段匹配也仍可返回，不能一刀切禁用历史。
  恢复后创建新的未抑制 live claim，不解禁原先被抑制的历史；字段始终有效、只换来源时
  重算 scope 而不按撤回抑制历史。这样才不会让已经释放给另一台资产的值仍精确跳回旧资产。

- **恢复旧值不是直接开回开关**（031）。非空静态值须按当前类型、格式、范围重新规范化校验，
  唯一值按全部资产最终 claims 检查；冲突用字段及资产 UUID 定位，拒绝整次保存。
  非计算必填字段的存量缺值可以暂缺，但新建与下次编辑必须补齐；必要的计算结果没有缺值
  豁免，新增/恢复及受影响计算闭包须成功求值。元数据、当前与后代选择、资产版本、计算、
  唯一和搜索索引在一个写事务完成，不伪造状态或持有方流转事件。
  普通保存、整批导入与重算也须在写事务首个领域写入前核验准备时 schema 指纹；
  `409 schema_stale` 要求重新加载或预览，不能把旧准备结果偷偷套到新字段集上。

- **属性过滤须同时匹配值与字段实际到达范围**（031）。仅用 `json_extract(attrs, key)`
  会把撤回的归档值当有效结果；同一快照内用有效类别/型号范围与 JSON 取值共同过滤，
  分页和 count 必须共用谓词。同 key 不同 ID 的定义保留各自范围，不逐台查询 schema。
  字段影响数按实际到达资产去重，不是下面的类别可用数或持有方盘库数。

- **状态是数据，不是常量。** 标签、颜色与三项行为都在 `statuses` 表里。
  标签**不在** `zh.status`（已撤销）—— 前端一律走 `useStatuses()`，
  服务端一律走 `model.StatusSet`。写事务里的判定必须从 `tx` 读状态集，不从连接池读。
  转换规则**内置对内置沿用原 5×5 矩阵**，涉及自定义才放行，这是为了不放松任何既有护栏。
  状态只剩两个行为开关（`counts_as_available`、`terminal`），且对内置锁死。
  **状态不再约束持有方的种类**（007 移除了 `requires_location`）—— 在库可以由公司、
  部门或某个人持有。唯一还要求「必须是位置」的是**默认库存点**，那是另一条规则：
  归还需要指向一个具体的地方。

- **持有方是一棵有规则的树，且可编辑可删除。** 部门必须属于公司，位置可挂公司或部门、
  也可不挂，公司无上级。规则写在 `internal/holder` 的 `allowedParents` 表里，
  前端有同形一份（`web/src/lib/types.ts`）**只用于不提供非法选项**，把关的仍然是服务端。
  移动要防成环。迁移**不回填**存量的无上级部门。
  **持有方没有「停用」**（006 起）：删除在有设备、有下级、是默认库存点时拒绝；
  仅在流转历史中出现只提示不拒绝 —— 与状态删除同一条规则。类型不可改。

- **归还的目的地在设备身上，不在系统身上。** `assets.home_holder_*` / `home_owner_id`
  是设备「不在外面时归属何处」。归还的解析在 `applyOne` **逐台**进行：
  请求指定 → 该资产的 home → 全局默认库存点 → 报错。
  解析绝不能挪回批次层面 —— 那会让一批来自四个仓库的设备仍然只去一个地方。
  三态：字段缺席 = 不动，显式 null = 清空，有值 = 设置。

- **导入模板的固定列是四个**：`model`、`vendor`、`holder`、`note`。厂商列可空 ——
  型号只在两家供应商同名时才需要它，但没有它那种行只能被拒。
  **016 起 `vendor` 列是按名字查厂商实体**：查不到就拒绝该行，**导入不创建主数据**
  （与找不到持有方、找不到型号同一条规则）。「厂商不存在」与「该厂商没有这款型号」
  是两句不同的话，因为要去修的地方不同。

- **勾选导出跨类别时按类别分包**（zip，每类别一个 CSV）。一张表放不下两个类别：
  固定列之外的列是各自类别的字段，同一个表头下会是两种含义。

- **导出必须指定类别**：固定九列（编号、类别、状态、持有方、负责人、型号、厂商、备注、建档时间）之外的列由该类别请求的完整 schema 决定；
  `fields` 参数**不给＝全部字段，给空串＝一列都不要**，两者不是同一个请求。
  `EveryPossibleField` 保留类别有效字段和全部型号/厂商可能列，同类别混合型号不分包，
  表头不随本次查到的资产并集变动。031 起每个 CSV、rows、打印单元格还要按行的类别与
  实际型号验证 **field ID** 是否有效：父类仍有 A，拒绝继承的后代即便 raw `attrs` 有 A
  也必须留空；不同型号同 key 的不同定义不能互相冒用。导入模板仍保留混合型号可能列，
  每行提交不适用字段的非空值须在预览拒绝，不静默丢弃或保存。

- **型号身上也有一句备注**（迁移 020）。`product_models.note` 与 `assets.note` 同一个道理，
  只是高一层：关于这款型号本身的事（已停产、某个版本别买、只有 -B 版能插 25G 模块）。
  **不要把它做成字段** —— 字段是资产要记的东西，而这句话对该型号每台设备都一样，
  做成字段等于在每台设备的录入表单上重复问一遍，还得每个类别配一份。
  三态与设备备注一致：**字段缺席 = 不动**，给空串才是清空。`/models?q=` 也搜它。

## 两种「有多少台」

**类别问「有多少台能用的」，持有方问「这里放着多少台」。口径故意不同。**

| 端点 | 问题 | 排除 `counts_as_available = 0` 的状态吗 |
|---|---|---|
| `/categories/counts` | 我们有多少台能用的路由器 | **排除**（今天只有已报废） |
| `/holders/counts` | 上海仓库里放着多少台 | **不排除** |

报废的设备还实实在在堆在那个仓库里等着处置 —— 盘库的人要数到它，
而问「我们还有几台能用的路由器」的人不要。

024 立的规矩是「**同一个问题**不能有两个答案」（概览与类别页对同一个类别必须给同一个数），
不是「两个问题必须同一个口径」。所以这不违反它。**但有一条硬要求**：

> **这两个数不得在同一屏上顶着同一个词出现。**

否则下一个人会拿它们做减法，而两个数的差既不是「报废了几台」也不是任何有意义的量。

**持有方的计数含子树、只数 `holder_type = 'entity'` 的设备**（设备也可以由账号持有，
那一侧不在持有方这棵树上），**每个持有方都有键、没有设备的写 0**。
它必须与 `GET /assets?holder_id=<id>&holder_include_descendants=true` 的 `total` 相等；
服务端有一条测试对每一个持有方比对这两者，因为「子树」在服务端有两处 SQL 写法。
