# 设计基线 v2 —— 编号模型重构与流转补全

本文承接 `docs/design-baseline.md`（决策 1–24），记录第二轮访谈确定的决策 **25–40**。
凡与 v1 冲突之处，**以本文为准**，并在对应条目里注明被推翻的原决策。

> 适用范围：feature `002-identity-and-transfer`。v1 基线中未被本文触及的部分继续有效。

---

## 缘起

demo 跑通后暴露四个问题，其中三个是功能缺口，一个是模型层面的错误设计：

| 问题 | 性质 |
| --- | --- |
| 类别强制绑定编号生成规则，没配就存不进资产 | **模型错误** |
| 资产录入后无法在持有方之间流转，也无法改状态 | 功能缺口 |
| 型号选择器在 UI 上根本不存在，`attr_defaults` 从未生效 | 功能缺口 |
| 默认库存点无法取消，且传 `false` 静默返回 200 | 缺陷 |

第一个是本轮的主体。它的根因是把「编号规则」放在了**类别**上，而编号本质上是**一个由其他信息项推导出来的信息项** ——
放错了地方，于是每个类别都被迫回答一个它不该回答的问题。

## 一、编号模型

### 决策 25：UUID 是唯一的内部标识，`assets.sn` 列删除

**推翻 v1 决策 3**（「SN 为强制的人类可读主标识」）。

`assets.id`（UUID）本来就是主键，v1 额外维护了一个 `sn TEXT NOT NULL UNIQUE` 列作为人类可读标识。
本轮删除该列：类别不再被迫配置编号规则，没有编号的资产是合法的。

### 决策 26：编号规则归入信息项，不再属于类别

`categories.sn_template` 列删除。编号规则以**表达式键**的形式存在于全局信息项库中，
与其他计算字段没有任何区别 —— 它只是「碰巧被某个类别选作显示编号」的那一个。

**信息项二分（仅概念与 UI 层面，数据模型不变）**：

| | 说明 | 对应 `type` |
| --- | --- | --- |
| **静态键** | 值由人工录入或导入 | `text` `number` `boolean` `date` `enum` `reference` `mac` `ip` `url` |
| **表达式键** | 值由模板对其他键求值得到 | `computed` |

`field_definitions` **不新增 `kind` 列**。十种类型继续平铺，二分只体现在建字段 UI 的下拉分组上。
理由：`kind` 与 `type` 必须保持一致，多一个冗余维度就多一处可能不一致的状态。

### 决策 27：`categories.display_key` 指定显示编号

新增列 `categories.display_key TEXT`，值是某个已绑定字段的 `key`。

- 该字段被用作列表首列、删除二次确认、导出首列、`verify` 输出与流转时间线中的设备指代。
- **不沿祖先链继承。** 与 `sn_template` 的继承语义不同：继承一个「显示哪个键」的选择容易在子类别上产生意外，
  而子类别通常正是需要不同编号规则的地方。子类别没配就走回退。
- 指定的字段必须在该类别的**有效字段集**（含继承）内，否则拒绝。

### 决策 28：`display_key` 必须指向标为唯一的字段

设置 `display_key` 时，若目标字段 `is_unique = 0` 则拒绝，并提示先把该信息项标为唯一。

理由：显示编号的全部用途 —— 贴标签、口头指代、盘点核对、扫码直达 —— 在可重复时全部失效。
v1 靠 `sn` 列的 `UNIQUE` 约束保证这件事，删列后必须由信息项自己的唯一性接手。

### 决策 29：空值回退到 UUID 前 8 位

类别未配置 `display_key` 时，界面与导出显示 `id` 的前 8 位十六进制（如 `a3f1e2d4`）。

配合决策 28、31、33，`display_key` 一旦配置就**必定有值**：
唯一 + 依赖必填 + 求值失败阻止保存，三条叠加封死了「配了但为空」的路径。
因此回退**只在「类别没配 display_key」这一种情形下触发**。

### 决策 30：`asset_sn_history` 废弃，其功能由 `asset_unique_values` 承接

**推翻 v1 决策 12**（「旧编号归档为别名，永久可搜」）中的实现方式，保留其意图。

v1 用一张专表记录被替换掉的 SN。删除 `sn` 列后该表失去主语，直接废弃。
但决策 32 引入的 `asset_unique_values` 带 `archived_at` 列，
任何唯一字段的旧值都会留档并参与精确匹配 —— 覆盖面比原来的「只有 SN」更宽。

存量 demo 数据中已生成的 `sn` 值**直接丢弃**，迁移后用 `nexus seed` 重建。

## 二、唯一值反查表

### 决策 31：精确匹配覆盖所有标为唯一的字段

**推翻 v1 决策 11** 中「精确匹配走 `sn` / 旧 `sn` / `mac`」的硬编码列表。

扫码搜索按顺序尝试：**任一唯一字段的当前值 → 任一唯一字段的历史值 → UUID 全值**。
命中唯一一条时直接跳转详情页，与 v1 行为一致。

好处：扫设备铭牌上的厂商序列号、扫资产标签、扫 MAC 都能直达，
不再需要在代码里硬编码 `mac` 这个 key。

### 决策 32：新建 `asset_unique_values` 反查表

```
asset_unique_values(
  asset_id    TEXT NOT NULL REFERENCES assets(id) ON DELETE CASCADE,
  field_key   TEXT NOT NULL,
  value       TEXT NOT NULL,
  archived_at TEXT,                       -- NULL 表示当前值
  created_at  TEXT NOT NULL
)
CREATE UNIQUE INDEX ux_uv_live ON asset_unique_values(field_key, value) WHERE archived_at IS NULL;
CREATE INDEX ix_uv_value  ON asset_unique_values(value);
CREATE INDEX ix_uv_asset  ON asset_unique_values(asset_id);
```

一张表同时解决三件事：

1. **唯一性校验**变成真正的 DB 级约束。
   v1 的 `SELECT`-then-`INSERT` 仅因写连接池为 1 且 `BEGIN IMMEDIATE` 串行化写入才成立；
   现在由部分唯一索引兜底，**「写连接池为 1」从正确性前提降级为性能选择**。
   章程中的该条硬规则据此放宽 —— 但保持现状不改，因为放宽没有收益。
2. **精确匹配**一次索引命中，不再全表扫 `json_each`。
3. **历史值**：`archived_at` 非空的行即旧值，承接废弃的别名表。

**一致性责任**：该表是 `assets.attrs` 的派生物，写入管线在同一事务内维护。
漂移风险由 `nexus verify` 新增的对帐项覆盖（决策 40）。

### 决策 33：值变更时归档旧行

唯一字段的值发生变化时，旧行 `archived_at` 置为当前时间，新值插入一行。
被归档的值仍参与精确匹配，但**不再参与唯一性约束** —— 部分索引的 `WHERE archived_at IS NULL` 保证了这一点。

**允许旧值被别的设备重新占用。** 这与 v1 决策 12「编号不可重用」相反：
v1 的规则是为防止编号回收造成历史混淆，但推广到所有唯一字段后会误伤真实场景 ——
换主板后旧 MAC 出现在另一台设备上是完全正常的。精确匹配命中多条时退化为列表，不做唯一跳转。

## 三、绑定与依赖

### 决策 34：绑定表达式键时递归校验整条依赖链

把表达式键绑定到类别时，递归展开其依赖：`A` 依赖 `B`，`B` 又依赖 `C`，则 `B` 与 `C` 都必须已在
该类别的有效字段集（含继承）内。缺任何一环则拒绝绑定，**错误信息列出缺的是哪些 key**。

**推翻 v1 决策 8** 中「引用不存在的键在求值时报错」的时机 —— 那太晚了：
配置错误只有在第一次录入资产时才暴露，且错误指向表达式键而非真正缺失的字段。

### 决策 35：绑定表达式键时强制其依赖为必填

递归依赖中的所有**静态键**必须已标为 `required = 1`，否则拒绝绑定，并列出要先改哪几个。

理由：决策 36 规定求值失败一律阻止保存，而依赖为空必然导致求值失败。
两条叠加的结果是「任何被表达式键读取的静态键都事实上变成必填」——
这个联系在配置页上完全看不出来，会以「为什么这台存不进去」的形式反复出现，
且错误指向表达式键而不是真正缺值的那个字段。本决策把隐形约束变成显式约束。

### 决策 36：表达式键求值失败一律阻止保存

维持 v1 行为不变。任何表达式键求值失败都回滚整次保存，不存半个状态。

### 决策 37：解绑与停用字段对称拦截

`Unbind` 新增反向依赖检查：若同一类别（或其子树）上存在读取该字段的表达式键，拒绝解绑。

这是 v1 已有的 `ArchiveField` 拦截的镜像。v1 只堵了停用方向，解绑方向敞开 ——
把 `mac` 从类别上解绑，该类别下所有资产立刻永久存不进去，且没有任何提示指向这次解绑。

`ReferrersOf` 的 `Kind` 取值中 `"category"`（sn_template 引用）随决策 26 一并移除，
只剩 `"field"`。

## 四、流转、型号与库存点

### 决策 38：详情页流转入口 —— 单按钮 + 共享弹层

资产详情页新增「流转」按钮，打开弹层选择目标状态与持有方。
**弹层是共享组件**：列表页的多选动作条按钮直接打开同一弹层并预选动作。

两处底层行为完全一致，只是入口密度不同（详情页单台、列表页批量）。
这样满足章程「用户体验一致性」原则 —— 同一操作只有一种交互形状。

单台操作时**不生成 `batch_id`**，与 v1 决策 17 一致。

### 决策 39：型号选择器与 `attr_defaults` 覆盖确认

- 录入页与详情页**都提供型号选择器**，可选范围限于该资产类别及其祖先链上的型号。
- 录入页选择型号时，`attr_defaults` 预填尚未填写的键（沿用 v1 决策 14 的拷贝语义）。
- 详情页更换型号时，**弹窗逐键展示 `当前值 → 新默认值`**，由操作者决定是否覆盖。
  不静默覆盖，也不静默跳过。

系统不记录某个值的来源（人工输入还是型号默认值），因此弹窗列出新型号 `attr_defaults` 中的**全部**键，
不试图猜测哪些「被人工改过」。

### 决策 40：默认库存点只能更换，不能取消

- `PATCH /holders/:id` 传 `is_default_stock: false` **返回明确错误**，不再静默返回 200。
- 界面上，当前默认库存点显示徽标，其他位置显示「设为默认」。
- **停用当前默认库存点时拒绝**，提示先把默认转移到别处。
  v1 的 `Archive` 会顺手把 `is_default_stock` 清零，那是取消默认的后门，与本决策直接冲突。

「没有默认库存点」这个状态仍然存在（系统初始态），但一旦设定就不可逆回。
归还操作在没有默认库存点时要求显式选择位置，此行为不变。

## 五、保存管线的变化

v1 的十阶段收缩为九阶段，编号相关的两步消失，唯一性一步换了实现：

| | v1 | v2 |
| --- | --- | --- |
| 1 | 解析有效字段集 | 不变 |
| 2 | 合并型号默认值 | 不变 |
| 3 | 归一化 | 不变 |
| 4 | 校验 | 不变 |
| 5 | 表达式键求值（拓扑序） | 不变 |
| 6 | **生成 SN** | **删除** |
| 7 | 唯一性校验（事务内 `SELECT`） | **写 `asset_unique_values`，由 DB 约束兜底** |
| 8 | **归档旧 SN** | **归档旧唯一值**（决策 33） |
| 9 | 乐观锁写入 | 不变 |
| 10 | 发出流转事件 | 不变 |

**「归一化必须早于唯一性」这条硬规则不变** —— 它是 `AA:BB:CC` 与 `aa-bb-cc` 被判为同一个 MAC 的唯一保障。

## 六、迁移

`migrations/002_identity.sql`：

1. `DROP TABLE asset_sn_history`
2. `DROP INDEX ix_assets_mac`（唯一值反查表接手，表达式索引不再需要）
3. 重建 `assets`：去掉 `sn` 列（SQLite 无法直接 `DROP COLUMN` 一个带 `UNIQUE` 约束的列）
4. 重建 `categories`：去掉 `sn_template`，加上 `display_key`
5. 新建 `asset_unique_values` 及其三个索引

存量数据不做转换，`nexus seed` 重建。

## 七、本轮修复的既有缺陷

| 缺陷 | 影响 |
| --- | --- |
| `Unbind` 零依赖检查 | 解绑被引用的字段可让整个类别永久无法保存资产 |
| `Archive` 静默清除 `is_default_stock` | 停用默认库存点是取消默认的后门 |
| `PATCH is_default_stock=false` 静默 200 | 什么都没做却报告成功 |
| `listBlockersSQL` 依赖 `sn` 列并 `ORDER BY sn` | 删列后直接报错，本轮一并改为按 `display_key` 求值后的显示名排序 |
