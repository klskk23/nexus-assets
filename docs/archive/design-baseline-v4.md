# 设计基线 v4 —— 状态成为可配置的数据

本文承接 v1（决策 1–24）、v2（25–40）、v3（41–52），记录决策 **53–60**。
冲突时以最新一版为准：**v4 > v3 > v2 > v1**。

---

## 缘起

五个状态自 001 起就是 Go 里的常量。它们不只是标签 —— 每一个都携带行为：

| 行为 | 目前的实现 |
| --- | --- |
| 合法转换 | `legalTransitions` 5×5 矩阵 |
| 在库必须放在位置 | `RequiresLocationHolder` 硬编码 `in_stock` |
| 报废不计入类别分布 | `overview.go` 里硬编码 `retired` |
| 签出 / 归还的推导 | `DeriveTransferKind` 硬编码 `in_stock ↔ in_use` |
| 中文标签 | `web/src/i18n/zh.ts` 与 `internal/importer/export.go` **各存一份** |

要允许自定义状态，这五处都得从「按常量判断」改成「按数据判断」。

---

## 一、状态表

### 决策 53：状态成为一张表，内置的五个作为种子数据

新建 `statuses` 表，主键是 key（`in_stock` 等）。内置五个由迁移写入，
`builtin = 1`；管理员新增的 `builtin = 0`。

`assets.status` **不加外键**。理由与 `field_definitions` 的删除保护一致：
应用层已经有「有资产使用则拒绝删除」的检查，再加一次表重建（`assets` 的第三次）
换不到新的保证。

### 决策 54：行为从常量变成列

每个状态携带三个开关，取代原先硬编码的三处判断：

| 列 | 取代 | 内置默认 |
| --- | --- | --- |
| `requires_location` | `RequiresLocationHolder` | 仅 `in_stock` 为真 |
| `counts_as_available` | overview 里的「排除 retired」 | 仅 `retired` 为假 |
| `terminal` | 转换矩阵里「retired 是终态」 | 仅 `retired` 为真 |

`terminal` 是把一条内置规则一般化：任何状态都可以被标为终态，而不只是报废。

### 决策 55：转换规则 —— 内置之间沿用原矩阵，涉及自定义则放行

**双方都是内置状态**时，沿用 v1 的 5×5 矩阵，一条不改。
`lost → in_repair`、`lost → in_use` 仍然被拒绝。

**任一方是自定义状态**时，允许转换（`from` 被标为终态的除外）。

理由：矩阵编码的是这五个状态**已知的语义**。自定义状态的语义系统并不知道，
凭什么说某个转换是错的？拒绝会让自定义状态变得无法使用。

这样切分的代价是规则不再是一张整齐的表；换来的是**现有的每一条护栏都原样保留**，
没有一处既有行为因为引入自定义状态而变松。

### 决策 56：签出 / 归还仍然绑定内置的 in_stock ↔ in_use

`DeriveTransferKind` 不改。「签出」「归还」是这两个内置状态之间的移动的名字；
自定义状态之间的移动记为 `status_change`，这已经是现有的兜底分支。

## 二、标签与颜色

### 决策 57：状态标签移入数据库，`zh.status` 撤销

标签此前在 `web/src/i18n/zh.ts` 与 `internal/importer/export.go` **各存一份**，
本来就是一处等着漂移的重复。状态可配置之后它必须来自数据库。

这不违反「用户可见文案集中在 i18n」——那条规则针对的是**代码里写死的文案**。
状态标签现在是管理员输入的数据，与信息项的 `label`、类别的 `name` 同一性质。

### 决策 58：颜色从固定色板里选，不是自由的十六进制

`statuses.color` 存色板里的名字（`green`、`amber`…），不存 `#RRGGBB`。

理由：自由颜色在暗色主题下必然翻车 —— 一个在浅色下好看的浅黄，在深色底上会刺眼或看不清。
色板在 `index.css` 里为两套主题各定义一次，管理员选的是「语义位置」而不是像素值。

**内置五个的默认色**（本轮设定）：

| 状态 | 颜色 | 理由 |
| --- | --- | --- |
| 在库 `in_stock` | `green` | 可用、正常，是希望看到的状态 |
| 已签出 `in_use` | `blue` | 也是正常状态，但设备不在手上 —— 与在库要一眼能分开 |
| 维修中 `in_repair` | `amber` | 需要留意，尚未变坏 |
| 丢失 `lost` | `red` | 出事了 |
| 已报废 `retired` | `slate` | 终态、不再活跃，视觉上应当退到背景里 |

## 三、生命周期

### 决策 59：内置状态不可删除，自定义状态在无资产使用时可删

内置的五个携带上表里的行为，删掉会让系统失去语义。它们可以改标签和颜色，不能删除。

自定义状态在**没有任何资产处于该状态**时可以删除；有则拒绝，并列出前几台与总数。
与信息项、类别的删除是同一条规则。

### 决策 60：历史里出现过的状态，删除时提示而非拒绝

`asset_transfers.from_status` / `to_status` 里可能留有该状态。删除后，时间线上
那几条会显示原始键名而不是标签（前端本来就有 `?? event.to_status` 的兜底）。

**提示而不是拒绝**：拒绝会让一个用过一次的自定义状态永远删不掉，而这里的退化是
可读性下降而非数据丢失。确认框会说明它在历史里出现过多少次。

这与 v3 决策 47（删除类别时解除型号关联）是同一种处置：**代价说清楚，由人决定**。
