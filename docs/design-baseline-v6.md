# 设计基线 v6 —— 撤回「单选」与「引用」两种字段类型

本文承接 v1（1–24）、v2（25–40）、v3（41–52）、v4（53–60）、v5（61–63），
记录决策 **64–66**。冲突时以最新一版为准：**v6 > v5 > v4 > v3 > v2 > v1**。

---

## 缘起

字段类型从 001 起就是十种。其中两种从未挣得自己的复杂度：

| 类型 | 它承诺的 | 它实际做到的 |
| --- | --- | --- |
| `enum`（单选） | 受控词表 + 选项废弃生命周期 | 一列会重复的文本，外加一套只为它存在的 UI 与校验 |
| `reference`（引用） | 指向账号或持有方实体 | **从来没有校验过目标是否存在** —— `validate.go` 里那句「由调用方对数据库校验」的注释，没有任何调用方兑现 |

引用类型尤其站不住：设备的负责人与持有方是 `assets` 上的列，
有外键、有流转历史、有归还目的地。一个软引用的自定义字段
只是把同一个问题换了个没人看守的地方再问一遍。

## 决策 64：两种类型从 `model.AllFieldTypes` 中移除

不是「界面不再提供」，是**领域层不再承认**。
`ValidateOptions` 现在把 `enum`、`reference` 当作未知类型拒绝，
所以导入、直接调接口、老前端都无法再造出这两种字段。

随之删除的：`model.EnumChoice`、`FieldOptions` 的
`choices` / `deprecated` / `target` / `entity_types`、
`schema.ChoiceExists` / `IsDeprecatedChoice`、
`asset/validate.go` 的两个分支、导入侧的 `resolveReference` 与 `usersByName`
（后者只有引用解析在用）、五个孤立的目录键。

前端同步删除：`FieldType` 联合类型的两项、`FieldEditor` 的两段配置区、
`DynamicForm` 的 `enum` 分支与 `isDeprecated`、十二条只服务它们的文案。
前端的 i18n 孤儿检查当场抓到了这十二条 —— 这正是那条测试存在的理由。

## 决策 65：存量字段**转成文本**，而不是删除

迁移 `010_drop_enum_reference.sql` 把 `type IN ('enum','reference')` 的字段
改成 `text` 并清空 `options`。

值本来就以字符串存在 `assets.attrs` 里，所以**一个值都不会丢**，
只是不再有下拉框和废弃标记。删除字段则会连同存量数据一起丢掉 ——
为省一条迁移而销毁数据，方向反了。

回滚是有损的：哪些字段曾是单选、它的选项有哪些、引用指向谁，
转换之后就没有了。所以 Down 什么也不做（`SELECT 1`），
留下的文本字段是诚实的结果，而不是一次猜测。

---

## 决策 66：正则与校验提示移进新建表单

原来只有编辑对话框里能填 `regex` / `regex_hint`，
于是「建一个受校验的文本字段」是两步：先建出来，再打开它改。
新建表单在类型为 `text` 时展示这两项，与 `computed` 展示表达式是同一条规则：
**每种类型只显示它自己的配置**。

## 决策 67：字段配置的拒绝也要走目录

撤回两种类型后第一次现场验证，创建 `reference` 字段收到的是
**「服务器内部错误」**（code `template_invalid`）。原因是
`CreateField` 与 `ValidateOptions` 里那几句裸 `fmt.Errorf` 没有目录键，
`userText` 于是按 011 的约定退回通用文案。

一并补齐的还有正则不合法、最小值大于最大值、小数位数越界、计算项缺表达式 ——
这些在 011 之前就一直是「服务器内部错误」，只是没有人撞上：
编辑对话框以外没有地方能填它们。**决策 66 把正则搬进新建表单，
等于把这条坏消息摆到了最常走的路上**，所以必须一起修。

与决策 63（默认库存点报 500）是同一类：
**能被操作者一次改对的输入，不该报成服务器故障。**
测试改为按目录键断言（`i18n.HasKey`），不再按中文措辞。

## 决策 68：改表达式即重算，两件事合成一次决定

原来是两个按钮、两个页面：在字段页改表达式，再到类别页按「重算存量数据」。
中间那句文案 ——「改动表达式只影响之后新建的资产。存量资产需要显式重算」——
如实描述了这个设计，也如实暴露了它的问题：**它把一致性交给了人的记性**。
忘记按第二个按钮，机队就一半按新规则编号、一半按旧的，而且不会有任何提示。

现在：字段编辑器里保存一个**表达式变了**的计算项，会弹确认框
（「保存会立刻按新规则重算所有使用它的存量资产；不重算就不保存」）。
确认 → PATCH 字段 + `POST /fields/:id/recompute?dry_run=false`；
取消 → 什么都不保存。只改标签不触发，因为它改变不了任何存量取值。

类别页的重算按钮与那句文案一并删除，`displayKey` 只剩「选哪个字段当编号」。

### 新端点 `POST /fields/:id/recompute`

类别端点问的是「把这棵子树重编一遍」；字段端点问的是
「让存量取值与我刚改的规则一致」—— 后者才是字段编辑器有资格问的问题。

它找出所有绑定了该字段的类别，**丢掉被祖先覆盖的那些**（绑定沿子树继承），
然后**先对全部子树做一遍试算**：第三个仓库有冲突，前两个就不许写。
理由与单棵子树用一个事务相同 —— 重编到一半比不重编更糟。

### 冲突时回滚规则

冲突意味着一台设备也没写。但字段已经 PATCH 出去了，
于是前端把 `options` **改回原值**，再把冲突列表显示在对话框里。
不回滚的话，留下的正是这套流程要消灭的状态：新设备按新规则、旧设备按旧规则。

## 决策 69：类别页也用表格，树靠缩进与行菜单表达

001–010 一直把类别页当例外：它是树，所以用 `CollapsibleTree`，
不套用「点击行编辑、右键出菜单」那套约定。代价是这一页的操作长得和别处都不一样 ——
删除是详情区里的一个按钮，解绑是每行右侧的一个按钮，都是别处已经清掉的形态。

现在与其他列表一致：

- 类别表按**深度优先顺序**排列，层级用**缩进**表达，**行点击弹出编辑对话框** ——
  与元数据表格「点击行编辑」完全一致，页面上不再有「选中态 + 右侧详情区」。
- 对话框里是这个类别的全部：名称、上级、编号字段（三者一次 `PATCH` 保存）、
  字段绑定表（绑定与解绑各自即时生效，所以放在保存按钮之外）、以及删除。
- 行右键菜单：编辑、新建子类别（预填父级）、展开或折叠子类别（无子类别时禁用）。
- **折叠为什么在菜单里**：名称单元格里放一个小箭头会连同行点击一起触发，
  一次点击出两个结果 —— 这正是 010 从别处清掉的形态。
- 字段列表也变成表格，解绑进右键菜单；**继承来的绑定禁用而不是隐藏**，
  因为它确实存在，只是不在这一层解。

代价说清楚：**没有一次性「全部展开/折叠」，深树要逐个折**。
类别数量是几十的量级，这个代价可以接受；真到了需要的时候再加，
而不是提前把树组件留在代码里。`CollapsibleTree` 与它的测试一并删除 ——
没有人渲染的组件不会自己保持正确。

顺带补上了原来缺的能力：**类别可以改名、可以改上级**（服务端 `PATCH /categories/:id`
从 001 起就支持，界面一直没有）。上级下拉里排除了自己与自己的子树。

`DisplayKeyEditor` 随之删除：它是一张独立的卡片，有自己的保存按钮，
在「一次保存」的对话框里就是第二个保存按钮 —— 两个保存按钮的表单没有人能读懂。

## 决策 70：「必填」是写入时的规则，不是数据不变量

问题从「能不能给已有设备的类别加字段」开始。实测的答案是：**一直都能**，
必填也能加 —— `POST /categories/:id/bindings {"required":true}` 返回 204，
没有任何拦截。绑定之后：

| 操作 | 结果 |
| --- | --- |
| 列表、详情 | 正常，缺的键就是不存在，旧值原样保留 |
| 签出 / 归还 / 转移 / 改状态 | 不受影响（`internal/transfer` 不走 `ValidateAttrs`） |
| 重算表达式 | 不受影响（直接写 attrs） |
| **编辑那台旧设备** | **422，`fields: {"rack": "此字段必填"}`** |

也就是「碰到才补」。这是 `ValidateAttrs` 只在写入路径上跑的自然结果。

三个选项里选了**保持行为、把话说出来**：

- 拒绝在有资产的类别上绑必填，意味着一个类别一旦装了东西就永远不能再有必填字段 ——
  代价远大于收益。
- 绑定时要求默认值并回填，等于给三年前的设备编一个机柜位，那是在造假数据。

所以改的是**界面**：绑定区勾上「必填」时，如果该类别子树下有资产，
显示一条 `Alert`，写明「已有 N 台设备……下次编辑其中任何一台时必须补上」。
台数来自 `GET /assets?category_id=…&include_descendants=true&limit=1` 的 `total`。

**勾的人不知道自己给同事埋了什么**，这才是原来的问题；能力一直都在。
行为本身在 `TestRequiredFieldCanBeBoundToAPopulatedCategory` 里钉住了。

## 决策 71：唯一性是关于类别的问题，不是关于系统的

两条规则一起改，因为它们是同一条规则的两层：

| 原来 | 现在 |
| --- | --- |
| 字段 `key` 全库唯一（`field_definitions.key UNIQUE`） | **同一条链/子树内唯一** —— 绑定时本来就在查，留这一处即可 |
| `is_unique` 的取值全系统唯一 | **绑定所在类别的子树内唯一** |

「机柜位」在路由器和交换机下各数各的，这是正常需求；
让两个互不相干的类别抢一个 `rack` 才是不正常的。

### 作用域为什么是「绑定所在类别的子树」

字段绑在哪一层，就在那一层的整棵子树里存在。绑在「网络设备」上的 MAC，
路由器和交换机都继承它，那么它的唯一性也必须跨这两者 ——
否则同一个 MAC 能在兄弟类别里各存一份。

实现上 `asset_unique_values` 加了 `scope_id`，部分唯一索引变成
`(scope_id, field_key, value) WHERE archived_at IS NULL`。
存量数据在迁移 011 里用纯 SQL 回填：对每一行，取**既绑定该键、又包含该资产、
且离根最近**的那个类别。

### 键可以重复之后，所有「按键名找」的查询都在答错问题

删除字段原来问的是「谁读了 `rack` 这个键」，于是会被
*另一个类别的* 表达式、*另一个类别的* 显示编号、
*另一棵树里* 同名键上的存量值挡住。三处都改成只看**该字段实际绑定的那些树**，
并且**没有绑定的字段谁也挡不住** —— 作用域是绑定给的。

回滚是拒绝而不是糊弄：旧的全局索引在「只在类别内唯一」的数据上建不起来，
迁移会直接失败，而不是悄悄丢掉其中一条。

## 决策 72：字段绑定类别，而不是类别绑定字段

同一个动作，问法反了会得到不同的界面。原来在类别页问「这个类别要哪些字段」，
于是字段页只是一张全局清单；键可以重复之后，那张清单里会出现两个 `rack`，
而它没有任何东西能把它们区分开。

- **字段页**加了类别筛选与翻页（`GET /fields?category_id=&offset=&limit=`
  返回 `{items,total,offset,limit}`，每项带 `category_ids`），
  并多了一列「所属类别」。
- **字段编辑对话框**里做绑定与解绑：选类别、勾必填、绑定；已绑定的类别列成表格，
  右键解绑。「必填 + 该类别已有 N 台设备」的提示（决策 70）随之搬到这里，
  因为台数取决于选中的是哪个类别。
- **类别对话框里的字段表变成只读**，并说明绑定在字段页做。
  它仍然回答「这个类别最终有哪些字段」（含继承），那是个有用的问题。
- `CrudPage` 相应支持 `list` 返回 `{items,total}`、`deps`、`filters`、`footer`
  四个口子，所以字段页仍然共用那套增删改查骨架，而不是又抄一份表格。
